# SETUP — bootstrap-инструкция для Claude и Codex

> Этот файл — инструкция для AI-агента, а не перечень команд, которые юрист должен выполнять вручную.
>
> Триггеры: «разверни legal-copilot», «setup», «установи проект», «подними проект».

Готовый сценарий рассчитан на Windows и PowerShell. В другой операционной системе сначала проверить совместимость команд и согласовать адаптацию с пользователем.

## Цель

Базовое развёртывание должно дать:

- установленное Python-окружение и зависимости проекта;
- установленный Tesseract OCR с языками `rus` и `eng` для локальной обработки сканов на Windows;
- рабочие проектные инструкции и skills для выбранного AI-раннера;
- запускаемый локальный gateway `legal-overlay`, даже если пользователь пока не подключил ни одного собственного источника;
- созданный или восстановленный пользовательский слой `profile/`;
- проверенный единый watcher входных каналов и выбранный пользователем режим
  запуска (Windows-автозапуск либо ручной);
- успешную общую проверку проекта.

Правовые корпуса, внешние базы, браузерная автоматизация, Docling и другие дополнительные возможности **не входят в обязательный baseline**. Tesseract OCR на Windows входит в стандартное развёртывание, поскольку используется при локальной обработке сканов и обезличивании документов.

## Общие правила

1. Сначала развернуть и проверить базовую среду, затем предложить дополнительные возможности.
2. Не предполагать, что у пользователя есть конкретная база, snapshot, подписка, ключ или учётная запись.
3. Не просить присылать пароли, токены и ключи в чат. Пользователь сохраняет их локально в `profile/settings/`.
4. Перед системной установкой, авторизацией, крупной загрузкой или изменением внешней конфигурации объяснить действие и дождаться подтверждения.
5. Не записывать машинные пути, версии локальных баз, имена пользователя или сведения о подключениях в публичные файлы репозитория.
6. При ошибке остановиться, показать фактический результат и не отмечать шаг как выполненный.

## Шаги базового развёртывания

### Шаг 1. Диагностика окружения

Из корня проекта проверить обязательные компоненты:

```powershell
"=== git ==="; (Get-Command git -ErrorAction SilentlyContinue).Source
"=== python ==="; (Get-Command python -ErrorAction SilentlyContinue).Source
"=== powershell ==="; $PSVersionTable.PSVersion
"=== tesseract ==="; (Get-Command tesseract -ErrorAction SilentlyContinue).Source; Test-Path "C:\Program Files\Tesseract-OCR\tesseract.exe"
"=== project ==="; Test-Path README.md; Test-Path CLAUDE.md; Test-Path AGENTS.md
"=== git checkout ==="; git rev-parse --show-toplevel; git branch --show-current
"=== watcher ==="; Test-Path tools\watch\cli.py
```

Если Python отсутствует, предложить установить Python 3.10+ официальным способом. UAC-подтверждение выполняет пользователь.

Штатное развёртывание выполняется из `git clone`, а не из GitHub Download ZIP:
git-метаданные нужны для обновлений, определения основного checkout и безопасной
работы из worktree. Если `.git` отсутствует, остановиться и предложить заново
клонировать репозиторий по `INSTALL-SPLIT.md`; не сообщать, что управляемая
установка завершена.

### Шаг 1а. Профиль пользователя

Проверить наличие профиля:

```powershell
Test-Path profile\profile.yaml
```

Если профиль отсутствует, предложить создать его:

```powershell
python tools/profile/relink.py --name "<имя пользователя>"
```

Не требовать имя: без `--name` используется имя учётной записи ОС. Если профиль перенесён с другой машины, действовать по `profile/README.md` и не перезаписывать его содержимое.

### Шаг 2. Установить Python-зависимости

```powershell
python --version
python -m pip install -r requirements.txt
```

Если установка требует изменения системного Python или прав администратора, сначала показать пользователю, что будет установлено, и получить подтверждение.

### Шаг 2а. Установить и проверить Tesseract OCR

На Windows Tesseract с языками `rus` и `eng` входит в стандартное развёртывание. Сначала найти уже установленный исполняемый файл через `Get-Command tesseract` и стандартные каталоги `C:\Program Files\Tesseract-OCR\` и `%LOCALAPPDATA%\Programs\Tesseract-OCR\`. Если Tesseract найден, повторно его не устанавливать.

Если Tesseract отсутствует, показать пользователю следующую команду, объяснить, что это системная установка локального OCR, и дождаться подтверждения:

```powershell
winget install UB-Mannheim.TesseractOCR --source winget
```

После установки определить фактический путь к `tesseract.exe` и проверить версию и языки:

```powershell
& "C:\Program Files\Tesseract-OCR\tesseract.exe" --version
& "C:\Program Files\Tesseract-OCR\tesseract.exe" --list-langs
python -c "from tools.doc_ingest import ocr_runner; print(ocr_runner.tesseract_available())"
python tools\doc_ingest\test_ocr.py
```

Если Tesseract установлен в другом месте, использовать найденный фактический путь, а не переписывать публичные файлы проекта под конкретную машину. Если код не находит нестандартный путь, предложить пользователю добавить каталог установки в локальный `PATH` и дождаться подтверждения перед изменением системной настройки. В списке языков должны присутствовать `rus` и `eng`. Если одного из них нет, предложить добавить языковой пакет через установщик UB Mannheim и повторить проверку. Не сообщать о полной готовности OCR, пока версия, оба языка и smoke-тест не подтверждены. Если пользователь отказался от системной установки, продолжить остальные шаги, но явно указать в финальном отчёте, что обработка сканов и OCR-зависимые сценарии недоступны.

### Шаг 3. Проверить конфигурацию раннеров

Проект уже содержит:

- `CLAUDE.md` и `.mcp.json` для Claude;
- `AGENTS.md`, `.codex/config.toml` и `.codex/agents/` для OpenAI Codex;
- канонические skills в `skills/`.

Не копировать инструкции и skills вручную в другие каталоги проекта.

### Шаг 4. Подключить repo-skills к Codex

Если пользователь работает в Codex:

```powershell
powershell -ExecutionPolicy Bypass -File tools/setup_codex_skills.ps1
python tools/codex_config_check.py
```

Скрипт создаёт `.agents/skills` как локальную ссылку на канонический каталог `skills/`. Для Claude этот шаг не нужен.

### Шаг 5. Проверить локальные настройки

Машинные пути, параметры подключений и ссылки на секреты хранятся в `profile/settings/`. Проверить, что локальные файлы исключены из Git:

```powershell
git check-ignore -v profile/settings/local.env
git check-ignore -v profile/settings/secrets.env
```

Не создавать и не заполнять secret-файлы, пока пользователь не выбрал функцию, которой они нужны.

### Шаг 5а. Подключить пользовательские локальные источники — опционально

Сначала спросить, есть ли у пользователя собственный совместимый правовой корпус, база образцов или внутренняя юридическая память.

- Если источников нет — пропустить шаг. Базовая работа проекта остаётся доступной.
- Если есть поддерживаемый snapshot — выполнить его read-only preflight и preview по `tools/legal_overlay/README.md` и `references/sqlite-snapshot-lifecycle.md`; применять путь только после показа результата пользователю и его подтверждения.
- Если структура данных другая — не пытаться подключить её как известную схему. Нужен отдельный provider profile и adapter.

Исходные базы не копировать, не изменять и не включать в репозиторий.

### Шаг 5б. Подключить внешние источники — опционально

Показать доступный локальный каталог подключений:

```powershell
python -m tools.legal_overlay.connection_setup init --confirm-write
python -m tools.legal_overlay.connection_setup status
```

Спросить пользователя, к каким источникам у него действительно есть доступ и какие из них он хочет использовать. Включать только выбранные providers. Авторизацию, OAuth-вход и сохранение credentials выполнять по инструкциям конкретного provider; секреты не выводить.

Правила выбора источников — `references/external-legal-databases.md`, их доказательственная роль — `references/source-hierarchy.md`.

### Шаг 6. Проверить Legal Overlay

`.mcp.json` и `.codex/config.toml` должны запускать один локальный gateway `legal-overlay` без машинных endpoints и значений секретов.

Проверить конфигурацию:

```powershell
Get-Content .mcp.json | ConvertFrom-Json | Out-Null
python tools/codex_config_check.py
```

Если раннер поддерживает MCP-status, убедиться, что сам gateway запускается. Отсутствие пользовательских баз или credentials отражается как отсутствие соответствующей возможности, а не как провал базовой установки.

### Шаг 6.1. Проверить обработку документов

```powershell
python tests\doc_ingest_smoke.py
```

Обычные офисные документы и текстовые PDF обрабатываются базовым ingestion-слоем. Тяжёлые сканы и сложная вёрстка относятся к опциональному Шагу 9.

### Шаг 6.5. Проверить проектных субагентов

```powershell
Get-ChildItem .claude/agents -File
Get-ChildItem .codex/agents -File
python tools/codex_config_check.py
```

Субагенты версионируются вместе с репозиторием; скачивать их отдельно не нужно.

### Шаг 6.6. Проверить рабочие каталоги

Убедиться, что присутствуют `workflow/` и `profile/`, а реальные рабочие документы и локальные настройки не попадут в Git:

```powershell
Test-Path workflow\README.md
Test-Path profile\README.md
git check-ignore -v workflow\_local-check.tmp
git check-ignore -v profile\settings\local.env
```

Тестовый файл создавать не требуется: `git check-ignore` проверяет правило и для отсутствующего пути.

### Шаг 6.7. Базовая проверка проекта

```powershell
powershell -ExecutionPolicy Bypass -File tools/verify_project.ps1
```

Ожидаемый финал: `PASS: legal-copilot verification completed`.

### Шаг 6.8. Единый watcher входных каналов

Watcher — часть базовой установки: это один локальный Python-процесс без LLM и
сетевых запросов. Он обслуживает два режима анонимайзера и его проекты,
`_claims`, пять каналов `profile/knowledge/*/_inbox` и `_counterparty/_inbox`. Ручной watcher
Legal DD в общий процесс не входит.

Сначала проверить код и все маршруты на изолированных временных данных:

```powershell
python -m tools.watch.cli --selftest
powershell -NoProfile -ExecutionPolicy Bypass -File tools\watch\install_windows.ps1
```

Вторая команда — только preview. Показать пользователю исполняемый файл Python,
code working directory, data root, имя Windows-задачи и объяснить, что задача:

- запускается при входе текущего пользователя в Windows и сразу после установки;
- локально перемещает файлы между объявленными входными/служебными папками;
- не вызывает LLM, не ходит в сеть и ничего не отправляет;
- при переносе папки проекта или смене Python должна быть переустановлена.

После явного подтверждения пользователя установить автозапуск:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\watch\install_windows.ps1 -Install
Get-ScheduledTask -TaskName "Legal Copilot Unified Watcher" | Select-Object TaskName, State
Test-Path workflow\_watcher\watcher.log
```

Ожидается `State: Running`; скрипт `-Install` сам запускает задачу, ждать нового
logon не нужно. Если пользователь не разрешил Windows-задачу, оставить рабочий
ручной путь и явно указать в финальном отчёте, что фоновой обработки нет:

```powershell
python -m tools.watch.cli --once
python -m tools.watch.cli --daemon
```

Для Codex разрешить хуки из `.codex/hooks.json`: в приложении Codex —
«Настройки → Hooks», в терминальном Codex CLI — команда `/hooks`. Project hook
не исполняется, пока пользователь не просмотрит и не доверит его текущую версию.
Секции `[hooks]` в `config.toml` при этом нет и не должно быть.
Для Claude проверить наличие `.claude/settings.json`. SessionStart hook только
показывает агрегированное число task-card без имён и текста документов; он не
заменяет фоновый Windows watcher.

## Дополнительные возможности

### Шаг 7. Браузерная автоматизация — опционально

Нужна для сценариев, которые работают с интерактивными сайтами и формами. Если такая задача ожидается, предложить установить Node.js, `agent-browser` и Chrome for Testing. Точные команды и smoke — `references/agent-browser-cheatsheet.md` и профильный skill.

Не устанавливать браузерный стек только ради базового запуска проекта. В Codex Desktop для интерактивных задач может использоваться встроенный browser control.

### Шаг 8. Сообщить промежуточный результат

Кратко перечислить:

- что входит в готовый baseline;
- какие выбранные пользователем дополнительные возможности подключены;
- что не настроено и поэтому недоступно;
- какие ручные действия ещё нужны.

Не включать в отчёт значения секретов и не публиковать машинные пути.

### Шаг 9. Docling — опционально

Подключать для сложных PDF, сканов, многоколоночных документов, штампов и тяжёлых таблиц, когда базового ingestion недостаточно. Docling, его модели и зависимости не входят в репозиторий.

Перед установкой предупредить о размере загрузки и требованиях к диску. Полная инструкция — `references/docling-mcp-setup.md`.

### Шаг 9а. Pre-LLM обезличивание — опционально

Если пользователь хочет использовать локальный конвейер обезличивания:

1. Проверить готовность по `tools/pre_anonymize/README.md`.
2. Убедиться, что обязательная проверка Tesseract из Шага 2а пройдена.
3. После подтверждения установить локальные ярлыки:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\pre_anonymize\install-shortcuts.ps1
python tools\pre_anonymize\prepare.py selftest
```

Ярлыки и рабочие файлы остаются внутри `workflow/_anonymizer/` и не коммитятся.
Ярлык watcher делегирует уже настроенному единому `tools/watch/`; второй фоновый
процесс специально не устанавливать.

### Шаг 9.5. Финальная проверка

После подключения выбранных дополнительных возможностей снова выполнить:

```powershell
powershell -ExecutionPolicy Bypass -File tools/verify_project.ps1
```

Дополнительно проверять только те компоненты, которые пользователь действительно включил.

### Шаг 10. Финальный отчёт

Сообщить пользователю:

- готов ли базовый проект;
- какие дополнительные возможности работают;
- какие ограничения остаются;
- где лежат локальные настройки и рабочие документы.

Не записывать машинно-зависимый setup-отчёт в репозиторий. При необходимости пользователь может отдельно попросить сохранить локальную заметку в `profile/`.

## Что требует участия пользователя

- подтверждение UAC или другой системной установки;
- подтверждение создания Windows-задачи единого watcher;
- ввод credentials непосредственно в доверенном интерфейсе;
- OAuth-вход, CAPTCHA и иная интерактивная авторизация;
- выбор собственных источников и допустимых внешних сервисов;
- подтверждение крупных загрузок и изменений вне рабочей папки.

## Если что-то пошло не так

Остановиться на неуспешном шаге, показать ошибку и предложить безопасный следующий вариант. Не повторять платный запрос, авторизацию или крупную загрузку без подтверждения. Не считать компонент настроенным только потому, что его конфигурационный файл существует.
