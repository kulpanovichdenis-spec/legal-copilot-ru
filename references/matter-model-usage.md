# Структурный слой дела: matter model — timeline + factual layer (правила использования)

Единый источник истины по машиночитаемому структурному слою дела. Skills
(`legal-opinion`, `procedural-document-drafter`, `contract-review` и др.)
**ссылаются** сюда, а не копируют правила. Тул и CLI — `tools/matter_model/`
(README там же).

## Что это и зачем

Для дел с массивом документов (порог — раздел «Когда заводить factual layer», cross-document анализ) агент иначе
**каждый раз заново собирает рассуждением** хронологию событий, стороны, что
подтверждено/спорно, чего не хватает, — а результат живёт прозой в
`case-context.md` и не переиспользуется между skills и сессиями (риски — упустить
противоречие/двойной счёт, тихо превратить предположение в установленный факт).
Структурный слой выносит фактуру дела в машиночитаемые файлы в `workflow/<дело>/`
(как сроки уже вынесены в `deadlines.yaml`): один раз извлекли из документов с
traceability — дальше skills **читают готовый слой**, а не пересобирают.

Слой = три файла в папке дела, один тул `tools/matter_model/`:

| Файл | Что в нём | Ядро |
|---|---|---|
| `matter-timeline.yaml` | **Хронология** — факты-**события** (дата, участник, место, сумма) | `model.py` |
| `matter-facts.yaml` | **Factual layer** — `parties` (стороны), `facts` (факты-состояния/утверждения), `gaps` (чего не хватает) | `facts.py` |
| `matter-positions.yaml` | **Карта позиций** — `issues` (спорные вопросы), `positions` (что заявляет каждая сторона, как заявлено, с locator) | `positions.py` |

Семь объектов factual-модели (первоисточник ТЗ 2026-09-10 §6.3) покрыты: `chronology`
= события timeline; `parties`/`key-facts`/`gaps` = коллекции `matter-facts.yaml`;
`disputed-facts`/`evidence-map`/`contradictions` = **производные представления**
(вычисляются в `report`, отдельно не хранятся — один источник истины на данные).

Связь «требование↔элементы↔факты↔доказательства» хранится в аналитическом блоке
`case_structure` файла `workflow/<дело>/_llm/_analysis/case-analysis.yaml` версии 2, вне factual layer.
Метод — `references/case-structure-method.md`; схема/проверка — `tools/case_analysis/README.md`.
Ссылки F/T/G/C/I переиспользуют фактуру, не копируют её. Отдельный matter-evidence.yaml
не создаётся; document-grid остаётся вне этого внедрения.

## Когда заводить (и когда НЕ надо)

- **Заводить:** дело с массивом документов, где важна сквозная хронология и
  сверка событий между документами (напр. взыскание по цепочке актов/справок/
  реестров). Триггеры обновления — как у `case-context.md`.
- **Не заводить:** одно-двухдокументное дело или разовый вопрос — достаточно
  `case-context.md` + узких тулов (`deadline_tracker`). Не плодить артефакт ради
  артефакта (audit-принцип против инфраструктуры без нужды).

## Граница с case-context (без дрейфа)

Один источник истины на каждый вид данных:

| Данные | Где живут |
|---|---|
| Факты-события с датой и источником | `matter-timeline.yaml` |
| Факты-состояния/утверждения, стороны (реестр + реквизиты + статус), пробелы | `matter-facts.yaml` |
| Позиции сторон как заявлены, спорные вопросы | `matter-positions.yaml` |
| Сроки (что горит) | `deadlines.yaml` |
| Стадия, стратегические решения юриста, навигация, стороны **одной строкой** | `case-context.md` |
| Правовой анализ, квалификация | документы-анализы в `workflow/`; по делу целиком — `_analysis/` дела (skill `case-analysis`) |

`matter-timeline.yaml` / `matter-facts.yaml` / `matter-positions.yaml` **не дублируют** правовой анализ,
сроки и решения — только фактуру. Стороны: `matter-facts.parties` — структурный
реестр (кто есть кто + реквизиты + `req_status` + traceability); `case-context.md`
«Стороны» — навигация одной строкой. При конфликте приоритет у свежих слов юриста;
расхождение отметить и обновить слой.

## Разделение LLM vs код

- **Агент (LLM):** извлекает события из документов (через `doc_ingest`, если
  файлы), формулирует `event`, определяет `fact_status`, проставляет
  `source_doc`/`source_fragment`/`location`/`amount`/`claim_key`, **юридически
  оценивает** выданных тулом кандидатов.
- **Автоматический сборщик слоя** — `skills/matter-knowledge` (Stage B): один проход
  по разобранному делу наполняет timeline/facts из документов и строит
  документо-центричный навигатор; ручной CLI остаётся для точечных правок.
- **Тул (детерминированное, low-freedom):** валидация схемы и traceability,
  сортировка по дате, формальный детект дубликатов/двойного счёта/расходящихся
  статусов, рендер сводки. Не квалифицирует и не делает правовых выводов.

## Обязательные инварианты

1. **Traceability.** Каждое событие обязано иметь `source_doc` + `source_fragment`
   (без них тул не вносит событие). Хронология без привязки к документу
   непроверяема и не переиспользуема.
2. **fact_status — из fact-matrix**, единый источник истины —
   `references/legal-opinion-method.md`: `CONFIRMED` (подтверждён документом),
   `REPORTED` (со слов), `INFERRED` (логически следует), `DISPUTED` (противоречие),
   `UNKNOWN` (значимый факт не установлен), `ASSUMED` (рабочее допущение). Любой
   статус ≠ `CONFIRMED` рендерится с маркером `[ПРОВЕРИТЬ ФАКТ]`.
3. **Даты.** `date_status=confirmed` требует непустую `date`; иначе `needs_check`
   и маркер `[ПРОВЕРИТЬ СРОК]` (та же дисциплина, что в `deadline_tracker`).
4. **Кандидаты — лид, не вывод.** Тул помечает формальные совпадения (двойной
   счёт, конфликт статусов) как **кандидатов на проверку**; юридическую оценку
   даёт юрист. Не выдавать кандидат за установленное противоречие.
5. **Не выдумывать.** Событие, дата, сумма, место — только из источника; чего в
   документах нет — не вносить или помечать соответствующим маркером
   (`references/citation-rules.md`).
6. **Дословная цитата с местом (решения юриста 2026-10-13).** У факта и события —
   `anchor`: `quote` (дословно из `source_doc`), `location` (пункт, страница) и
   `quote_check`, который ставит код (`tools/evidence_anchor/anchor.py`): `matched` /
   `location_mismatch` / `ocr_fuzzy` / `mismatch` / `source_unavailable`. Сверка дословная,
   допускается разница только в пробелах, переносах, кавычках и тире. Цитату дают ключом
   `--quote` (место — `--quote-location`) в `model.py add`, `facts.py add-fact` и `update`.
   **`CONFIRMED` — только с цитатой, найденной в источнике** (`matched` или `ocr_fuzzy`):
   без неё запись вносится как `REPORTED` с причиной в `status_history`, а повышение до
   `CONFIRMED` через `update` отклоняется. `source_doc` можно писать именем файла — код
   найдёт его в папке дела; в проекте анонимайзера сверка идёт по `*.anon.md`.
   Пересверка всего дела после замены документов —
   `python tools/matter_model/anchors.py check --case <папка дела>` (по умолчанию только
   показывает изменения; `--write` записывает, в т. ч. понижает `CONFIRMED` без цитаты).

## Рабочий цикл (мультидок-дело)

1. `init` — создать `workflow/<дело>/_llm/matter-timeline.yaml`.
2. По каждому документу дела: извлечь события → `add` (с traceability и
   `fact_status`); для событий об ущербе указывать `location` + `amount` и общий
   `claim_key`, чтобы сработал детект двойного счёта / конфликта статусов.
3. `validate` — убедиться, что схема и traceability чистые.
4. `report` — получить хронологию + **список кандидатов** противоречий/двойного
   счёта; каждый кандидат отработать юридически (подтвердить/снять).
5. Дальше skills (`legal-opinion`, `procedural-document-drafter`) **читают**
   готовый timeline, а не пересобирают хронологию с нуля.

Команды CLI — `tools/matter_model/README.md`.

## Factual layer (`matter-facts.yaml`)

Слой между ingestion и legal research: факт отделён от юридической квалификации,
у каждого факта locator на первоисточник, слой переиспользуется downstream-скиллами
без перечитывания исходников. Три коллекции (схема полей и CLI — `tools/matter_model/README.md`):

- **`parties`** (`P-001…`) — реестр сторон: `name`, `role`
  (`our_side/counterparty/opponent/court/gov_body/third_party`), `requisites`,
  `req_status` (`verified/unverified`), обязательный locator.
- **`facts`** (`F-001…`) — объекты FACT (факты-**состояния/утверждения**, не события):
  `statement`, `fact_status` (тот же fact-matrix), обязательный locator,
  `legal_relevance` (`not_assessed/potentially_relevant/material`), `contradicted_by`,
  `related_events` (связь на `T-…` timeline), `status_history`.
- **`gaps`** (`G-001…`) — объекты GAP: `unknown`, `why_relevant`, `potential_evidence`,
  `status` (`open/searching/resolved/unavailable`).

Производные представления в `report` (не хранятся, DRY): **evidence-map**
(факт/событие → документ), **disputed-facts** (DISPUTED + `contradicted_by` +
`status_conflict` из timeline), **contradictions** (кандидаты: fact-уровень + timeline).

### Жёсткие принципы (≤7)

1. **Inference не становится established fact по умолчанию** (риск №1). Факт со статусом
   `REPORTED/INFERRED/ASSUMED/UNKNOWN` **нельзя тихо повысить** до `CONFIRMED`:
   повышение через `update` требует нового/изменённого `source_doc`+`source_fragment`
   (появилось доказательство), иначе тул отказывает; смена статуса пишется в
   `status_history`. Архитектурное правило, не только маркер.
2. **Каждый существенный факт — с locator** (`source_doc`+`source_fragment`); тот же
   инвариант, что у timeline — тул не вносит `party`/`fact` без locator'а. У `gap`
   вместо доказательства обязателен `why_relevant`.
3. **Факт отделён от юридической квалификации.** `legal_relevance` — отдельное поле
   (дефолт `not_assessed`); построение слоя **не присваивает** правовой вес; `material`
   ставит юрист/агент при анализе, тул — никогда сам.
4. **Factual model = persistent matter state, переиспользуется** заключением/иском/
   отзывом/претензией/evidence-matrix. Downstream **читает** слой, не пересобирает
   (см. «Проводка downstream»).
5. **Правка юриста без переписывания результата** — одна команда `update` (одно поле,
   ревалидация); правку `fact_status`/`source` юрист (или агент по его слову) фиксирует
   в `feedback-log` (`skills/feedback-log`).
6. **Кандидат — лид, не вывод** (как в timeline): детект противоречий/двойного счёта —
   кандидаты; юридическую оценку даёт юрист. Авто-противоречий как установленных нет.
7. **Не выдумывать; не смешивать юрисдикции; конфиденциальность.** Сторона/факт/сумма —
   только из источника (иначе маркер, `references/citation-rules.md`); слой в `workflow/`
   (gitignore) — необезличенные данные допустимы.

### Проводка downstream (переиспользование слоя)

Downstream-skill для мультидок-дела с собранным factual layer **читает готовый слой,
а не пересобирает фактуру из исходников**:

- `legal-opinion` (Шаг 1) — fact matrix строится из `matter-facts.yaml` /
  `matter-timeline.yaml`, если они есть; иначе как раньше (в контексте), предложив
  завести слой для мультидок-дела.
- `procedural-document-drafter` (шаги «фактическая хронология» / «карта доказывания») —
  читают готовый слой, если он есть; правовая позиция формируется **после** фактуры.
- `case-analysis` (Stage C) — ведёт `matter-positions.yaml` и читает timeline/facts;
  выводы и стратегия — только в `_analysis/` дела, не в `matter-*.yaml`.
- Слой создаётся существующими средствами агента (первоисточник §10 этап 2); полный
  local-first ingestion pipeline для этого не обязателен.

### Когда заводить factual layer

**Только мультидок-дело.** Порог задан в коде, в одном месте: `KNOWLEDGE_MIN_DOCS` в
`tools/case_intake/knowledge_gate.py` (сейчас 3 документа без служебных файлов, `Проекты/`,
`_knowledge/`, `_analysis/`). Проверка — `python tools/case_intake/knowledge_gate.py "workflow/<дело>"`.
Приём (`case-intake`) пишет этот статус в отчёт раскладки, а `queue_cli complete` не закрывает
задачу приёма, пока слой нужен и не собран. Одно-двухдокументное дело или разовый вопрос →
`case-context.md` + узкие тулы; не плодить артефакт ради артефакта.

## Слой позиций (`matter-positions.yaml`)

Третья коллекция слоя (тул `tools/matter_model/positions.py`). Ведёт skill
`case-analysis` (Stage C).

- `issues` (I-001…) — спорные вопросы: `question`, `status` (`proposed`; юрист на чекпоинте
  ставит `confirmed` или `dropped`), `depth` (`quick`/`standard`/`deep`), `stance`
  (`neutral`/`position_led`), `desired_position` (обязателен при `position_led`).
- `positions` (C-001…) — что **заявляет** сторона: `party_ref` (из `matter-facts.parties`),
  `issue_ref`, `kind` (`claim`/`argument`/`defense`/`procedural_request`), `statement` (как в
  документе), `evidence[]`, `stated_basis` (на что сослалась сторона, это не наша проверка),
  `source_doc` + `source_fragment` (обязательны).
- Позиция — факт о деле («сторона утверждает X»), не установленный факт и не вывод. Оценка
  правоты, калибровка и стратегия живут в `_analysis/` дела, не здесь.
- Лиды `report` (`unanswered` / `no_evidence` / `unverified_quote` / `empty_issue` /
  `no_our_side`) — формальный детект для чекпоинта, не вывод.
- **Доказательства позиции — цитатами (Т3, 2026-10-13).** `positions.py add-support --id C-00N
  --source-doc D --quote "дословно" [--quote-location "п. 5.1"] --stance supports|contradicts`:
  цитата сверяется с источником сразу. Состояние позиции: `gap` (нет подтверждающей цитаты),
  `needs_evidence` (цитаты не найдены в источнике или доказательство только названо в
  `evidence[]`), `disputed` (есть опровергающая цитата) — вычисляет код; `supported` /
  `partial` — суждение агента (`set-state`), допустимое только при проверенной подтверждающей
  цитате и без опровергающей. `mark-checked` — отметка «проверено юристом».
  `positions.py report --chart` — карта «позиция → цитата → опровержение → состояние»,
  пробелы и спорное первым блоком. Перефраз в кавычках не ставится: без цитаты — пересказ
  без кавычек с местом.
- Downstream: `procedural-document-drafter` читает карту и `case_structure`, если они есть,
  вместо повторного сбора позиций. Проверить свежие материалы и изменения стадии;
  метод передачи и доказательственный фильтр — `references/case-structure-method.md`.
  Правовые оценки остаются в `_analysis/`, не в карте заявленных позиций.

## Конфиденциальность

`matter-timeline.yaml` живёт в `workflow/` (в `.gitignore`) — допустимы
необезличенные данные (реквизиты, суммы, ПДн), как и для `case-context.md`.

## Формат для юриста

Сам yaml и markdown-`report` — рабочие материалы **агента**. Если хронология
нужна юристу как итог — отдать `.docx` (сборка — `references/docx-generation.md`),
не отдавать yaml как результат.
