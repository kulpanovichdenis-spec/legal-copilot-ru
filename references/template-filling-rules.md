# Template Filling Rules — работа по образцу

Назначение: единые правила, как заполнять документ по образцу (типовое ходатайство, заявление, уведомление, формальное письмо, ДС по шаблону, претензия по шаблону, заявление о судебных расходах и т. п.), когда часть документа постоянна (форма), а часть берётся из конкретных первоисточников (объективные данные).

Файл обязателен к применению во всех случаях, когда юрист передаёт **образец** и просит подготовить документ под конкретный случай.

**Граница с составлением договора.** Если юрист не просил заполнить конкретный образец, а нужен новый договор или новый документ комплекта (`skills/contract-drafter/SKILL.md`), структура образца **не наследуется**: она строится по жизненному циклу сделки, а образцы дают формулировки (`references/contract-design.md` раздел 5; решение юриста 2026-09-14). Правило «форма наследуется из образца» ниже действует, когда юрист прямо поручил работу по образцу.

## 1. Базовое разделение

При работе по образцу различай:

- **Форма** — структура документа, расположение блоков, стандартные формулировки, оформление, разметка реквизитов. Форма наследуется из образца без изменений.
- **Объективные данные** — все фактические значения: стороны и их реквизиты, адресаты, адреса, номера дел / договоров / постановлений, УИН, суммы, даты, наименования объектов. Объективные данные **всегда** сверяются с первоисточником, даже если значения совпадают с образцом.

Что относится к форме, а что — к объективным данным, определяется по типу документа. См. раздел 5.

## 2. Правило 1. Карта полей до заполнения

До любой подстановки выполняется следующее:

1. Выписать список **всех** объективных полей в образце.
2. Для каждого поля указать первоисточник (постановление, договор, квитанция, реестр, выписка, доверенность, переписка).
3. Извлечь значение из первоисточника.
4. Только потом подставлять.

Карта оформляется по `templates/sample-prep/field-mapping-template.md`. Без карты подстановка не начинается.

### Фирменные бланки конкретной организации — не часть формы

Если образец оформлен на фирменном бланке (логотип, реквизиты организации, адрес, телефон, e-mail, шаблон шапки с исх. № и датой) — **этот бланк не часть формы**, а объективные данные конкретной организации. Бланк из образца **не копируется** в новые документы.

Для новых документов используется бланк той организации, от имени которой готовится документ. Если бланка нет — оформляется нейтральная шапка с обязательными элементами (наименование, адрес, контактные данные, исх. № при необходимости).

Из образца на фирменном бланке берётся **только содержательная часть**: заголовок, фабула, требование, перечень приложений, подпись (как структурный блок, без конкретных ФИО и должности).

## 3. Правило 2. Не наследовать поля автоматически

Запрещено:

- считать, что адресат в образце применим к новому случаю;
- считать, что ФИО / наименование заявителя из образца применимо к новому случаю;
- считать, что номер дела / договора / постановления из образца применим к новому случаю;
- считать, что реквизиты сторон, адреса, банковские реквизиты, ИНН/ОГРН/КПП из образца применимы к новому случаю;
- считать, что сумма / дата / срок из образца применимы к новому случаю;
- считать, что приложения из образца применимы к новому случаю.

Любое объективное поле копируется из образца только после явной сверки с первоисточником.

**При случайном совпадении значений** (один и тот же суд, одно и то же лицо в нескольких документах, один и тот же договор) сверка всё равно обязательна. Совпадение не подменяет проверку.

## 4. Правило 3. Соответствие нескольких источников

Если объективное поле упоминается в двух и более источниках, значения должны совпадать. Примеры:

- УИН должен совпадать в постановлении и в квитанции об оплате штрафа;
- номер договора должен совпадать в дополнительном соглашении, в платёжных документах и в актах;
- сумма требования должна совпадать в претензии, в расчёте и в первичных документах;
- ИНН/ОГРН должны совпадать в договоре, в выписке из ЕГРЮЛ и в платёжных документах.

Несовпадение — стоп-сигнал. Фиксировать маркером `[ПРОВЕРИТЬ СООТВЕТСТВИЕ ИСТОЧНИКОВ]` и не подставлять никакое из значений до выяснения.

## 5. Правило 4. Один первоисточник = один документ

Если задача — подготовить несколько документов по образцу (например, 5 ходатайств по 5 постановлениям, 3 претензии по 3 договорам), каждый документ заполняется по своему первоисточнику. Цикл одинаковый, источники разные. Поля **не переносятся** между документами.

После генерации серии документов — обязательная проверка: ни одно поле случайно не унаследовалось из соседнего документа в серии.

## 6. Правило 5. Адаптация образца под смежную ситуацию

Образцы в слое `legal-document-samples` — **не банк готовых форм 1:1**. Это набор структурно-стилистических паттернов, переносимых на сходные документы.

Если для конкретной ситуации **нет точного образца**, берётся **ближайший** и адаптируется:

- ближайший по типу документа (ходатайство → ходатайство; претензия → претензия; отзыв → отзыв);
- ближайший по процессуальному режиму (ГПК → ГПК; АПК → АПК; КоАП → КоАП);
- ближайший по существу (истребование у частного лица ↔ истребование у госоргана; претензия по поставке ↔ претензия по оказанию услуг).

Алгоритм адаптации:

1. Идентифицировать тип документа в новой задаче и применимую норму (для процессуальных документов — норму, регулирующую содержание).
2. Подобрать ближайший образец в личном слое профиля `profile/knowledge/document-samples/cards/` (Glob+Read; навигатор `references/legal-document-samples-usage.md`). Если несколько — взять структуру более универсального, формулировки — более точного по существу.
3. Проверить новый тип документа против нормы — какие обязательные элементы требуются (могут отличаться от элементов в образце).
4. Перенести структуру и формулировки. Адаптировать к обязательным элементам новой нормы — добавить недостающие блоки, переформулировать те, что относятся к другому процессуальному режиму.
5. Заполнить объективные данные из первоисточника (см. правила 1–4).
6. Указать в карте полей: «Образец взят как структурный пример (укажи имя файла); адаптация под [новый тип]; добавленные блоки: [перечень]; пропущенные блоки: [перечень с обоснованием]».

Запреты при адаптации:

- нельзя переносить норму из образца, если новый процессуальный режим иной (АПК ≠ ГПК ≠ КАС ≠ КоАП). Норма проверяется по новой задаче.
- нельзя сохранять обязательный элемент образца, если по новой норме он не требуется и нелогичен в новой задаче.
- нельзя опускать обязательный элемент новой нормы только потому, что его не было в образце.

При сомнениях в адаптации — `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]`.

## 7. Что входит в форму, что в объективные данные (по типам)

### 6.1. Ходатайства, заявления, уведомления, сопроводительные письма

Форма:
- структура (адресат → заявитель → блок дела → заголовок → текст → приложение → подпись/дата);
- стандартные формулировки («направляю», «прошу», «приобщить», «уведомляю»);
- расположение блока подписи и даты;
- наличие/отсутствие блока «Приложение».

Объективные данные:
- адресат: наименование суда / органа / контрагента, номер судебного участка / отдела, ФИО должностного лица если указано;
- адрес адресата;
- ФИО / наименование заявителя;
- адрес заявителя;
- номер дела / производства / претензии;
- реквизиты постановления (дата, номер);
- УИН и иные платёжные идентификаторы;
- сумма;
- дата документа;
- перечень приложений с количеством листов.

### 6.2. Дополнительные соглашения, договорные документы по шаблону

Форма:
- структура (преамбула → стороны → существо изменения → дата вступления в силу → подписи);
- стандартные оговорки («во всём остальном, что не предусмотрено настоящим Соглашением…»);
- расположение блоков «изложить в следующей редакции», «дополнить пунктом», «исключить».

Объективные данные:
- стороны: наименования, ИНН, ОГРН, КПП, адреса (юридический и почтовый), банковские реквизиты;
- ФИО, должность и основание полномочий подписантов;
- номер и дата основного договора;
- номер ДС;
- изменяемые пункты (номера, прежняя и новая редакция);
- даты: подписания, вступления в силу, ретроспективности (если есть);
- суммы (если меняются).

### 6.3. Претензии, ответы на претензии по шаблону

Форма:
- структура (адресат → заявитель → фабула → требование → срок ответа → последствия → подпись);
- стандартные формулировки требования и предупреждения о последствиях.

Объективные данные:
- стороны и их реквизиты;
- основание (номер и дата договора, основания внедоговорного требования);
- фактические обстоятельства (даты, объёмы, документы);
- расчёт суммы;
- срок ответа и порядок его исчисления;
- реквизиты для исполнения требования.

**Дата передачи/приёмки из акта, накладной, УПД — не верхняя дата документа.** Когда факт (момент передачи товара, приёмки работ/услуг, начала просрочки) берётся из акта / накладной (ТОРГ-12, ТТН) / УПД, дата в шапке — это дата составления, а не автоматически момент передачи/приёмки: смотреть дату у подписи получателя/заказчика и графу о дате получения/приёмки. Подробно — `references/contract-playbook.md`, раздел 2.5. Расхождение или отсутствие даты у подписи — `[ПРОВЕРИТЬ СРОК]` / `[ПРОВЕРИТЬ ФАКТ]`, не додумывать.

### 6.4. Заявления о судебных расходах, ходатайства о приобщении доказательств

Форма:
- структура (адресат → реквизиты дела → существо ходатайства → перечень документов → подпись).

Объективные данные:
- номер дела;
- состав суда / мирового судьи;
- стороны;
- перечень фактически приобщаемых документов с количеством листов;
- суммы (для заявлений о расходах) с расчётом.

## 7. Алгоритм работы

1. Получить образец.
2. Извлечь форму (структура + стандартные формулировки).
3. Извлечь перечень объективных полей.
4. Получить (или запросить у юриста) первоисточник для каждого поля.
5. Заполнить карту соответствия по `templates/sample-prep/field-mapping-template.md`.
6. Сверить пересекающиеся поля между несколькими источниками. Несовпадение — стоп.
7. Подставить значения в форму.
8. Проверить: ни одно объективное поле не унаследовано из образца без сверки.
9. Если генерируется серия документов — проверить, что поля не перетекли между документами серии.
10. Передать результат юристу с приложенной картой полей.

## 8. Маркеры

- `[СВЕРИТЬ С ПЕРВОИСТОЧНИКОМ]` — поле требует проверки первоисточника, даже если значение уже подставлено.
- `[ПРОВЕРИТЬ СООТВЕТСТВИЕ ИСТОЧНИКОВ]` — поле есть в двух источниках, значения не сверены или не совпали.
- `[ПРОВЕРИТЬ РЕКВИЗИТЫ]` — отдельный технический реквизит (номер счёта, БИК, КПП), не подтверждённый первоисточником.
