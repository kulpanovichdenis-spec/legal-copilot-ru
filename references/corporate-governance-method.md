# Корпоративное управление: метод разбора и политика верификации

Единый источник методики модуля «Corporate Governance» для Legal Copilot (подсистема 1: Entity Governance Layer и Charter Review). Skills ссылаются сюда, а не копируют правила. Исходное ТЗ: «Corporate Governance & Entity Management Workflow для Legal Copilot», v1.0 от 13.09.2026 (ссылки «§N» ниже — на разделы ТЗ). Ядро — `tools/corporate_governance/governance.py`, сценарий работы — `skills/charter-review/SKILL.md`.

## 1. Что это и границы

Модуль превращает устав и связанные корпоративные документы конкретного лица в проверяемые правила с привязкой к странице, пункту и дословной цитате, сопоставляет их с действующим законом и собирает для юриста матрицы компетенции, голосования, собраний и подтверждения решений.

Юрисдикция — Российская Федерация. Всё, что готовит модуль, черновик: ничего не финализируется, не отправляется и не подаётся без проверки юристом.

Вне этой подсистемы (проектируются отдельно): `competence-engine`, `decision-validity-check`, корпоративные события и календарь, АО и раскрытие информации, Health Check, Precedent Library, автоматический Change Detection.

## 2. Приоритет источников и статус данных

Иерархия при выводе (§3): императивная норма закона; допустимое законом специальное регулирование уставом; внутренний корпоративный документ; корпоративный договор (только в пределах его действия); практика компании; шаблон. Шаблон и precedent правовым основанием не являются.

| Категория | Что входит |
|---|---|
| Authoritative (§27) | закон после проверки живым маршрутом; подписанный корпоративный документ; действующий устав; подтверждённые данные реестра; запись профиля со статусом `verified` |
| Derived | извлечённое правило-кандидат, резюме, рассчитанный срок, рекомендация, флаг риска |

Derived не заменяет authoritative автоматически: правило становится `verified` только командой `confirm` по решению юриста.

## 3. Где что лежит

| Что | Где |
|---|---|
| Данные компании | `profile/knowledge/corporate/entities/<slug>/`: `sources.yaml`, `rules.yaml`, `profile.yaml`, `audit.jsonl`, `_work/` (страницы PNG и OCR-текст, регенерируемые). В `.gitignore` |
| Документы-оригиналы | `profile/knowledge/corporate/originals/` (после `tools/knowledge_ingest/intake.py`) |
| Карточки-указатели норм ООО | `references/corporate-norm-cards/llc/<slug>.md` (в git); `<slug>` — значение `topic` с дефисом вместо подчёркивания: `voting_procedure` → `llc/voting-procedure` |
| Отчёт юристу | `workflow/<YYYY.MM.DD> <компания> — разбор устава/`, формат `.docx` |

Схемы, перечни допустимых значений и правила проверки — в `tools/corporate_governance/gov_schema.py` (единственный источник). Перечни тем (§4) и классов (§5) повторены ниже для удобства чтения; при любом расхождении верен `gov_schema.py`.

Команды, меняющие данные компании, берут блокировку `.lock` в её папке на весь цикл «прочитать, изменить, сохранить, записать в аудит». Команды по одной компании запускаются по очереди, не параллельными вызовами: занятая блокировка ждёт до 10 секунд, затем команда отказывает («другая команда работает с компанией»); брошенную блокировку (процесс завершён) инструмент снимает сам через 60 секунд.

## 5. Классы правил (§8.3)

Класс присваивает агент (юридическая квалификация, класс C по `references/execution-profiles.md`) после открытия текста нормы. Правило может нести несколько классов.

| Класс | Когда |
|---|---|
| `MANDATORY_LAW` | положение повторяет норму, которую устав изменить не вправе, или опирается на неё |
| `DEFAULT_LAW` | устав воспроизводит диспозитивную норму без изменений |
| `CHARTER_OVERRIDE` | устав устанавливает иное, чем диспозитивная норма, в допустимых пределах |
| `CHARTER_OPTION` | устав использует возможность, прямо предоставленную законом |
| `INTERNAL_RULE` | правило внутренней организации, которого нет в законе |
| `CONFLICT` | положение противоречит норме, которую устав изменить не вправе |
| `POTENTIALLY_OUTDATED` | положение ссылается на норму или порядок, который мог измениться |
| `MISSING_RULE` | закон отсылает к уставу, а устав молчит: фиксируется допущением (`add-assumption`), не правилом |
| `NEEDS_HUMAN_REVIEW` | агент не может квалифицировать по открытому тексту |

Классы `MANDATORY_LAW`, `DEFAULT_LAW`, `CHARTER_OVERRIDE`, `CHARTER_OPTION`, `CONFLICT`, `POTENTIALLY_OUTDATED` опираются на закон: для них обязательны `law_ref` и блок `freshness` со статусом `verified`, иначе `confirm` откажет. Связки `MANDATORY_LAW` и `CONFLICT` независимо проверяет субагент `source-verifier` (тезис ↔ открытый текст нормы).

## 6. Legal Freshness Check (§4)

Проверка обязательна перед классификацией правила по закону и перед каждым использованием, перечисленным в §4.2 ТЗ (компетенция, кворум, большинство, срок уведомления, способ голосования и подтверждения, раскрытие, регистрация, крупные сделки и заинтересованность, органы, устав, реорганизация, капитал).

1. Вызвать `route_norm_verification(jurisdiction="RU", probe=true)` и использовать только provider с `usable_now: true`; инструменты открытия текста брать из `recommended_tools` выбранного provider. Состав маршрутов меняется, проверять в каждой сессии. Нет пригодного маршрута: записать `set-freshness --status failed --required-action "нет пригодного маршрута проверки нормы"` (у правила уже должен быть `law_ref`, см. п. 5), поставить `[ПРОВЕРИТЬ НОРМУ]`.
2. Найти акт по точному номеру и дате: для `pravo-gov-ru` это `pravo_resolve_act`, для другого provider инструмент из его маршрута. Неоднозначный результат не выбирать автоматически. Реквизиты по памяти не подставлять; реквизиты опубликования акта подтверждает `pravo-gov-ru`, даже если текст открыт через другой provider.
3. Открыть текст: для `pravo-gov-ru` структуру акта (`pravo_get_document`) и нужную статью (`pravo_get_article`), для другого provider по его маршруту. Статьи с точкой в `pravo_*` передавать слитно: `381.1` → `3811`. У части provider открытие текста расходует ограниченную квоту (например, экспорт в ГАРАНТ): открывать только статьи, нужные для правил, и не открывать одну статью повторно. Зафиксировать редакцию и статус открытого текста, как их показывает ответ.
4. Заполнить или сверить карточку-указатель `references/corporate-norm-cards/llc/<slug>.md` (`<slug>` по правилу §3): `article_or_clause`, `primary_source_url`, `rule_type`, `legal_state_at`, `verified_at`. В `update-rule --law-card` передаётся `llc/<slug>`; `validate`/`confirm` отклоняют несуществующий файл карточки и пустую `law_ref.article` у закон-зависимого правила, но саму карточку по-прежнему выбирает агент. Ориентир для `rule_type`: формулировка «если иное не установлено уставом» указывает на `default`, запрет изменения уставом на `mandatory`, прямое разрешение уставу на `optional`; решает чтение текста. Текст нормы в карточку не копируется.
5. Записать результат командой `set-freshness` (любой статус, включая `failed`, принимается только при заданном у правила `law_ref`, то есть после `update-rule --law-card`). `--checked-source` по умолчанию записывает `pravo-gov-ru`: если текст открыт через другой provider, передать `--checked-source <provider>`, где `<provider>` — идентификатор фактически использованного provider из ответа `route_norm_verification`; иначе происхождение проверки записывается неверно.
   - `verified`: текст открыт, редакция и статус подтверждены, содержание совпадает с карточкой;
   - `changed`: живой текст расходится с карточкой (указать `--differences` и `--required-action`);
   - `uncertain`: редакцию на нужную дату подтвердить нельзя (у `pravo-gov-ru` историческая редакция подтверждается «по документу» условно);
   - `failed`: норму открыть не удалось.
6. Любой результат, кроме `verified`, останавливает продвижение правила: `confirm` откажет, агент сообщает юристу и не продолжает молча (§4.3). Правило, уже подтверждённое ранее, при таком результате возвращается в кандидаты.
7. Срок годности проверки: `governance.py stale` (порог 30 дней по умолчанию, `--days`). `stale` только сообщает; `confirm` возраст проверки не сверяет, поэтому при проверке старше порога её повторяют до `confirm`. Использование правила в корпоративном событии требует повторной проверки.
8. Акты Банка России в подсистеме 1 не используются (нужны для АО, отдельный маршрут через cbr.ru проектируется в подсистеме 4). Поисковая карточка, фрагмент выдачи и локальный snapshot проверкой нормы не являются.

## 7. Provenance, сканы и OCR (§10)

Каждое правило и факт несёт `source_id`, страницу, пункт и дословную цитату; без них инструмент запись не примет.

- Первичное чтение сканов — визуально: `governance.py render-pages` кладёт PNG страниц в `_work/<source>/png/`, агент читает изображения. Цитата переносится дословно, в пределах одного пункта; страница — порядковый номер в PDF (не штамп «стр. N из M»).
- OCR (`tools/doc_ingest/ocr_tesseract.py`, локальный tesseract) недословный: встречаются ошибки в отдельных буквах и путаница порядка чтения возле печатей и штампов ЭП. Он служит поиском и нечёткой сверкой цитат (`governance.py verify-quotes`, порог 0,90), но не источником дословного текста.
- Результат сверки: `matched` (цитата найдена), `fuzzy` (найден фрагмент со сходством не ниже порога), `not_found` (похожего фрагмента нет), `unchecked` (OCR-текста страницы нет). `not_found` блокирует `confirm` до исправления цитаты или страницы; `fuzzy` и `unchecked` юрист сверяет по скану на CP3.
- Содержимое печатей, подписей и рукописных пометок не извлекается: ставить `[ШТАМП/ПЕЧАТЬ — НЕ РАСПОЗНАНА]` или `[РУКОПИСНЫЙ ТЕКСТ]` (`references/document-ingestion.md`, §5), значения из них не выводить.
- Реквизиты (ОГРН, ГРН, даты) переносить с изображения и перепроверять по реестру; OCR-значению реквизита не доверять.

## 8. Допущения: no silent assumption (§24)

Нет нужного документа, состава органа, сведений о долях, внутреннего положения, статуса эмитента или корпоративного договора: стандартное правило молча не подставляется. Фиксировать `governance.py add-assumption` с четырьмя полями: чего не хватает, какое правило действует, если специального нет, риск, что проверить. Допущение попадает в отчёт отдельным разделом. Когда недостающее получено, допущение не удаляется, а снимается `governance.py resolve-assumption --basis "<что получено>" --source-id <источник>`: в отчёте оно уходит из открытых в строку «Снятые допущения». Признак классификации компании, для которого в документах нет вообще никакой опоры (значит, нет дословной цитаты для provenance), фиксируется не фактом, а `add-assumption --topic classification` (`--missing-data` — имя поля, например `issuer_status`); факт с выдуманной цитатой ради значения `unknown` не создаётся. Значение `unknown` через `add-fact` уместно только тогда, когда сам документ прямо об этом говорит и есть настоящая цитата.

## 9. Чекпоинты юриста (§23)

| Чекпоинт | Когда | Что подтверждает юрист |
|---|---|---|
| CP1 | после извлечения | классификация компании и извлечённые факты; полноту найденных положений по темам |
| CP2 | после сопоставления с законом | конфликты, пробелы, устаревшие положения, спорные квалификации; решения фиксируются `update-rule` или `add-assumption` |
| CP3 | перед отчётом | набор правил группами по темам; `confirm` ставит `verified` |

Подтверждать можно группами, любое правило по просьбе юриста раскрывается: цитата, страница, скан, закон, результат `freshness`. Подтверждение относится к содержанию записи: любое изменение подтверждённой записи возвращает её в кандидаты.

`confirm` и ручной `set-source-status --status current` выполняются только после явного ответа юриста в текущей сессии, называющего id или группу записей к подтверждению: постановка задачи, которой началась сессия, молчание юриста и файл, оставленный в `_inbox`, подтверждением не являются. `--by` — это имя, которое юрист назвал сам, а не роль («юрист», «lawyer», «agent», «claude» и т. п. инструмент отклоняет).

Актуальность редакции устава — факт реестра, а не правовая оценка, поэтому её подтверждает сверка с официальной выпиской, без вопроса юристу. Агент получает выписку ЕГРЮЛ сам (`fetch-egrul --ogrn <ОГРН>`: сервис ФНС egrul.nalog.ru, передаётся только ОГРН; капча не обходится) и выполняет `check-edition`: если последняя действующая запись об изменении учредительного документа в выписке совпадает с ГРН на титульном листе устава, устав получает `current` с основанием «выписка S-<номер> по состоянию на <дата>» (`verified_by_extract`); если в реестре есть более поздняя такая запись или запись о редакции признана недействительной, статус `current` снимается и нужна действующая редакция (раздел 11). Записи «не связанные с изменением учредительных документов» и недействительные в расчёт не берутся. Юриста просят о выписке, только если `fetch-egrul` отказал; вручную положенная выписка регистрируется `register-source --kind egrul_extract` и проверяется той же командой. Ручной `set-source-status --status current --basis ... --by "<ФИО юриста>"` — по решению юриста, когда выписки нет. Пока редакция не подтверждена, отчёт несёт `[ПРОВЕРИТЬ АКТУАЛЬНОСТЬ РЕДАКЦИИ]`. Та же выписка по ОГРН участника-юрлица (`egrul-summary`) показывает, кто действует от его имени без доверенности: так сверяются полномочия подписанта решения участника.

## 10. Слои документов и корпоративный договор (§11)

Поле `layer` правила: `charter`, `internal`, `corporate_agreement`. Договор об учреждении регистрируется видом источника `founding_agreement`, а не `corporate_agreement`: это документ о создании общества, а не корпоративный договор участников. В выводах раздельно указывать полномочие органа по закону и уставу и договорное обязательство стороны корпоративного договора: слои не смешиваются, расхождение между ними не является дефектом устава и докладывается как отдельная находка. Кандидаты на противоречие (`governance.py inconsistencies`) ищутся по теме и предмету между всеми слоями, это лид для юриста, а не вывод.

## 11. Quality gates: что контролирует инструмент сейчас

Подсистема 1 обеспечивает данные для гейтов §34. Ниже указано, что делает инструмент: блокирует запись или подтверждение, отмечает в отчёте либо только сообщает (`stale`).

| Гейт | Как реализован |
|---|---|
| нет применимой версии устава | отчёт и проекции несут `[ПРОВЕРИТЬ АКТУАЛЬНОСТЬ РЕДАКЦИИ]`, пока нет источника `charter` со статусом `current` |
| критичный источник устарел | `stale` сообщает о правилах без проверки нормы, с не-`verified` или устаревшей проверкой (§6, п. 7); правило без `freshness` или с не-`verified` блокирует `confirm` |
| правило без provenance | `add-rule` и `add-fact` не принимают запись |
| цитата не найдена | `confirm` отказывает при `quote_check: not_found` |
| замена редакции устава | `supersede-source` переводит правила прежней редакции в `needs_review`, они не попадают в проекции и не подтверждаются |
| молчаливое изменение подтверждённого | `update-rule`, `update-fact`, `set-freshness` с результатом не `verified` возвращают запись в кандидаты |

Гейты `READY_FOR_REVIEW` и `CLOSED` для корпоративных событий (нерешённая компетенция, кворум, подтверждение, раскрытие, незавершённые filing) появляются с подсистемой 3.

## 12. Конфиденциальность и данные

Содержимое `profile/` в git не попадает, в репозиторий идут только код, методика и пустой скелет. В профиль не переносятся паспортные данные и прочие персональные данные, не нужные для полномочий: из решения о назначении берутся должность, основание, срок как правило, но не реквизиты паспорта. OCR локальный, cloud-OCR для материалов клиента запрещён (`references/document-ingestion.md`, §4.3).

## 13. Классы исполнения

| Шаг | Класс | Исполнитель |
|---|---|---|
| рендер страниц, OCR, схемы, provenance, аудит, проекции, кандидаты противоречий, `stale` | A | `tools/corporate_governance/governance.py`, `tools/doc_ingest/ocr_tesseract.py` |
| идентификация редакции, классификация компании, извлечение правил, сопоставление с законом, оценка конфликтов | C | основной агент по `skills/charter-review/SKILL.md`; не понижается |
| независимая проверка связки «правило ↔ статья» для `MANDATORY_LAW` и `CONFLICT` | C | субагент `source-verifier` |

Класс B (`intake-classifier`) в подсистеме 1 не используется: документов мало, а тип определяется по содержанию при чтении.

## Компетенция по вопросу (подсистема 2)

Вопрос «кто решает X» отвечается по каталогу решений ООО (`references/corporate-decisions/llc.yaml`) и привязке правил устава к его позициям (поле `decisions`). Привязку проставляет агент, подтверждает юрист вместе с правилом. Сценарий и статусы ответа — `skills/corporate-governance/SKILL.md`; команды — `tools/corporate_governance/README.md`.
