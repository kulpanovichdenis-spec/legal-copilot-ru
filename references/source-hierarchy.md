# Source Hierarchy

Назначение: порядок выбора источников при работе с правовыми и судебными документами. Все skills и agents обязаны учитывать иерархию при подготовке аргументации.

## Рабочий цикл для любой правовой задачи

Единый алгоритм. Все skills ссылаются на этот раздел и **обязаны выполнить его до формирования правовой позиции**. Детали каждого слоя — ниже по файлу.

**Каноническое разделение discovery и verification.** Локальная карточка,
SQLite-результат и поисковый snippet используются только для поиска и навигации.
Перед использованием нормы как правового основания открыть её полный текст и
проверить редакцию через подключённый источник с ролью `norm_verification`:
официальный портал либо профессиональную правовую систему, чьи полный текст,
редакции, статус, pinpoint и provenance подтверждены профилем и живым smoke.
Сначала вызвать `route_norm_verification(jurisdiction=..., probe=true)` и
использовать только маршрут с `usable_now: true`. Если такого маршрута нет —
поставить явный маркер непроверенности; неподключённый provider не вызывать.

1. **Legal Overlay — первая остановка для discovery.** Для тематического поиска использовать `legal-overlay.legal_search(issue=..., jurisdiction=..., source_types=[...], data_classification=...)`: namespace `legal-overlay` обозначает единый локальный gateway, а не конкретный provider и не уровень доказательности. Для точного номера акта передать `act_number` + `act_date`. `get_legal_text` раскрывает snapshot и остаётся навигацией; `get_official_article` / `get_official_document` являются проверкой только когда provenance показывает фактический live-provider. Перед правовым выводом применить каноническое разделение выше и проверить ключевой НПА через маршрут `usable_now: true`.
2. **Судебная практика — сначала через Overlay.** Начать с `legal_search(source_types=["case_law"])`; для точных полей локального корпуса использовать совместимые `search_positions(topic|article|keyword|case_number|law|link_status)` и `list_position_norm_links(unit_id)`. Если локального слоя недостаточно — основной внешний поиск через КонсультантПлюс (`consultant_search` → `consultant_get_document` / `consultant_get_text`); ГАРАНТ отключён и не вызывается. Дальше, если авторизация выполнена, — единый Casus `casuslegal_search_practice(..., corpus="main|sip|kas|kud")`, но только для corpus из локального `allowed_corpora`; карточку раскрывать `casuslegal_get_case_details` с тем же corpus. Legacy `sip_*` / `kas_*` / `kud_*` допустимы только как явно включённый fallback. Для рекламной административной практики ФАС использовать `search_fas_ad_practice` → `get_fas_case`. Поисковая карточка внешней базы не заменяет полный акт и официальную сверку. **Как вести подбор практики** — метод `references/case-law-search.md`; правила внешних корпусов — `references/external-legal-databases.md`.
2а. **Покрытие практикой — на уровне каждого тезиса, не только главной нормы.** Шаги 1–2 распространяются на **каждую норму, из которой в ответе делается вывод о правовом последствии** (утрата/преклюзия права, недействительность, невозможность требования и т. п.), включая побочные тезисы. Для каждой такой статьи — `search_positions(article=...)`; пусто → либо продолжить по шагу 5, либо калиброванная формулировка («по общему правилу», «есть риск, что…») с явной пометкой «практика по этому тезису не проверялась». **Категоричные абсолюты не используются** («лишается всех прав», «всегда», «однозначно», «невозможно» — под запретом по умолчанию; единственное исключение — тезис с позицией, проверенной по шагам 1–2). Диспозитивность нормы («если иное не предусмотрено договором») указывать всегда — она сама по себе снимает категоричность.
3. **Локальное знание / Vault / контекст.** `legal_search(source_types=["internal"])` сначала возвращает human-verified reusable knowledge, затем локальную методику, затем доступный внутренний corpus; machine candidates не входят в выдачу. `practice_pattern` из прошлых дел используется только как evidence/drafting/risk context по `references/case-knowledge-layer.md`; связанная case study раскрывается по provenance при необходимости. Для специализированных слоёв использовать совместимые `search_comments` / `search_all_legal_memory`, `search_legal_opinions`, `search_telegram_reviewed`, `search_official_labor_guidance`, `list_topic_maps` и граф. Трудовые FAQ Роструда имеют класс `administrative_guidance`: это официальные ненормативные разъяснения, которые раскрываются через `get_official_labor_guidance` и не заменяют проверку применимой нормы. **Verified knowledge подтверждает формулировку knowledge object, но не заменяет лежащий под ним первоисточник; playbooks, opinions, Telegram, MOC и comments — навигация/контекст, не источник права.**
4. **Качество и актуальность.** Для НПА с `needs_review`, actionable-проверками или `last_checked` старше 6 месяцев вызвать `route_norm_verification(jurisdiction=..., probe=true)` и сверить редакцию по `usable_now: true` provider; до этого ставить `[ПРОВЕРИТЬ АКТУАЛЬНОСТЬ РЕДАКЦИИ]`. Комментарии, доктрина, обзоры практики и Telegram — источник подхода, а не действующей редакции нормы; не ставить на них маркер редакции и не гонять по ним `check_currency`.
5. **Чего нет локально** — подзаконные акты, региональное право, а также судебная практика **вне локального слоя позиций** (за пределами тем/периодов импортированных обзоров ВС РФ). Порядок тот же: КонсультантПлюс, затем Casus / ПравоТех по их правилам, затем официальные порталы Приоритета 1 (pravo.gov.ru, kad.arbitr.ru, сайт ВС РФ, сайты ведомств). ГАРАНТ отключён. Переход помечать «в локальных базах не найдено». Не выдумывать.

   ⚠️ **Для судебной практики вне локального слоя** — внешний поиск идёт через КонсультантПлюс, затем первоисточник на kad.arbitr.ru и официальном сайте ВС РФ. Карточка К+, прочие агрегаторы и выжимки веб-экстрактора — навигационный лид. ГАРАНТ отключён. **Реквизиты конкретного судебного акта (суд, дата, номер дела) не выводятся юристу, пока первоисточник не открыт и позиция не сверена** — маркер `[ПРОВЕРИТЬ РЕКВИЗИТЫ]` не заменяет открытие первоисточника.
6. **Перед сохранением готового документа в `workflow/` — проверка каждой ссылки.** `find_federal_act` и локальные карточки дают только existence/discovery. Для каждой используемой нормы вызвать `route_norm_verification(jurisdiction=..., probe=true)`, открыть полный текст по маршруту `usable_now: true` и проверить реквизиты, редакцию, статус, pinpoint и provenance. `NOT_FOUND` в локальном реестре — пробел покрытия. Нет пригодного маршрута — `[ПРОВЕРИТЬ НОРМУ]`; сомнение в редакции — `[ПРОВЕРИТЬ АКТУАЛЬНОСТЬ РЕДАКЦИИ]`. Кратко отчитаться: проверено / не найдено / маркеров.
7. **Цитирование** — строго по `references/citation-rules.md`.

Этого раздела достаточно для типовой задачи. Слои 0a/0b/1/2/3 ниже — это подробности и граничные случаи.

## Приоритет 0. Локальный Legal Overlay и подключённые providers

Codex, Claude и Cursor подключаются к одной локальной MCP-точке под namespace `legal-overlay` (`.codex/config.toml`, `.mcp.json`, `.cursor/mcp.json`). URL, transport, fallback и provider-native schema остаются внутри Overlay. Перед ручным веб-поиском нужно проверить его provider-neutral tools и зафиксировать coverage gaps/fallbacks.

- **0a — локальная фармацевтическая правовая база** (единый Overlay, раздельные providers):
  - `local-legal-ru-sqlite` — основной immutable structured corpus: НПА, snapshot-тексты, связи, обзоры практики и судебные позиции; legacy-копии единой доктрины из пользовательской выдачи исключены;
  - `local-legal-uz-sqlite` — отдельный корпус UZ с сохранением `verification_status`;
  - `local-legal-doctrine-sqlite` — канонический единый корпус доктрины (`doctrine_only`) с произведениями, страницами, offsets и provenance;
  - `local-legal-memory-sqlite` — opinions, reviewed Telegram и MOC с сохранёнными legacy tool names;
  - образцы и клаузы не входят в корпус Overlay: `profile/knowledge/document-samples/` и `profile/knowledge/clauses/` читаются через Glob+Read;

Федеральные акты ищутся в локальном RU snapshot, но его `get_legal_text` — текст зафиксированного экспорта, не подтверждение текущей редакции. Для нормы вызвать `route_norm_verification(jurisdiction="RU", probe=true)` и использовать только `usable_now: true`. Маршрут может выбрать прямой provider pravo.gov.ru (`pravo_resolve_act` → `pravo_get_document` / `pravo_get_article`) либо подключённую профессиональную систему с подтверждёнными capabilities.

### 0a. Локальная фармацевтическая правовая база (автономный SQLite)

Все обращения идут через один локальный namespace `mcp__legal-overlay__*`. Structured/vault corpus читается из локальных SQLite providers; сервер не участвует в работе. Отдельного MCP `legal-pharma-memory` нет.

| Слой | Назначение | Инструменты |
|---|---|---|
| **`local-legal-ru-sqlite` structured** | Индекс, метаданные, связи, snapshot-текст | `search_legal_kb` / `find_by_act_number` / `get_legal_text`, `get_document_relations`, `sqlite_legal_ru_status` |
| **`local-legal-ru-sqlite` corpus** | НПА, комментарии/обзоры практики, судебные позиции и связи без legacy-дублей доктрины | `search_legal_kb` / `search_comments` / `search_positions` |
| **`local-legal-doctrine-sqlite`** | Постатейные комментарии, доктринальные позиции и литературные заметки | `search_doctrine` / `get_doctrine_unit` / `list_doctrine_sources` / `sqlite_legal_doctrine_status` |
| **`local-legal-memory-sqlite`** | Внутренний контекст и навигация | opinions, reviewed Telegram, MOC |

**Правило приоритета внутри 0a:** всё идёт через локальный Overlay. Opinions — internal context, Telegram — secondary context, MOC — navigation only. Автоматические узлы графа — локальный `list_relation_hubs`.

Не читать массово исходные vault-файлы вручную, если задачу решает локальный SQLite provider (быстрее, индексированно, со статусами и snapshot provenance).

**Гайды:**
- `references/legal-kb-usage.md` — structured runtime layer (SQLite через Overlay)
- `references/legal-pharma-memory-usage.md` — локальный vault/second-brain гайд для `legal-memory.sqlite`

### 0a-vault. Vault/second-brain — полностью локальный read-only слой

Обработанные НПА, разъяснения, обзоры практики и судебные позиции включены в `legal-ru.sqlite`. Единая доктрина включена в `legal-doctrine.sqlite`; legacy-копии с `canonical_key LIKE 'legacy-wiki:doctrine_commentary--%'` из пользовательского RU-поиска исключены. Opinions, reviewed Telegram, MOC и официальный ненормативный слой FAQ Роструда включены в `legal-memory.sqlite`. Все файлы доступны локально через Overlay; отдельного MCP `legal-pharma-memory` нет.

Доступ — через `mcp__legal-overlay__*`:

- **`search_doctrine`** → **`get_doctrine_unit`** — канонический поиск и постраничное чтение доктрины; каждый результат `doctrine_only`, упомянутые нормы и дела проверяются отдельно;
- **`search_comments`** / **`search_all_legal_memory`** — совместимый полнотекстовый поиск по оставшимся комментариям и обзорам практики в RU-корпусе, без legacy-копий единой доктрины;
- **`search_positions`** — позиции ВС РФ (практика);
- **`search_official_labor_guidance`** → **`get_official_labor_guidance`** — поиск и чтение FAQ Роструда с `source_url`, provenance и маркировкой `administrative_guidance`; применимая норма проверяется отдельно;
- **`get_comment`** / **`get_document`** / **`get_legal_text`** — раскрыть найденную карточку / текст;
- **`get_document_relations`** / **`get_legal_graph_neighbors`** — граф связей.

**Локальные read-only слои:** `opinions` (`search_legal_opinions`), `telegram_reviewed` (`search_telegram_reviewed`), `labor_official` (`search_official_labor_guidance`) и курируемые MOC (`list_topic_maps`). Telegram по умолчанию выдаёт только `keep_commentary` / `keep_guideline`; review/delete статусы доступны лишь явным фильтром. Роструд всегда маркируется как официальное ненормативное разъяснение.

Историческая структура vault (отдельный MCP выведен; таблица сохраняет происхождение слоёв, а не текущую физическую маршрутизацию):

| Слой | Что внутри | Объём (на 2026-06-04) |
|---|---|---|
| `norms` | НПА, кодексы, ФЗ, постановления, ведомственные акты, ГОСТы, обзоры практики | ~120 |
| `comments` | Разъяснения, письма ведомств, готовые решения | ~8 (растёт) |
| `opinions` | Собственные заключения юриста (`source_approach_reviewed`) | ~16 |
| `telegram_reviewed` | **Проверенный** telegram/commentary слой (`keep_commentary` / `keep_guideline`) — рабочий Telegram-слой | растёт |
| `telegram_positions_strict` / `telegram_positions` | Очередь проверки (`needs_source_review`), auto-extracted — **не рабочий слой** | ~2675 |
| `telegram` | Сырой архив (`raw_archive`) — не использовать в ответах | — |

Тематические карты (актуальные на 2026-06-04, см. `list_topic_maps`):

- БАД, пищевая продукция, СГР и маркировка;
- Врачи, мероприятия, подарки и образцы;
- Договоры, закупки, РУ и госконтракты;
- ЕАЭС, техническое регулирование и таможенные правила;
- Конкуренция, ФАС и антимонопольные риски;
- Персональные данные и цифровые сервисы;
- Регистрация и обращение лекарственных средств;
- Реклама, продвижение и коммуникации.

**Когда обязательно использовать Приоритет 0:**

1. Поиск НПА по любому из перечисленных тематических разделов фарма-правового домена.
2. Поиск позиции по сложному фармацевтическому вопросу — `search_comments` / `search_positions`; дополнительный reviewed Telegram-контекст — `search_telegram_reviewed`.
3. Подготовка договора/претензии/ответа ФАС/Роспотребнадзору/Росздравнадзору — разъяснения через `search_comments`, собственные прошлые заключения — `search_legal_opinions`, контекст конкретного дела — `case-context.md`.
4. Любая правовая аргументация по фарма-домену — НПА и обзоры искать через `search_legal_kb` / `search_comments`, доктрину — через `search_doctrine`; норму затем проверять через `route_norm_verification(jurisdiction=..., probe=true)` и маршрут `usable_now: true`.

**Правила сосуществования с Приоритетом 1:**

- Найденная в локальной базе норма **всё равно проверяется** через `route_norm_verification(jurisdiction=..., probe=true)` и только маршрут `usable_now: true` перед цитированием — в карточках указана `act_date` и иногда `effective_date`, но редакция могла измениться после `last_checked`. Маркер `[ПРОВЕРИТЬ АКТУАЛЬНОСТЬ РЕДАКЦИИ]` обязателен, если `last_checked` старше 6 месяцев.
- Telegram `telegram_reviewed` доступен через `search_telegram_reviewed` / `get_telegram_reviewed`. По умолчанию использовать только `keep_commentary` / `keep_guideline`; `needs_source_review` и `delete_candidate` не считать подтверждённым материалом. Вес слоя — `references/legal-pharma-memory-usage.md`.
- Если в локальной базе ничего не найдено — продолжить по шагу 5 «Рабочего цикла», **без молчаливого пропуска**: в результате прямо отмечать «в локальных базах не найдено».

**Подробнее:** `references/legal-pharma-memory-usage.md` — детальный гайд по работе с базой, формат карточек, правила цитирования локальных источников, типовые поисковые запросы.

### 0b. Федеральное законодательство — local SQLite discovery + capability verification

Федеральные акты ищутся через единый namespace `legal-overlay`, но core tools первично читают `local-legal-ru-sqlite`. Snapshot фиксирует состояние на дату экспорта и сам не обновляется. Для правового основания всегда отделять discovery от verification:

- existence-check и snapshot — навигация, даже при `FOUND`;
- `route_norm_verification(jurisdiction="RU", probe=true)` выбирает доступный официальный портал или профессиональную правовую систему по подтверждённым capabilities;
- использовать только `usable_now: true`, раскрыть полный текст и проверить редакцию, статус, pinpoint и provenance; прямой маршрут pravo.gov.ru описан в `references/web-research-tools.md`, раздел 3.2;
- отсутствие пригодного маршрута — `[ПРОВЕРИТЬ НОРМУ]`; сомнение в редакции — `[ПРОВЕРИТЬ АКТУАЛЬНОСТЬ РЕДАКЦИИ]`;
- оформление ссылки — по `references/citation-rules.md`.

### 0c. Рекламная практика ФАС — provider-neutral FAS tools

- `search_fas_ad_practice(query, filters?, limit?, data_classification="public_or_abstracted")` — 2–4 абстрагированные поисковые гипотезы;
- `list_fas_filter_options()` — допустимые годы, регионы и статьи;
- `get_fas_case(case_id)` — раскрытие выбранной карточки.

Ответ обязан содержать `provider_used`, attempted/succeeded providers, fallback и warnings. `DEGRADED` означает использование transitional fallback, а не отсутствие результатов. Поисковый корпус имеет уровень `derived_official_corpus`: docId/excerpt служат навигацией, ключевые реквизиты и правовой тезис сверяются по официальному `fas_url`. Конфиденциальные факты, ПДн и текст материалов клиента во внешний запрос не передаются.

### 0d. Внешние профессиональные базы — локальные connectors

КонсультантПлюс, Glossa, единый и четыре legacy Casus connectors, ПравоТех и отключённый ГАРАНТ зарегистрированы внутри Overlay.
**КонсультантПлюс — основной внешний источник для поиска НПА и судебной практики** (после локального discovery, до Casus/ПравоТех и веб-агрегаторов). Использовать `consultant_search` с последующим раскрытием текста/карточки; после live-smoke 2026-10-09 это `live_professional` provider в пределах профиля. Поисковая категория не заменяет точный статус, историческая редакция не выбирается через текущий API, опубликование и реквизиты судебного акта сверяются официально. ГАРАНТ отключён и не вызывается. Как использовать и какие ограничения — `references/source-profiles/consultant-plus.md`.
Codex и Claude Desktop не получают отдельные provider-конфиги. До появления
локального credential источник имеет статус `auth_required` и tools не публикует.

- **Glossa** — доктрина: толкование и аргументы, затем обязательный якорь на норму и практику.
- **Casus** — единый connector с раздельными corpus и fail-closed `allowed_corpora`; snippet раскрывается до полного акта с тем же corpus.
- **ПравоТех** — платное второе мнение: прямой запрос юриста либо подтверждённая эскалация после неудовлетворительного собственного исследования. В него передаётся полный обезличенный юридический вопрос, не строка поиска. После MCP 502 вопрос и ответ наблюдались в кабинете, но надёжная доставка результата через MCP не подтверждена; `submitted_pending_account_check` означает неопределённый результат, требует ручной проверки кабинета и запрещает retry. Проверенный inventory не даёт raw-полного текста/редакции нормы и не пригоден для `norm_verification`; первый полный ответ показал mixed citation accuracy, поэтому каждый тезис и реквизит проверяется независимо.
- Конфиденциальные факты перед внешним запросом абстрагируются; provider, retrieval date и verification status сохраняются.

Полная маршрутизация, tool rules, квоты и порядок авторизации —
`references/external-legal-databases.md`.

**НЕ покрыты локально** (после локального discovery — КонсультантПлюс, затем Приоритет 1): подзаконные акты (постановления Правительства, ведомственные приказы), региональное законодательство, судебная практика вне локального слоя позиций. Официальные порталы: pravo.gov.ru для опубликования подзаконки, kad.arbitr.ru и сайт ВС РФ как первоисточник практики, сайты ведомств для приказов. Если профессионального маршрута нет, СудАкт используется как бесплатный резерв полного текста с пометкой агрегатора и последующей сверкой процессуального статуса при первой возможности.

### Что делать, если локальная база пустая

Локальный Overlay ничего не нашёл и тип источника локально не покрыт — идти по одной цепочке (КонсультантПлюс → Casus / ПравоТех по их правилам → официальные порталы), **прямо отметив** «в локальных базах не найдено / тип источника не покрыт локальными базами». Порядок по типу источника (механика выбора инструмента — `references/web-research-tools.md`, раздел 2 «Дерево выбора инструмента»; внешний поиск — `references/external-legal-databases.md`, «Правила КонсультантПлюс»):

1. **Федеральный акт (ФЗ/ФКЗ/кодекс/Конституция).** Независимо от результата локального поиска вызвать `route_norm_verification(jurisdiction="RU", probe=true)`. Использовать только `usable_now: true`, раскрыть полный текст и применить `requires`, `coverage` и `limitations` выбранного профиля. Для К+ точный статус и историческая редакция остаются за официальной сверкой. Для direct pravo-provider порядок — `references/pravo-gov-ru-search-protocol.md`; нет пригодного маршрута — `[ПРОВЕРИТЬ НОРМУ]`.
2. **Подзаконный / ведомственный / региональный акт** (типичный «не покрыт локально» случай). Порядок: КонсультантПлюс (`consultant_search` → раскрытие текста/карточки) → `pravo.gov.ru` / `publication.pravo.gov.ru` для официальной публикации, точного статуса и доступной исторической сверки. Поисковая карточка — навигационный лид; дата `edition`, производная из заголовка К+, сама по себе редакцию на целевую дату не подтверждает. Разделы 3.2/3.4 `references/web-research-tools.md`.
   **Официальную сверку делает агент, а не юрист.** `pravo_resolve_act(номер, дата)` → `pravo_get_document(nd)` работает для любого федерального акта с номером и датой, в том числе для указов Президента и постановлений Правительства (проверено 16.10.2026: Указ № 1203, ПП № 644, ПП № 167). Сайт kremlin.ru, сайты ведомств и WebFetch — только если pravo.gov.ru акт не нашёл. Перекладывать сверку на юриста маркером `[СВЕРИТЬ С ПЕРВОИСТОЧНИКОМ]` можно, только когда все маршруты с `usable_now: true` опробованы и текста не дали; в маркере перечислить, что пробовалось (например, «pravo.gov.ru — не найден по номеру и дате; К+ — не найден»). Один сбой одного инструмента (WebFetch не открыл страницу) не основание остановиться (BL-044).
3. **Судебная практика** (`legal-overlay.search_positions` вернул пусто). Дальше КонсультантПлюс (`consultant_search` → раскрытие результата), затем первоисточник на kad.arbitr.ru и сайте ВС РФ (vsrf.ru). Общий `WebSearch` и агрегаторы — навигационный лид. **Реквизиты акта показываются юристу только после открытия первоисточника** (п. 5 «Рабочего цикла» выше). Раздел 3.1 `references/web-research-tools.md`.
4. **Разъяснение госоргана** — официальный сайт органа; раздел 3.4 `references/web-research-tools.md`.

Во всех случаях: не выдумывать; не найдено — честно отметить и поставить маркер, а не достраивать по догадке.

## Workflow для правовых выводов

Этот алгоритм включается, когда задача = **анализ договора, подготовка позиции для суда, ответ госоргану, правовое заключение**. Отличается от типового рабочего цикла порядком: сначала понять как норму толкуют, потом сверить с текстом нормы.

### Настройка исследования: глубина и позиция

Перед шагами 1–4 задаются два параметра. Оба **определяет агент сам** (юрист может переопределить); выбранные значения агент называет одной строкой.

#### Глубина исследования (auto)

Глубина — **не ярлык, а конкретный объём работы**. Уровень выбирается по сигналам задачи, а не назначается «на глаз».

**Сигналы → уровень.** `quick` — вопрос закрывается нормой «в лоб»: регулирование устойчивое, нашлись аналогичные кейсы напрямую, цена ошибки невысока (обычно один простой вопрос). `standard` и `deep` — **одинаковая глубина проработки каждого issue**, отличаются только числом исследуемых вопросов: любой из факторов «серьёзной» задачи (высокая цена ошибки/ответственность, спор/банкротство, регуляторный/антимонопольный/уголовный компонент, новизна или противоречивость практики, конфликт норм, трансграничность, адресат — C-level/совет директоров/госорган) → как минимум `standard` (один ключевой issue); если серьёзных вопросов **несколько** (несколько issue, несколько квалификаций, разбивающихся на отдельные вопросы) → `deep`.

**Что конкретно меняется по уровням** (это и есть «реальная глубина»):

| Параметр | quick | standard | deep |
|---|---|---|---|
| Число issue в исследовании | обычно один, вопрос закрывается «в лоб» | ровно один ключевой issue | несколько issue |
| Правовые версии на issue (**потолок, не минимум**) | до ~2 версий | до ~6–8 версий | до ~6–8 версий на **каждый** issue |
| Потолок вызовов на issue (анти-круг) | ≤ ~8 tool-call | ≤ ~24–30 tool-call | ≤ ~24–30 на **каждый** issue |
| Слои источников | текст нормы + проверка практики по ключевой статье | норма + практика ВС + доктрина + обзоры + альтернативные квалификации + переходные положения + сверка редакций во времени | то же, что `standard`, по каждому issue |
| Adverse-проход | in-context, кратко | по ключевому issue отдельным проходом (в Claude Code — субагент) | по каждому issue отдельным проходом (субагент) |
| Сверка редакции | на текущую дату | во времени: дата отношений → спорное событие → сейчас | то же, по каждому issue |
| Верификация ссылок | self-check **всех** ссылок | полный claim-ledger + source-verifier | полный claim-ledger + source-verifier + consistency-checker (issue ≥2) |
| Объём аудит-следа | лёгкий research log + fact matrix | все матрицы полностью | все матрицы полностью |

**Правило выбора.** Оценить сигналы: закрывается «в лоб» и ставки невысоки → `quick`; один серьёзный вопрос → `standard`; несколько серьёзных вопросов → `deep`. `standard` и `deep` прорабатывают каждый issue **одинаково глубоко** (за основу — прежний объём `deep`); разница только в числе issue. Юрист может поднять или опустить уровень; выбрал ниже вопреки высокому риску — выполнить, зафиксировав ограничение. **Глубина ≠ число ссылок и ≠ число запросов** — потолки (правовые версии + вызовы, ниже) это верхняя граница, а не цель: основания найдены и проверены → остановиться, не добирая запросы до потолка. В `deep` дополнительно определить **режим сведения выводов** — **раздельный** (ответ по каждому вопросу самостоятелен) или **комплексный** (позиции по вопросам объединяются в единый вывод на общий вопрос); критерий и сигналы — `references/legal-opinion-method.md`, §3. Диспетчеризация субагентов Claude Code по уровням — `references/legal-opinion-subagents.md`.

**Ограничитель (обязателен — чтобы `deep` не крутился бесконечно). Два независимых стопа на issue, срабатывает который раньше.**

**Правовая версия** — отдельная правовая теория (какая норма / конструкция / квалификация управляет вопросом), отработанная проходом по стеку источников: доктрина (как толкуют) → практика (как применяют) → **official-текст нормы** (якорь) — по «Workflow для правовых выводов» ниже; какой источник на каком шаге и его authority level — каталог `references/source-profiles/`. Версия ≠ один запрос и ≠ переформулировка.

1. **Гейт по версиям (первичный, по насыщению).** Считаются *разные правовые версии*, не вызовы инструментов и не переформулировки. Стоп, когда вопрос закрыт: применимая норма найдена и **сверена по official-тексту**, ключевая практика проверена, adverse-версия отработана, новые запросы **дают только повторы** (критерий достаточности — `references/legal-opinion-method.md`, §4). Потолок версий на issue (**максимум**, не минимум): `quick` — до ~2, `standard`/`deep` — до ~6–8 (у `standard` issue один, у `deep` — несколько).
2. **Tool-call cap (вторичный, анти-круг).** Отдельный предел на число вызовов, чтобы бесплодная версия не уходила на круг переформулировок. На версию: первый запрос пустой/бедный (< 2–3 релевантных) → до 2–4 expansions из словаря (`references/query-cookbook.md`) → версия исчерпана. На issue (совокупный потолок ≈ версии × ~4): `quick` — до ~8 вызовов, `standard`/`deep` — до ~24–30.

Для судебной практики `established=True` из `tools/case_law/practice_status.py` означает насыщение однотипной поддержки, но не заменяет гейт по версиям. Перед передачей результата сверить coverage по `references/case-law-cards/CL-7-synthesis-and-coverage.md`: later history, применимый режим и issue, targeted adverse, конфликты и независимость линий. Прямая действующая позиция высшего суда при закрытом coverage не требует искусственного добора кассаций. Supporting-проход передаёт обязательный независимый adverse вызывающему workflow; ожидание source-verifier или human gate не запускает новый retrieval-круг.

Сработал любой стоп без результата → недостающее под gap-маркер (`[ПРОВЕРИТЬ НОРМУ]` / «в пределах проведённого исследования не обнаружено») и юристу, **не** достраивается догадкой и **не** уходит на новый круг (честный отказ — штатный исход). Повторные прогоны субагентов по одному предмету ограничены отдельно — не более 3 проходов (`references/legal-opinion-subagents.md`, «Потолок повторов»).

#### Позиция исследования: нейтральное vs под заявленную позицию (research_stance)

- **Нейтральное** (`neutral`, по умолчанию) — искомая позиция не задана: агент устанавливает применимое право и приходит к выводу.
- **Под заявленную позицию** (`position_led`) — юрист заранее назвал искомую позицию / квалификацию / основание, под которое нужно обоснование. Агент целенаправленно ищет и выстраивает **сильнейшее обоснование под неё**, но объективность обязательна и не снижается:
  - **adverse-проход обязателен независимо от глубины** — искать и то, что против позиции (в `quick` — хотя бы in-context; иначе субагент `adversarial-researcher`);
  - позиция **не держится** → честный вывод ведёт: прямо сказать, что основание слабое/не подтверждается, показать сильнейший контраргумент, дать откалиброванную оценку и, если есть, более прочную альтернативную квалификацию;
  - **запрещено**: выдумывать поддержку, замалчивать противоположную практику, подавать слабую позицию как надёжную («натягивать сову на глобус»);
  - расхождение по существу с заявленной позицией → `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]`; слабость основания отражается в калибровке уверенности, а не прячется за уверенным языком.

Применяется и в заключениях (`legal-opinion`), и в процессуальных документах (`procedural-document-drafter` — с предпросмотр-гейтом перед составлением).

### 1. Доктрина — постатейные комментарии и doctrine-карточки

Цель: понять, как устроена норма, каков её практический смысл, на что обращать внимание при толковании.

- **`legal-overlay.search_doctrine(query=...)` — первичный поиск доктрины.** Фильтры: `source_family`, `unit_type`, `article`; произведения перечисляет `list_doctrine_sources`.
- **`search_positions` — только для судебных/правовых позиций RU-корпуса.** По общей доктринальной теме это дополнение, а не замена `search_doctrine`.
- **Чтение найденного доктринального unit** — `get_doctrine_unit(unit_id, offset, limit)`. Текст читается постранично; provenance сохраняет произведение, страницы и текстовые offsets.
- Если вопрос связан с арендой или другой темой, для которой загружена доктрина, — искать через `search_doctrine`, раскрывать релевантный unit через `get_doctrine_unit`, затем отдельно проверять связанные нормы и судебные акты.
- Тип карточки `article_commentary_unit` — структура, доктрина, страницы источника, практическое правило.
- Тип карточки `legal_position` — рабочая позиция, извлечённая из комментария. Использовать как аргумент/подход, не как норму.
- Все результаты doctrine provider имеют `authority_class = doctrine_only`; они не подтверждают действующую редакцию нормы или содержание судебного акта.
- **Не представлять доктринальный тезис как обязательную судебную практику.** Это доктринальный/интерпретационный слой. Маркировать в ответе: «это доктринальный подход».

### 2. Судебная практика — обзоры практики + search_positions

Цель: понять, как суды подходят к ситуации.

- `legal-overlay.search_positions(topic|article|keyword|query)` — позиции ВС РФ из обзоров практики. Цитировать как практику с `case_number` + `decision_date_text` + `unit_heading`.
- `legal-overlay.search_comments(query=...)` — карточки обзоров практики (`court_practice_item`). Это **review/source-reference layer** (извлечения из обзоров судебной практики), не первичный текст судебного акта. Маркировать: «позиция найдена в слое обзоров практики; первичный акт требует проверки перед итоговым использованием».
- Если нашлось в обоих — использовать вместе: позиция ВС + комментарийная поддержка из обзоров практики усиливают друг друга.

### 3. Актуальный текст нормы — НПА

Цель: верификация. Доктрина и практика помогают толковать, но норма — финальный якорь.

- `legal-overlay.get_legal_text(document_id)` — snapshot-текст, навигация. В ответе **не должно быть `[INDEXED_STORAGE]`**. Правовое основание — полный текст с маршрута `usable_now: true`.
- Если `needs_review` или `last_checked` старше 6 месяцев — маркер `[ПРОВЕРИТЬ АКТУАЛЬНОСТЬ РЕДАКЦИИ]`.
- Если акта или его действующей редакции в локальном snapshot нет — `route_norm_verification(jurisdiction=..., probe=true)` и маршрут `usable_now: true`. Нет пригодного маршрута — `[ПРОВЕРИТЬ НОРМУ]`.

### 4. Аналогия

Если ситуация похожа на ту, которую покрывает норма или практика, но не идентична — вывод допустим, но обязательно явно помечается маркером `[ПРИМЕНЯЕТСЯ ПО АНАЛОГИИ: …]` по формуле из `references/citation-rules.md`.

Аналогия — не догадка. Обосновывать сходство признаков явно. Указывать отличие и риск того, что суд/орган может не принять аналогию.

### Иерархия уверенности в выводе

| Слой | Что даёт | Как маркировать |
|---|---|---|
| Раскрытый текст НПА от `usable_now: true` verification-provider | Что норма говорит | Без маркера только после проверки редакции, статуса, pinpoint и provenance |
| Позиции ВС РФ (search_positions) | Как суды применяют норму | «Позиция ВС РФ» + реквизиты |
| Обзоры практики (court_practice_item) | Как суды рассуждали | «По обзору судебной практики, YYYY, N X» + «требует проверки первичного акта» |
| FAS search (`derived_official_corpus`) | Навигация по решениям ФАС | Указать УФАС/дату/docId/provider status; ключевое проверить по официальному `fas_url` |
| Доктринальный комментарий (`source_approach_reviewed`) | Как норму толковать | «Доктринальный подход» |
| Telegram `telegram_reviewed` / opinions | Доступны через `search_telegram_reviewed` / `search_legal_opinions` | Внутренний и вторичный контекст, не источник права; открыть карточку, указать status/channel и проверить первоисточник; правила веса — `legal-pharma-memory-usage.md` |
| Telegram `needs_source_review` (`telegram_positions_strict`) | Очередь проверки, не рабочий слой | Не использовать без проверки первоисточника + предупреждение «источник не подтверждён» |

## Правила работы с источниками

1. Никогда не ссылаться на источник, который не проверен. При отсутствии возможности проверить — ставить маркер `[ПРОВЕРИТЬ ИСТОЧНИК]`.
2. Никогда не использовать формулировку «суды считают…», «практика складывается…» без конкретных судебных актов.
3. Цитата из судебного акта приводится только в кавычках и только если текст сверен с оригиналом. Иначе — пересказ без кавычек и пометка `[ПРОВЕРИТЬ ТОЧНОСТЬ ЦИТАТЫ]`.
4. Аналитическая статья не заменяет норму и не заменяет судебный акт.
5. Региональная практика отмечается явно — нельзя выдавать локальный подход за общефедеральный.
6. Устаревшие редакции норм и отменённые акты — отмечать явно.
7. Разъяснения нижестоящих ведомств — отмечать ведомство и дату; учитывать их меньший вес по сравнению с ВС РФ и КС РФ.

## Если применимой практики не найдено

Не выдумывать. Прямо указать: «применимой опубликованной практики не выявлено, требуется самостоятельная проверка юриста». Ставить `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]`.
