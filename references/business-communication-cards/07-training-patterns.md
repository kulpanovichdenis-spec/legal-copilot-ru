# BC-7 · Нарративные шаблоны обучения

Для TRAINING (карточка `references/business-communication-cards/04-training.md`) и вторичного компонента других режимов. Шаблон — структура storyline, а не визуальный шаблон.

## P1 · CURRENT → PROBLEM → BETTER → WHY
Как мы обычно делаем → в чём проблема → как лучше → почему это важно.
Для: договорные формулировки, маркетинговые материалы, переписка, ТЗ, закупки, согласования.
Блоки: `wrong_example` (side_by_side с `better_example`) → `business_consequence` → `checklist`.

## P2 · WHAT → WHY → HOW
Что проверяем → зачем → как. Для пошаговых операций.
Блоки: `checklist` / `process` (flow), в каждом шаге `why`.

## P3 · REAL DOCUMENT WALKTHROUGH
Реальный документ → выделенный фрагмент → что проверить → почему → следующий шаг.
Блоки: `internal_case` с `image` + `annotations` (`annotated_document`) → `checklist` → `escalation_rule`. Реальный документ приоритетнее иллюстрации; перед показом — обезличивание.

## P4 · CASE → RULE → ACTION
Что произошло → почему это нарушение или риск → какое правило → что делать у нас.
Для regulatory / compliance обучения. Блоки: `enforcement_case` → `legal_rule` (кратко на слайде, полностью в notes) → `required_action`.

## Референсные паттерны из материалов юриста (§32 ТЗ)

Сверены 2026-09-15 по четырём внутренним обучающим презентациям юриста (две по рекламе, две по договорной работе; оригиналы — в пользовательском профиле, не в репозитории). Ниже — только структура и приёмы, без фактов из материалов.

- **Договоры (подтверждено).** Фактическая структура: «главная мысль» в начале → разделы по темам → серия пар «как мы обычно делаем → в чём проблема → как может быть» (около десяти пар: предмет, сроки, характеристики, фиксация договорённостей, персональные данные, услуги или подряд) → блок ограничений (взаимодействие со специалистами здравоохранения) → «заключение — главная мысль» в конце.
  - Сохраняем: вывод и в начале, и в конце; пары «плохо / хорошо» (P1, `side_by_side`); подробный кейс «расхождение характеристик → последствие → как надо было»; мысль «описывать предмет профессиональным, а не юридическим языком»; выделение изменённой формулировки внутри «как может быть».
  - Исправляем при генерации: рубрики «как мы обычно делаем / как может быть / важно / проблема» не ставим в заголовок — заголовок = вывод пары, рубрики остаются подписями колонок; три финальных слайда «главная мысль» сводим в один `checklist` + `escalation_rule`; добавляем явную точку «когда обращаться в Legal» (в исходниках есть только контакт на закрывающем слайде).
- **Реклама (подтверждено).** Фактическая структура: статистика правоприменения → полномочие регулятора → кейс → квалификация → санкция → следующий кейс; нормы дословно на слайдах; реальные скриншоты материалов; вопрос-связка «при чём тут мы?»; закрывающий слайд с контактом.
  - Сохраняем: реальные скриншоты материалов (P3, `annotated_document`); вопрос-связку как мостик к блоку «что это значит для нас»; статистику как `business_context`.
  - Исправляем при генерации: первым идёт `key_message` «что это значит для нас»; нормы — в notes и приложение; рубрики-ярлыки («пример», «много букв» и т. п.) → заголовки-выводы; финал — `required_action` + `checklist`; санкция — `exposure` («потенциальная экспозиция до …»), не экономия.
- **Доверенность:** среди присланных материалов нет — паттерн «пришёл реальный документ → что смотрим → зачем → следующий источник → итоговый checklist → эскалация» (P3) остаётся по ТЗ.
- **Визуальный язык исходников:** преобладают декоративные и юмористические изображения — по методике (§11) допустимы, только если не вытесняют доказательство; в исходных заметках к слайдам только служебный текст шаблона, авторских notes нет.
