# Классы исполнения и маршрутизация моделей (единый слой правил)

Единый источник истины по вопросу «какой класс исполнителя берёт конкретный шаг работы»: код, дешёвая модель или дорогая reasoning-модель. Skills и агенты ссылаются сюда, не описывают правила у себя.

**Происхождение.** ТЗ юриста «Multi-agent / Multi-model архитектура». Главный принцип ТЗ: *frontier-модель должна тратить интеллект на решения, а не токены на механическую работу* — но и обратное верно: **дешёвая модель не допускается туда, где цена ошибки юридическая**.

**Область.** Claude Code и OpenAI Codex имеют проектные определения субагентов и
выбирают модель средствами своего раннера. Для остальных раннеров классы ниже
остаются методическим разделением и исполняются доступным им способом.

---

## 1. Три класса

| Класс | Кто исполняет | Когда |
|---|---|---|
| **A. Код** | Python в `tools/`, без LLM | Задача надёжно решается кодом: расчёт сроков, парсинг известной структуры, конвертация форматов, regex-извлечение, валидация схемы, сборка `.docx`, именование файлов, дедупликация |
| **B. Дешёвый воркер** | Субагент на лёгкой модели (`haiku`), строгий JSON на выходе | Ограниченная интеллектуальная операция с проверяемым результатом: классификация по фиксированному словарю, извлечение реквизитов, сегментация текста, tagging, приведение к схеме, парсинг выдачи поисковой базы |
| **C. Frontier-reasoner** | Основной агент или субагент на `opus` | Юридическая квалификация, синтез правила, оценка применимости практики, сопоставление конкурирующих позиций, критика, стратегический выбор, финальные формулировки, оценка существенности риска |

**Правило приоритета:** сначала пробовать A, затем B, и только потом C. **Но не наоборот**: понижать класс у шага, который уже отнесён к C, нельзя без явного решения юриста.

## 2. Когда класс C обязателен (не понижать)

Хотя бы одно условие — значит C:

- требуется юридическая квалификация или выбор между квалификациями;
- нужно связать несколько источников между собой;
- есть конфликтующие позиции/практика;
- оценивается применимость судебной позиции к нашим фактам;
- вывод существенно зависит от нюансов фактов;
- требуется критика позиции или стратегический выбор;
- ошибка имеет юридические последствия для доверителя;
- формируется окончательная формулировка, которая пойдёт юристу как черновик документа.

**Отдельно и жёстко:** маркеры неполноты (`[ПРОВЕРИТЬ НОРМУ]`, `[СВЕРИТЬ С ПЕРВОИСТОЧНИКОМ]` и др.), решение «источник подтверждает тезис / не подтверждает», перевод карточки практики в `VERIFIED_*` — **никогда не класс B**. Это суждение, а не извлечение.

## 3. Когда класс B уместен

Все условия сразу:

1. ответ имеет **заранее заданную схему** (JSON), которую можно проверить кодом;
2. задача локальна — один вход даёт одну классификацию/извлечение;
3. нет сложной правовой аргументации;
4. **ошибка будет обнаружена дальше по цепочке** — детерминированной проверкой (API, реестр, схема) или frontier-этапом.

Не выполняется хотя бы одно — брать C.

## 4. Протокол эскалации B → C

Дешёвый воркер обязан уметь сказать «не могу» вместо того, чтобы угадать. В схеме ответа — поле `escalate` со значениями:

| Статус | Значение |
|---|---|
| `UNCERTAIN` | низкая уверенность в классификации |
| `CONFLICT` | входные данные противоречивы |
| `INSUFFICIENT_CONTEXT` | переданного фрагмента не хватает |
| `REQUIRES_REASONING` | задача оказалась содержательнее, чем классификация |

Любое непустое значение → шаг автоматически повышается до класса C. **Обратная эскалация (C → B) без явного решения юриста запрещена.**

Правило вызывающего: `escalate` непустой ИЛИ схема не прошла валидацию ИЛИ `confidence` ниже порога → результат воркера **не используется**, шаг выполняется классом C.

## 5. Дисциплина входа для класса B

- Передавать **только необходимое**: инструкцию, релевантный фрагмент, схему, минимальный справочник (словарь типов). Не передавать весь контекст дела — это дороже и повышает шанс потери внимания.
- Не передавать материалы, которых воркеру не нужно видеть (конфиденциальные части, не относящиеся к задаче).
- Воркер **не пишет файлы** и не принимает решений о ходе работы — только возвращает структуру.

## 7. Класс-B воркер `intake-classifier` (спецификация — заложена заранее)

**Статус:** ✅ реализован для обоих основных раннеров:
`.claude/agents/intake-classifier.md` и `.codex/agents/intake-classifier.toml`.
Конкретная модель задаётся в этих runner-specific файлах; skills и watcher не
дублируют имя модели.

**Граница возможностей, которую нельзя обойти.** Субагент существует только
внутри сессии Claude Code или Codex — **фоновый Python-процесс не вызывает его**.
Поэтому `tools/watch/` доводит слой A до task-card в общей очереди, а SessionStart
hook лишь сообщает обезличенные счётчики. Класс B и последующие шаги выполняет
агент уже в сессии. Любой будущий класс-B шаг проектировать так же.

**Почему отдельная роль, а не переиспользование трёх существующих.** `source-verifier` / `adversarial-researcher` / `consistency-checker` — это класс C: проверяющие и оппонирующие роли на `opus`. Классификатор — класс B на лёгкой модели, противоположный режим. Смешивать нельзя. При этом воркер **один на все задачи класса B** (разные инструкции + разные схемы), а не по воркеру на задачу — иначе получится swarm, прямо запрещённый ТЗ.

```yaml
name: intake-classifier
description: Класс-B воркер. Классификация и извлечение по фиксированной схеме
  (входящий документ, метаданные судебного акта, выдача поисковой базы, тип клаузы).
  Возвращает строгий JSON, не делает правовых выводов, эскалирует при неопределённости.
tools: Read, Grep, Glob        # без Write/Edit, без MCP правовых баз
model: haiku
```

**Схема ответа (общая рамка, поля под задачу):**

```json
{
  "task": "document_intake | court_decision_meta | search_results | clause_type",
  "result": { },
  "confidence": 0.0,
  "escalate": null,
  "source_fragments": []
}
```

Для `document_intake` (п. 1 плана) `result` содержит: `doc_kind` (иск / отзыв / претензия / ходатайство / жалоба / определение / решение / запрос госоргана / предписание / акт КНМ / иное), `direction` (`incoming`/`outgoing`), `case_number` (или `null`), `parties` (как в тексте, без нормализации), `doc_date`, `addressee_authority`.

**Жёсткие запреты воркеру:**
- не делать правовых выводов и не оценивать перспективы;
- не выставлять маркеры неполноты (это класс C);
- не нормализовать реквизиты «по смыслу» — только как в тексте, сверка реквизитов остаётся за DaData/реестром (класс A);
- при любом сомнении — `escalate`, а не догадка.

**Как встраивается в авто-разбор папок (п. 1 плана):**

```
файл в workflow/_claims/                          ← единый канал приёма
   ↓ A  watcher: стабильность файла, ингестия (doc_ingest), regex-номера дел,
   │    подбор папки дела → карточка задачи в _claims/queue/, оригинал в processed/
   ─── граница процесса: дальше только в сессии Claude Code / Codex ───
   ↓ B  intake-classifier → JSON (тип, направление, номер дела, стороны, адресат-орган)
   ↓ A  валидация схемы; сверка номера дела с regex-результатом watcher'а
   ↓    escalate / невалидно / низкая уверенность → C: основной агент, затем unsorted/
   ↓ A  case bootstrap (case-context.md, matter-timeline.yaml), имя папки — safe_folder_name
   ↓ C  одна строка юристу: что за документ, в какое дело лёг, какой skill предлагается
```

Финальные решения (что это за документ юридически, что с ним делать) остаются за юристом — watcher только раскладывает.

## 8. Наблюдаемость

Точная стоимость на уровне отдельного субагента в этой среде **недоступна** (ограничение, не задача). Реалистичный минимум — считать в `tools/session_telemetry`: skill, роль, класс (A/B/C), факт эскалации B→C, успех/неуспех. Отдельный счётчик не заводить — расширять существующую телеметрию (пересечение с п. 13.8 roadmap: единый лог, не два).

## 9. Чего сознательно не делаем

- Не строим router на много уровней моделей — три класса, четвёртый (`MID`) только если логи покажут необходимость.
- Не заводим по воркеру на задачу — один класс-B воркер с разными инструкциями.
- Не раздаём классы всем skills (на 2026-09-22 их 36; аудит 2026-09-08 покрывал тогдашние 28) — класс A уже покрыт кодом, остальное по существу класс C.
- Не переводим в класс B ничего, где ошибка не ловится следующим этапом.
- Не меняем `.claude/agents/*` без конкретной задачи.
