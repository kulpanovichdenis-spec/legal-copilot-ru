# Clause Review — JSON Response Schema

Формальная схема ответа skill `clause-review` (см. `skills/clause-review/SKILL.md`).
Используется как контракт между LLM и Word Add-in backend (zod-валидация на backend, рендеринг в TaskPane).

## Принципы

1. **Возвращается строго JSON.** Никакого текста до или после, никакого markdown-кода в обёртке.
2. **Все поля обязательны**: если значения нет — указывается пустая строка `""` (для строк) или пустой массив `[]`.
3. **Enum-поля** (`clauseType`, `riskLevel`) — значения **строго из словаря**; никаких синонимов.
4. **Длина текстовых полей** — ориентиры в схеме; backend может валидировать жёстко.
5. **Никаких ссылок на нормы / практику** без проверки. При сомнении — `lawyerNote`.

## Описание полей

### `clauseType` (enum, обязательно)

Тип пункта по словарю. Значения см. в схеме выше или в `skills/clause-review/SKILL.md` («Словарь типов пунктов»).

Правила:
- если пункт сочетает несколько типов (например, «приёмка + сроки») — выбрать **доминирующий**;
- если ни один не подходит — `"иное"` + пояснение природы пункта в `issue`.

### `riskLevel` (enum, обязательно)

Уровень риска по `references/risk-scale.md` (раздел «Машиночитаемые значения»).

Правила:
- ставить **по худшему сценарию**, реально применимому;
- если для оценки нужен контекст — ставить **предварительный** уровень + `needMoreContext: true`;
- `"вопрос-бизнесу"` — только если решение **действительно** бизнес-вопрос, а не уклонение от ответа.

### `issue` (string, обязательно)

Одно-два предложения, **по существу**. Без воды, без эмоций.

✅ «Условие предусматривает одностороннюю ответственность нашей стороны и отсутствие cap на убытки контрагента».
❌ «Тут много чего не так, нужно править, в целом плохой пункт».

### `recommendation` (string, обязательно)

Одно-два предложения: **направление правки** или **конкретное действие**.

✅ «Предложить взаимную ответственность и cap на убытки в размере годовой стоимости контракта».
❌ «Подумать над переформулированием».

### `proposedWording` (string, может быть пусто)

Готовая редакция пункта. **Скопировал — вставил в Word.**

Правила:
- если в реестре есть одобренная клауза этого типа — открыть её из личного слоя профиля (`profile/knowledge/clauses/cards/<slug>.md`, навигатор `skills/clause-library/SKILL.md`) и использовать как базу (с адаптацией под стороны / нумерацию);
- если без соседних пунктов редакцию не сформулировать корректно — оставить пустым и поставить `needMoreContext: true`;
- маркеры (`[...]`) **не использовать** — это готовый текст для копирования.

### `counterpartyComment` (string, может быть пусто)

Формулировка для отправки контрагенту. Деловой и конструктивный тон.

Правила:
- начинать с фактической констатации, не с обвинения;
- предлагать решение, а не только указывать на проблему;
- избегать эмоциональных оценок;
- маркеры **не использовать**.

✅ «Предлагаем уточнить ответственность сторон, чтобы условие было взаимным и сбалансированным. Готовы обсудить cap на убытки на уровне годовой стоимости контракта».
❌ «Условие незаконное / абсурдное / несправедливое».

### `needMoreContext` (boolean, обязательно)

`true`, если для надёжной оценки или формулировки правки нужны соседние пункты.

Типичные ситуации:
- Пункт об ограничении ответственности → нужен пункт об убытках, расторжении;
- Пункт о форс-мажоре → нужен пункт о применимом праве (международные сделки);
- Пункт о подсудности → нужен пункт о применимом праве;
- Пункт об индексации цены → нужен пункт о цене и порядке оплаты.

### `contextNeeded` (array, обязательно)

Массив строк. Каждая строка — название нужного пункта или категория вводной.

✅ `["раздел об убытках", "раздел о расторжении", "приложение со спецификацией"]`
❌ `["больше контекста", "детали"]`

Если `needMoreContext: false` — `contextNeeded: []`.

### `lawyerNote` (string, может быть пусто)

Что юристу проверить или какое стратегическое решение принять.

Допустимы маркеры:
- `[ПРОВЕРИТЬ ФАКТ]`
- `[ПРОВЕРИТЬ НОРМУ]`
- `[ПРОВЕРИТЬ ИСТОЧНИК]`
- `[ПРОВЕРИТЬ СРОК]`
- `[ПРОВЕРИТЬ РЕКВИЗИТЫ]`
- `[ПРОВЕРИТЬ КОРПОРАТИВНЫЕ ОДОБРЕНИЯ]`
- `[ПРОВЕРИТЬ НАЛОГОВЫЕ ПОСЛЕДСТВИЯ]`
- `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]`

## Валидация на backend

В Word Add-in backend (Node.js / TypeScript) валидация через zod:

```typescript
import { z } from "zod";

export const ClauseTypeEnum = z.enum([
  "предмет", "цена", "сроки", "приёмка", "качество",
  "ответственность", "расторжение", "форс-мажор",
  "конфиденциальность", "интеллектуальная собственность",
  "персональные данные", "реклама и маркировка",
  "подсудность и применимое право", "уступка прав",
  "привлечение третьих лиц", "уведомления",
  "электронный документооборот", "антикоррупционные заверения",
  "санкции и экспортный контроль", "заверения и гарантии",
  "срок действия и автопролонгация", "иное"
]);

export const RiskLevelEnum = z.enum([
  "блокирующий", "высокий", "средний", "низкий", "вопрос-бизнесу"
]);

export const ClauseReviewResponseSchema = z.object({
  clauseType: ClauseTypeEnum,
  riskLevel: RiskLevelEnum,
  issue: z.string().min(1).max(500),
  recommendation: z.string().min(1).max(500),
  proposedWording: z.string().max(3000),
  counterpartyComment: z.string().max(1000),
  needMoreContext: z.boolean(),
  contextNeeded: z.array(z.string().min(1).max(200)).max(10),
  lawyerNote: z.string().max(1000),
});

export type ClauseReviewResponse = z.infer<typeof ClauseReviewResponseSchema>;
```

Если ответ LLM не проходит валидацию — backend возвращает ошибку `"Invalid response format from LLM"` с деталями zod-ошибки, UI показывает сообщение «попробуйте ещё раз / переформулируйте запрос».
