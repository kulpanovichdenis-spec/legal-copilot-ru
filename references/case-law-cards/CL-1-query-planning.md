# CL-1. Планирование запросов

Карта case-law-search. Вход, цикл и провайдеры — `references/case-law-search.md` (индекс). Подгружать только сработавшие карты, не весь набор.

**Принцип (§31.2–3).** Не одна строка запроса. По каждому самостоятельному issue — несколько независимых гипотез. Первый поиск короткий и широкий; сужать только под конкретный дефект выдачи, а не заранее.

**Перед запросами зафиксировать проверяемую рамку.** Для issue сформулировать узкий `proposition`: какой критерий или подход проверяется, при каком режиме права и какие находки его опровергнут либо ограничат. Это не предрешает вывод и не заменяет facts-first; рамка нужна, чтобы одинаковый исход по иному основанию не попал в ту же линию. Отдельно назвать роль прохода (`standalone` / `supporting` / `adverse`) и targeted opposition. Неизвестное оставить gap, а не достраивать.

**Два базовых типа запроса на issue:**
- **Query A — facts-first**: короткий запрос по ключевым фактическим обстоятельствам, без навязывания одной квалификации. Цель — найти дела с похожим фактическим паттерном и не потерять решения, где те же факты квалифицированы иначе (страховка от ошибочной первичной квалификации).
- **Query B — qualification-first**: через известную/предполагаемую квалификацию, конструкцию, норму, вид требования, способ защиты. Если практика ищется после доктрины и квалификация уже надёжна — сразу точная терминология. Facts-first при этом сохраняется.

**Альтернативные квалификации — отдельные гипотезы (§6.2).** Реалистичные альтернативы не склеивать в одну длинную строку: один factual pattern → Q1 facts-first, Q2 квалификация №1, Q3 квалификация №2. Каждая правовая версия — отдельный проход (это и есть «правовые версии» гейта из `references/source-hierarchy.md`, «Ограничитель»).

**Не перегружать запрос (§6.3).** Только признаки, необходимые для различения ситуации. Не добавлять полный нарратив, второстепенные даты, имена сторон, все возможные нормы и квалификации сразу.

**Развитие запроса после первой выдачи (§7).** Учиться терминологии у найденных актов: судебные формулировки, применённые нормы, названия требований/способов защиты, процитированные authorities и ключевые акты. Следующие запросы строить на этом. Сильный найденный акт — новый поисковый узел (его норма, позиция ВС/ВАС, на которую он ссылается, процитированные решения). **Query expansion — это лексические синонимы одной версии, а не свободная генерация перефразирований** (`references/query-cookbook.md`).

**Сужать только под наблюдаемый дефект (§7.3):** широкая выдача → +1 разграничивающий факт; не та конструкция → уточнить квалификацию; смешаны требования → уточнить claim/remedy; нет нужного уровня → ограничить инстанцию; нужен прогноз вертикали → уточнить округ/forum; плохое покрытие → сменить provider. Обязательной последовательности нет.

Следующее действие определяется конкретным пробелом coverage из CL-7. Кандидат-статус `established` прекращает добор однотипных подтверждений, но сам по себе не закрывает историю пересмотра, применимый режим или adverse. Сработавший cap/недоступность означает остановку с gap, а не новую волну перефразирований.

**Инструменты:** `legal_search(source_types=["case_law"])` → для точных полей локального слоя позиций `search_positions(topic|article|keyword|case_number|law)`; вне локального слоя — kad.arbitr.ru / сайт ВС (Приоритет 1, `references/source-hierarchy.md`). Антипаттерны — `references/case-law-search.md`, раздел «Чего не делать».
