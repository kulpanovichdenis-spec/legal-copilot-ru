# Генерация .docx — технические правила

## Назначение

**Это единое правило сборки любого .docx в проекте.** Оно применяется ко всем документам, которые собираются в .docx, — претензии, ходатайства, иски, отзывы, объяснения, ответы госорганам, письма, договоры, дополнительные соглашения, протоколы разногласий, двуязычные (EN/RU) договоры и т. д. Отдельных правил «под тип документа» нет: тип документа определяет *содержание и структуру* (это договорный/процессуальный playbook и образцы), а *как собрать из этого .docx* — всегда по этому файлу. Финальный документ готовится **сразу в .docx**, без промежуточной стадии в .md. Правила ниже — для среды Windows.

### Главный принцип: документ собирается, а не копируется из готового файла

`.docx` **собирается программно** из структуры документа и правил этого файла (python-docx), а не «переносится» из заранее заготовленного .docx-файла-болванки. Готовые примеры и структура берутся из образцов (`legal-document-samples` через MCP) и из договорного/процессуального playbook — это **источник структуры, формулировок и тактики**, но сам файл всегда собирается заново по этим правилам. Это касается и одноязычных, и двуязычных документов одинаково. Исключение — не «сборка с нуля», а **точечная правка уже согласованного .docx** (после правок юриста): см. раздел «Точечная правка существующего .docx».

## Инструмент по умолчанию

**python-docx** (пакет `docx` в Python). Установлен на рабочей машине. Использовать его как primary tool.

**Визуальный QA после сборки:** `python tools/docx_render/render_docx.py <input.docx> --output-dir <дело>/_llm/runs/<запуск>/qa/<версия> --emit-pdf`. На Windows проектный renderer использует Microsoft Word COM, на других платформах — `soffice`; PDF постранично преобразуется в PNG через `pypdfium2`. Исходный DOCX не изменяется, а существующие render-артефакты не перезаписываются.

**Fallback при недоступности python-docx**:

1. **Microsoft Word via COM** (PowerShell — `New-Object -ComObject Word.Application`). Надёжно при наличии установленного Word; медленнее python-docx.
2. **docx-js (npm)** — только если установлен Node.js. На рабочей машине не установлен; не использовать без явной установки.

**Не использовать**:

- LibreOffice headless для генерации с нуля — медленно, неконсистентный рендер;
- pandoc для генерации сложных документов — не поддерживает таблицы с заданной шириной столбцов, висячие отступы и сложное форматирование шапки.

## Алгоритм работы

1. Создать рабочий .py-скрипт через `Write` tool (не inline через Bash heredoc — multi-line строки в Bash на Windows ломаются).
2. Скрипт сохранять в scratchpad своей сессии (если раннер его даёт) или в `workflow/<дело>/_scripts/`; имя — `make_<имя>_<ГГГГММДД-ЧЧММСС>.py`. Не класть в общий `%TEMP%` с типовым именем: параллельные сессии над одноимённым документом запустят чужой скрипт и перезапишут чужой файл (прецедент 2026-10-14, BL-045).
3. Запустить по абсолютному пути: `python <абсолютный путь>.py`.
4. **Верифицировать результат** — извлечь текст сгенерированного .docx через распаковку XML и сверить параграфы, разделы, таблицы.

## Профили оформления: процессуальные, договорные документы и аналитическая заметка

Процессуальные документы (иски, заявления в суд, отзывы, ходатайства, жалобы, объяснения), претензии, ответы госорганам, договорные документы и аналитические заметки юристу **собираются через общий модуль** `tools/docx_style/profiles.py`, а не набором функций, скопированных в рабочий скрипт. Параметры — `references/document-formatting.md`, разделы 1–2 и 6–7. Процессуальный профиль — `ProceduralDoc`; вариант договорного оформления выбирается по таблице 6.0: «Стандарт» — `ContractDoc`, «Для физлиц» — `IndividualDoc`, «Рубрикатор» — `RubricDoc`; заметка — `NoteDoc`.

**Письмо на фирменном бланке** (письмо контрагенту, ответ госоргану, если у пользователя подключён фирменный стиль) собирается не профилем, а поверх бланка компании: `tools/brand_kit/letterhead.py` (`LetterheadDoc`). Когда бланк применяется и как заполнять слоты — `references/brand-letterhead.md`.

**Точечная правка процессуального документа** (раздел ниже) допустима только для файла, который уже собран в этом профиле. Если документ старого формата нужно существенно менять, его пересобирают через `ProceduralDoc` целиком: вставка абзацев с чужим кеглем и отступами даёт «лоскутный» документ (дефект 2026-10-13, заявления о включении в реестр).

Разметка текста во всех классах: `**полужирный**`, `^1` — надстрочный номер сноски; маркеры `[ПРОВЕРИТЬ …]` подсвечиваются автоматически.

```python
import sys; sys.path.insert(0, r"<корень legal-copilot>")
from tools.docx_style.profiles import ProceduralDoc, ContractDoc, IndividualDoc, RubricDoc, NoteDoc

# Процессуальный документ, претензия, ответ госоргану
p = ProceduralDoc()
p.head(["**В Арбитражный суд …**", "адрес суда"],      # блоки шапки справа, кегль = тексту
       ["**Истец:** ООО «…»", "ИНН …, ОГРН …", "Адрес: …"],
       ["**Цена иска:** … руб.", "**Государственная пошлина:** … руб."])
p.title("ИСКОВОЕ ЗАЯВЛЕНИЕ", "о взыскании …")
p.section("I. ОБСТОЯТЕЛЬСТВА ДЕЛА")
p.point("1.", "Факт с привязкой к доказательству.")  # висячий отступ 0,8 см
p.section("II. ПРАВОВОЕ ОБОСНОВАНИЕ")
p.section("2.1. Основание требования")
p.para("Норма и её применение к фактам.")
p.table(["Показатель", "Сумма, руб."], rows, [11.5, 5.0])  # сумма = 16,5 см
p.para("На основании изложенного, руководствуясь …,")
p.prayer()                                          # «ПРОШУ:»
p.point("1.", "Взыскать …")
p.section("Приложения:")
p.point("1.", "Договор № … от …, на 3 л.")
p.signature(["Генеральный директор ООО «…»", "________________ / И. О. Фамилия"])
p.footer()                                          # номер страницы
p.save(r"…\workflow\…\Исковое заявление.docx")

# «Стандарт» — договоры, ДС, спецификации, NDA
d = ContractDoc()                                   # compact=True — уместить короткое ДС на 1 стр.
d.header("Договор поставки № … от …")               # верхний колонтитул на каждой странице
d.title("Договор поставки № …")                     # подзаголовок ДС — вторым аргументом
d.place_date("г. Москва", "«__» ________ 2026 г.")
d.preamble("…, именуемое в дальнейшем **«Поставщик»**, …")
d.section("1.", "Предмет и модель работы")          # section("", …) — раздел без номера
d.clause("1.1.", "Текст пункта.")                  # номер мелко в колонке, текст на общей вертикали
d.bullet("подпункт перечня;")
d.clause("1.", "Изложить пункт 2.6 Договора в следующей редакции:", keep_next=True)
d.quoted(["«2.6. Абзац 1.", "Абзац 2.»"])           # новая редакция в ДС
d.table(["Документ", "Кто", "Срок"], rows, [7.0, 4.0, 4.7])   # сумма = ширине колонки текста (15,7 см)
d.signatures([{"role": "Поставщик", "name": "…", "details": ["ИНН … / КПП …"], "signatory": "…"}, {...}])
d.footer(["Поставщик", "Покупатель"])              # визирование + «X | Y»
d.save(r"…\workflow\…\Договор.docx")

# «Для физлиц» — трудовые, ГПХ, потребительские
iv = IndividualDoc()
iv.head("Трудовой договор № …", "г. …", "дата", [("caption", "Работодатель"), ("value", "…")],
        [("caption", "Работник"), ("value", "…")])
iv.cards([([("caption", "Должность^1"), ("key", "…")], [("caption", "Заработная плата"), ("key", "…")])])
iv.box([("caption", "Приложения"), ("bullet", "…")])
iv.notes([(1, "Трудовая функция определяется в Приложении № 1.")])
iv.section("", "Начало работы"); iv.clause("1.", "…")   # далее — как «Стандарт»
# у физлица в signatures: {"role": "Работник", ..., "stamp": False}

# «Рубрикатор» — оферты и term sheet
rb = RubricDoc()
rb.title("Оферта на заключение договора оказания услуг", "далее — Оферта")
rb.lead("Дата публикации: …")
rb.rubric("Предмет", ["Пункт 1.", "Пункт 2.", ("bullet", "элемент перечня;")])   # сквозная нумерация
rb.rubric("Стоимость", [("text", "…")], numbered=False)                          # строка term sheet
```

`python tools/docx_style/profiles.py selftest` — самопроверка (нет автонумерации, у всех run есть `eastAsia`, стили без тематических шрифтов и линий, повтор заголовка таблицы, колонтитулы, подсветка маркеров, «Стандарт» по ширине и название на вертикали текста, «Для физлиц» по левому краю, сквозная нумерация рубрикатора, нет «М. П.» у физлица, поля); `… demo <папка>` — макеты всех вариантов без фактуры для визуальной сверки. Если стиль меняется — меняются вместе `document-formatting.md` (6–7) и модуль, затем `selftest` и рендер демо.

Двуязычные документы — `BilingualDoc` (`document-formatting.md` 6.5; пример — в разделе «Двуязычные (двухколоночные) документы» ниже). Сохранность текста при переоформлении готового документа — `python tools/docx_style/textcheck.py <исходник> <результат>`.

Процессуальные документы пока собираются по функциям ниже (процессуальный профиль, `document-formatting.md` раздел 1).

## Шаблон скрипта (python-docx)

### Базовые настройки страницы и шрифта

```python
from docx import Document
from docx.shared import Pt, Cm, RGBColor

from docx.oxml.ns import qn

doc = Document()

# Page setup
section = doc.sections[0]
# A4 — для европейских адресатов
section.page_width = Cm(21.0)
section.page_height = Cm(29.7)
# US Letter — для американских:
# section.page_width = Cm(21.59)
# section.page_height = Cm(27.94)
section.left_margin = Cm(2.5)
section.right_margin = Cm(2.0)
section.top_margin = Cm(2.0)
section.bottom_margin = Cm(2.0)
```

### Шрифт + кириллица (eastAsia)

**Критическое правило** для документов с кириллическим вкраплением (русские названия, имена сторон): задавать атрибут `eastAsia` в rFonts. Иначе кириллица может рендериться шрифтом по умолчанию (Calibri) даже при установке основного шрифта Times New Roman.

```python
FONT = "Times New Roman"

style = doc.styles["Normal"]
style.font.name = FONT
style.font.size = Pt(11)

rPr = style.element.get_or_add_rPr()
rFonts = rPr.find(qn("w:rFonts"))
if rFonts is None:
    rFonts = OxmlElement("w:rFonts")
    rPr.append(rFonts)
rFonts.set(qn("w:ascii"), FONT)
rFonts.set(qn("w:hAnsi"), FONT)
rFonts.set(qn("w:cs"), FONT)
rFonts.set(qn("w:eastAsia"), FONT)  # ← критично для кириллицы
```

Аналогичную установку нужно делать для каждого Run, который содержит кириллицу. Helper:

```python
def set_run(run, *, bold=False, italic=False, size=Pt(11), font=FONT):
    run.font.name = font
    run.font.size = size
    run.bold = bold
    run.italic = italic
    rPr = run._element.get_or_add_rPr()
    rFonts = rPr.find(qn("w:rFonts"))
    if rFonts is None:
        rFonts = OxmlElement("w:rFonts")
        rPr.append(rFonts)
    rFonts.set(qn("w:ascii"), font)
    rFonts.set(qn("w:hAnsi"), font)
    rFonts.set(qn("w:cs"), font)
    rFonts.set(qn("w:eastAsia"), font)
```

### Нумерованные параграфы в legal style (висячий отступ)

Для русскоязычных процессуальных документов, претензий и ответов госорганам это делает `ProceduralDoc.point()` (раздел «Профили оформления» выше); фрагмент ниже остаётся техникой для документов вне профиля (Letter of Claim и иные англоязычные письма) — где параграфы 1, 2, 3 … выровнены к левому краю текста с висячим отступом первой строки. **Не использовать** автонумерацию Word (она ломается при правках пользователя): нумерация — литералом + табуляция.

```python
def add_numbered(doc, num, text):
    p = doc.add_paragraph()
    pf = p.paragraph_format
    pf.space_before = Pt(0)
    pf.space_after = Pt(6)
    pf.line_spacing = 1.15
    pf.left_indent = Cm(1.0)
    pf.first_line_indent = Cm(-1.0)
    p.alignment = WD_ALIGN_PARAGRAPH.JUSTIFY

    r_num = p.add_run(f"{num}.\t")
    set_run(r_num)
    r_txt = p.add_run(text)
    set_run(r_txt)
    return p
```

### Подпункты (a), (b), (c)

```python
def add_sub(doc, label, text, *, level=1):
    p = doc.add_paragraph()
    pf = p.paragraph_format
    pf.space_before = Pt(0)
    pf.space_after = Pt(4)
    pf.line_spacing = 1.15
    pf.left_indent = Cm(2.0 if level == 1 else 3.0)
    pf.first_line_indent = Cm(-1.0)
    p.alignment = WD_ALIGN_PARAGRAPH.JUSTIFY

    r_label = p.add_run(f"{label}\t")
    set_run(r_label)
    r_txt = p.add_run(text)
    set_run(r_txt)
```

### Поля с прочерками

```python
def add_field_line(doc, label, value="____", *, indent_cm=2.0):
    p = doc.add_paragraph()
    pf = p.paragraph_format
    pf.space_before = Pt(0)
    pf.space_after = Pt(2)
    pf.line_spacing = 1.15
    pf.left_indent = Cm(indent_cm)
    r1 = p.add_run(f"{label}")
    set_run(r1)
    r2 = p.add_run(value)
    set_run(r2)
```

### Таблицы (например, расчёт суммы)

Задавать ширину столбцов **дважды**: на уровне таблицы (через установку cell.width в цикле) и контролировать суммой. Без этого Word рендерит таблицы криво.

```python
table = doc.add_table(rows=4, cols=2)
table.alignment = WD_TABLE_ALIGNMENT.CENTER
table.autofit = False
col_widths = [Cm(8.0), Cm(5.0)]
for i, w in enumerate(col_widths):
    for cell in table.columns[i].cells:
        cell.width = w

rows_data = [
    ("Transportation expenses:", "____ USD"),
    ("Destruction expenses:",    "____ USD"),
    ("Customs payments:",        "____ USD"),
    ("Total:",                   "____ USD"),
]
for i, (lab, val) in enumerate(rows_data):
    row = table.rows[i]
    c1, c2 = row.cells
    p1 = c1.paragraphs[0]
    r = p1.add_run(lab)
    set_run(r, bold=(i == len(rows_data) - 1))
    p2 = c2.paragraphs[0]
    p2.alignment = WD_ALIGN_PARAGRAPH.RIGHT
    r = p2.add_run(val)
    set_run(r, bold=(i == len(rows_data) - 1))
```

## Двуязычные (двухколоночные) документы

Применяется к любому документу, который ведётся на двух языках синхронно (типично EN | RU): двуязычные договоры, приложения, письма иностранному контрагенту. Язык-приоритет (какая версия имеет преимущественную силу при расхождении) фиксируется в самом документе; техника сборки от типа сделки не зависит.

**Раскладка и оформление** — `references/document-formatting.md` раздел 6.5 (параметры, выравнивание по номерам пунктов, заголовки парой, сетка сторон, сноски по языкам); сборка — `BilingualDoc` из `tools/docx_style/profiles.py`:

```python
from tools.docx_style.profiles import BilingualDoc
bi = BilingualDoc()
bi.header("Supply Contract No. … / Контракт на поставку № …")
bi.title("Supply Contract No. … / Контракт на поставку № …", "Date / Дата: …")
bi.parties(["Buyer / Покупатель: …", "Address / Адрес: …"], ["Supplier / Поставщик: …", "…"])
bi.section("3. Delivery terms", "3. Условия поставки")
bi.block(en_paragraphs, ru_paragraphs)        # выравнивание по «3.1.»; ("текст", True) — элемент перечня
bi.pair("…EN…", "…RU…")                         # одна строка вручную
bi.data_table(["No.", "Description / Описание", …], rows, widths)   # на всю ширину (17,0 см)
bi.signatures(["On behalf of the Buyer / …", "…"], ["On behalf of the Supplier / …", "…"])
bi.footer()
```

Шрифт Times New Roman с обязательным `eastAsia` (иначе кириллица в правой колонке съедет на Calibri) модуль ставит сам.

**Переоформление готового двуязычного документа** («оформи договор по правилам»): текст не меняется. Структуру берут из исходника: абзацы каждой ячейки, признак элемента списка (`w:numPr`), объединённые ячейки учитываются один раз (сравнивать `cell._tc` через `is`, не `id()`). После сборки — `python tools/docx_style/textcheck.py <исходник.docx> <результат.docx>`: потеряно и добавлено — 0. Замеченные при чтении расхождения языковых версий и ошибки в ссылках — юристу списком, не правкой.

**Синхронность — главное правило.** Любая правка вносится **в обе колонки одновременно**. Самая частая ошибка — поправить только русскую колонку; если приоритет у английской версии, несинхронизированная правка юридически не работает. После правки — diff по изменённым строкам обеих колонок.

**Поиск нужного пункта — по началу текста, а не по номеру.** Подстрока с номером (`«9.3.»`) встречается и внутри других пунктов («в соответствии с пунктом 9.3.»). Искать ячейку/строку по **началу текста пункта**, иначе правка уйдёт не туда. После любой правки — верификация обратным извлечением текста (проверить: нет дублей строк, не осталось старых формулировок).

**Незаполненные данные — маркеры, не догадки.** Реквизиты сторон, суммы, сроки, характеристики предмета берутся только из документов сделки/первоисточника; чего нет — маркер (`[ПРОВЕРИТЬ РЕКВИЗИТЫ]` / `[ПРОВЕРИТЬ СРОК]` / `[ПРОВЕРИТЬ ХАРАКТЕРИСТИКИ]`), а не правдоподобная подстановка. Структуру, перечень условий и тактику конкретного типа договора — из договорного playbook и образцов `legal-document-samples`.

## Точечная правка существующего .docx (после правок юриста)

Единственный случай, когда .docx **не пересобирается с нуля**: файл уже согласован/поправлен юристом, и нужно внести адресное изменение, не потеряв его правки.

- **Не перегенерировать файл целиком** — только точечная правка существующего .docx (замена текста конкретной ячейки/параграфа, вставка/удаление строк).
- **Перед правкой** — извлечь текст (XML-метод из раздела «Проверка результата») и сделать diff, чтобы видеть текущее состояние и не затереть правки юриста.
- **Искать место правки по началу текста** пункта/абзаца (не по номеру — см. ловушку выше).
- **После правки** — снова извлечь текст и сверить: изменение внесено, дублей строк нет, старые формулировки не остались; для двуязычных — обе колонки синхронны.

## Редлайн (режим исправлений) по файлу юриста или контрагента

Когда юрист просит «правки в редлайн» или файл уже содержит чужие исправления (бизнес, контрагент), правки вносятся **режимом исправлений Word**, а не пересборкой.

- **Свой документ после правок юриста** (новая версия ДС, договора): собрать чистую новую версию из файла юриста (python-docx, абзацы переносить как XML-элементы — форматирование юриста сохраняется), затем сравнить `tools/docx_redline/compare.ps1` (исходник = файл юриста, результат — `… rev N (редлайн).docx`). Автор — по указанию юриста, иначе «Claude (legal-copilot)».
- **Чужая форма «использовать как есть»** (приложение контрагента, форма бизнеса): не пересобирать и не принимать чужие исправления. Правка — `tools/docx_redline/apply_ops.ps1` по JSON-списку операций (замена, удаление, вставка, замена хвоста или всего абзаца, удаление абзаца, комментарий): копия исходника, режим исправлений, сверка каждого места до первой правки. Номера абзацев — тем же скриптом с `-List`. Скрипт под задачу заново не писать; формат `ops.json` — `tools/docx_redline/README.md`. Где данные должен заполнить контрагент или бизнес, ставится комментарий, а не выдуманная конкретика. Комментарий крепится точечно к фразе, о которой он (поле `cat`), а не к целому абзацу, разделу или большой вставке; удаление и переписывание без нужды не комментировать (замечание юриста 26.10.2026). Автор — «от имени юриста» (`Application.UserName`); другое имя — `-Author`, прежнее имя пользователя Word скрипт возвращает сам.
- PowerShell 5.1 читает `.ps1` с кириллицей только в UTF-8 **с BOM**.
- Проверка: `tools/docx_redline/verify.ps1` — авторы и число `w:ins`/`w:del`/`w:moveFrom`/комментариев в XML; итоговый текст (все исправления приняты во временной копии) с номерами списков. PDF для просмотра — отдельным запуском `tools/docx_render/render_docx.py`, не в том же процессе Word.

## Запуск и кодировки

### Windows console и Cyrillic в путях

При запуске через Bash на Windows вывод `print(path)` с кириллическими символами может рендериться искажённо (CP866 / CP1251 fallback вместо UTF-8). **Это не влияет** на сам файл — только на отображение в консоли.

Если требуется чистый вывод пути:

```bash
PYTHONIOENCODING=utf-8 python script.py
```

Или в самом скрипте перед print:

```python
import sys
sys.stdout.reconfigure(encoding='utf-8')
```

## Колонтитулы и равномерная пагинация

Для объёмных процессуальных документов (отзывы, возражения, иски с большим числом разделов):

### Колонтитулы

- Верхний колонтитул: краткое название документа и дата («Отзыв на исковое заявление от ДД.ММ.ГГ»), курсив, 9–10 пт, по левому краю; допустима тонкая линия под колонтитулом.
- Номер страницы — по центру нижнего колонтитула.
- На первой странице верхний колонтитул отсутствует (в python-docx: `section.different_first_page_header_footer = True`), номер страницы сохраняется.

### Равномерная пагинация

- **Не начинать каждый раздел с новой страницы** автоматически. Принудительный разрыв — только для действительно отдельного крупного блока или по прямому требованию юриста.
- `keep_with_next` применять к заголовку и короткому вводному абзацу, но **не** к длинным абзацам, таблицам и изображениям — иначе появляются крупные пустоты.
- Не оставлять на промежуточной странице непреднамеренную пустоту больше ~четверти полезной высоты. Если вставка или таблица уходит на следующую страницу и оставляет пустоту — уменьшить её высоту, сократить интервалы либо перенести часть вводного текста.
- При разрыве таблицы между страницами — повторять строку заголовка (`row.repeat_header = True` / `tblHeader`).
- Длинный список приложений допустимо верстать в две сбалансированные колонки; не создавать отдельную страницу только ради подписи.
- Если есть оглавление — после финального рендера сверять номера страниц вручную (автополя TOC при генерации через python-docx не пересчитываются без открытия в Word).

## Вставки фрагментов документов (изображения из PDF-доказательств)

Фрагмент документа вставляется картинкой, только когда важна **визуальная форма** доказательства: подпись, отметка, штамп, таблица, схема, реквизиты, взаимное расположение текста, контекст переписки. Если визуальная форма несущественна — предпочитать точную цитату курсивом (дешевле и надёжнее).

Правила:

- обрезать фрагмент тесно, до доказательственного содержания, но сохранять дату, заголовок или соседнюю строку, позволяющую идентифицировать источник;
- не вырывать фразу из контекста документа;
- размещать сразу после вводящего абзаца, который называет источник (документ, дата, приложение) и объясняет, что именно видно во вставке; после вставки — обязательно продолжить анализ;
- короткий фрагмент письма / таблицы / оговорки — почти на всю ширину текста; схему или фотографию — по центру на 55–70 % ширины;
- проверять читаемость при масштабе 100 %, не искажать пропорции;
- не добавлять декоративные рамки, тени и подписи, которых нет в стиле документа.

### Проверка результата

После генерации **извлекать текст** обратно через ту же XML-схему и сверять параграфы:

```powershell
$src = "путь.docx"
$tmp = "$env:TEMP\docx_verify"
if (Test-Path $tmp) { Remove-Item $tmp -Recurse -Force }
New-Item -ItemType Directory -Path $tmp | Out-Null
Add-Type -AssemblyName System.IO.Compression.FileSystem
[System.IO.Compression.ZipFile]::ExtractToDirectory($src, $tmp)
[xml]$x = Get-Content "$tmp\word\document.xml" -Encoding UTF8
$ns = New-Object System.Xml.XmlNamespaceManager($x.NameTable)
$ns.AddNamespace("w","http://schemas.openxmlformats.org/wordprocessingml/2006/main")
$paras = $x.SelectNodes("//w:p", $ns)
foreach ($p in $paras) {
  $texts = $p.SelectNodes(".//w:t", $ns)
  $line = ""
  foreach ($t in $texts) { $line += $t.InnerText }
  $line
}
```

Этим же методом сравнивают «исходный draft» vs «правка пользователя» — для извлечения уроков.

### Три прохода финальной проверки

Перед выдачей документа юристу — три последовательных прохода:

1. **Содержательный**: вид документа выбран верно; позиция оппонента передана точно; каждое фактическое утверждение имеет источник; цитаты сверены; выводы логически следуют; пробелы обозначены маркерами.
2. **Процессуальный и редакционный**: термины единообразны (словарь материалов дела); нумерация разделов и перекрёстные ссылки верны; имена, роли, номера, суммы, даты совпадают с материалами; просительная часть соответствует процессуальной роли; ссылки на нормы прошли existence-check.
3. **Структурный и версточный**: XML-извлечение текста (см. выше) + **визуальная постраничная проверка рендера** через `tools/docx_render/render_docx.py`. Просмотреть каждую PNG-страницу: нет обрезки текста, наложений, «одиноких» заголовков внизу страницы, нечитаемых вставок, случайной смены шрифта и крупных непреднамеренных пустот. Если оба backend-а (Word COM и LibreOffice) недоступны — явно сообщить юристу, что визуальная проверка не выполнялась и нужен просмотр в Word.

## Что не работать (известные сбои)

1. **Inline Python через Bash heredoc на Windows** — много кавычек ломаются. Скрипт сохранять через `Write` tool.
2. **Word.Application COM из service/background-сеанса** — Word может требовать интерактивного пользователя. Проектный renderer проверен в обычном Windows-сеансе и при ошибке пытается использовать LibreOffice; для сервиса нужен установленный headless LibreOffice.
3. **`from docx.shared import RGBColor` без использования** — безвредно, но в проекте старые версии могут не иметь его. Если не нужен — не импортировать.
4. **`section.page_width` / `section.page_height`** — должны быть установлены **до** добавления содержимого. После — игнорируется.
5. **rFonts без eastAsia** — кириллица в Times New Roman может рендериться Calibri (Word fallback). Всегда задавать `eastAsia`.
6. **Автонумерация Word (numbering.xml)** — ломается при правках пользователя; параграфы перенумеровываются непредсказуемо. Литералом + табуляция — надёжнее.
7. **WD_TABLE_ALIGNMENT vs WD_ROW_ALIGNMENT** — не путать; для таблицы — table.alignment, не row.alignment.
8. **Встроенные стили шаблона python-docx** (`Title`, `Heading 1/2`) — по умолчанию тематический шрифт (Calibri Light), синий цвет и у `Title` синяя линия снизу. Установки `font.name` недостаточно: нужно убрать атрибуты `w:asciiTheme`/`w:hAnsiTheme`/`w:eastAsiaTheme`/`w:cstheme`, задать чёрный цвет и удалить `w:pBdr` (так делает `tools/docx_style/profiles.py`).
9. **Заливка ячейки без `w:val="clear"`** — Word может отрисовать узор вместо ровного тона; `w:shd` всегда с `w:val="clear"` и `w:fill`.
10. **Таблица уходит за правое поле** — `cell.width` и `table.autofit = False` недостаточно: Word берёт ширины из `w:tblGrid`. Нужны `w:tblLayout w:type="fixed"`, `w:tblW` и ширины колонок сетки (`table.columns[i].width`); в модуле — `_fix_widths(table, widths_cm)`, применяется ко всем таблицам.
11. **Объединённые ячейки при чтении исходника** — `row.cells` возвращает объединённую ячейку несколько раз, а `id()` proxy-объектов python-docx переиспользуется: дедуплицировать по `cell._tc` через `is`, иначе часть текста потеряется при переоформлении или сверке.

## Алгоритм работы по задаче «Подготовить документ X в .docx»

1. **Анализ** (контекст, договор, фактическая база, нормы) → выясняем что готовим.
2. **Уточнения у пользователя** (формат, тон, тактика, объём раскрытия, требования).
3. **Сопроводительная записка для юриста** (`.docx` в той же папке): применимые нормы / клаузы, маркеры, риски, контр-риски, стратегические комментарии — **только аналитика, не сам текст документа**. Записка адресована человеку (юристу), поэтому по общему правилу CLAUDE.md «Формат результата» отдаётся в `.docx`; `.md`-копию сохранять в служебной папке дела лишь как техническую (рабочий материал агента), не как итоговый файл записки.
4. **Генерация .docx** через python-docx (по правилам выше) — и самого документа, и сопроводительной записки.
5. **Верификация** через XML extraction и визуальный рендер всех страниц в PNG.
5а. **Пресейв-гейт** (CLAUDE.md «Финальная валидация перед сохранением»): existence-check ссылок на ФЗ/кодексы + **чистка от AI-slop** по `references/anti-slop.md` (машинно — `python tools/slop_check/check.py <файл>`). Калибровка: не трогать правовые связки, формулы цитирования и намеренный регистр.
6. **Сообщение пользователю** — путь к .docx + что внутри + куда смотреть в записке для сверки + строка об итогах slop-чека.

Шаг 3 (записка) — **не дублирует** сам документ. Записка — про *почему* сделано так; основной .docx — про *что* отправляется адресату.
