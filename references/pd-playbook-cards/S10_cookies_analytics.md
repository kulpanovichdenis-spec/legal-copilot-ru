**Назначение:** квалифицировать фактические потоки данных без механического переноса GDPR/ePrivacy на российское право.

## 1. Business triggers

- web analytics
- advertising pixels
- session replay
- mobile SDK
- cookies/local storage
- device fingerprinting

## 2. Processing activities

- установка/чтение идентификатора
- сбор событий
- построение профиля
- передача analytics/ad provider
- таргетинг

## 3. Subjects / data

**Субъекты**
- посетитель сайта/пользователь приложения

**Типичные данные**
- cookie/device identifiers
- IP
- browser/device properties
- events/pages/actions
- profile/segments

## 4. Purpose model

- необходимая техническая функция
- безопасность
- аналитика
- персонализация
- реклама/таргетинг

**Правило:** одна техническая система или один бизнес-процесс могут включать несколько самостоятельных целей. Каждая цель получает собственные `legal basis / dataset / recipients / retention`.

## 6. Decision tree

1. Провести фактический scan/inventory технологий и получателей.
2. Для каждой технологии определить данные, возможность связать их с лицом и цель.
3. Отделить essential/security от analytics/advertising.
4. Определить основание в российском праве; не объявлять cookie-banner обязательным лишь по аналогии с GDPR.
5. Для внешнего провайдера применить S16; для зарубежного потока — S22/S23.
6. Отдельно проверить direct marketing/profiling через S11/S12.

## 7. MUST controls

- документировать реальные инструменты, а не только заявленные в policy
- исключить лишние/забытые pixels
- обеспечить соответствие публичной информации фактическому стеку
- проверить трансграничные потоки

## 8. Recommended controls

- granular preference center может использоваться как conservative control, но маркируется best practice, если прямое требование российской нормы не установлено
- регулярный tag/SDK audit

## 9. Evidence / документы

- cookie/SDK register
- network scan
- provider roles
- purpose/basis matrix
- версии баннера/политики

## 10. Red flags

- копирование GDPR-текста как российского требования
- скрытые advertising trackers
- неизвестные зарубежные получатели
- session replay с вводом чувствительных данных

## 11. Regulator / expert layer

- Б-152 и Denuo используются как ориентир по текущей регуляторной практике; устные/конференционные позиции не равны официальному письменному разъяснению.
- Kept используется как источник conservative audit controls, а не как доказательство обязательности granular cookie consent.

**Правило веса:** экспертный материал используется только как аналитический ориентир. Формулировки консультантов не воспроизводятся и не превращаются в `MUST` без подтверждения первичным источником.

## 12. Uncertainty / границы вывода

- Зона высокоинтерпретационная: перед финальным выводом проверять свежие письменные позиции РКН/ГРЧЦ и судебную практику.
- Не считать любой cookie ПД автоматически; оценивать идентифицируемость в конкретной архитектуре.
