## 1. Business triggers

- сведения о здоровье
- медицинские документы
- данные пациента
- сведения о расовой/национальной принадлежности
- политические взгляды/религия/интимная жизнь
- выводы AI/analytics о таких признаках

## 2. Processing activities

- сбор
- хранение
- передача
- аналитика
- профилирование
- обезличивание/псевдонимизация

## 3. Subjects / data

**Субъекты**
- работники
- пациенты/потребители
- участники исследований/программ
- иные физлица

**Типичные данные**
- категории, прямо подпадающие под ст.10
- структурированные медицинские данные
- тексты/case narratives, из которых следует состояние здоровья
- производные признаки, раскрывающие специальную категорию

## 4. Purpose model

- медицина/охрана труда
- фармаконадзор
- страхование
- законные HR-процессы
- исследования/аналитика — при отдельном основании

**Правило:** одна техническая система или один бизнес-процесс могут включать несколько самостоятельных целей. Каждая цель получает собственные `legal basis / dataset / recipients / retention`.

## 6. Decision tree

1. Определить, относится ли информация прямо или по смыслу к специальной категории.
2. Найти конкретное допустимое условие ст.10; общей ссылки на ст.6 недостаточно.
3. Проверить, можно ли достичь цели без special data или с меньшей детализацией.
4. Определить узкий круг доступа и отдельный retention.
5. Для внешнего SaaS/AI выполнить S16/S22/S23/S29.
6. Для pharma health data определить также отраслевую цель: pharmacovigilance, patient support, medical information, research и т.д.

## 7. MUST controls

- документировать конкретное основание ст.10
- строгая access segregation
- не считать псевдонимизацию равной обезличиванию
- в incident assessment отдельно отмечать наличие специальных категорий

## 8. Recommended controls

- разделять идентификаторы и медицинский payload архитектурно
- по возможности использовать агрегированные/обезличенные наборы для аналитики

## 9. Evidence / документы

- special-data register
- legal basis memo
- access matrix
- vendor/AI assessment
- retention/deletion evidence

## 10. Red flags

- медицинские данные в обычной CRM без разделения
- health notes в свободном тексте call-center
- передача пациентского кейса в public AI
- вывод sensitive attributes для рекламы

## 11. Regulator / expert layer

- VERBA используется как отраслевой источник вопросов pharma/health/AI, но все обязательные выводы подтверждаются законом.
- Б-152 и Privacy Advocates используются для process mapping, не для замены ст.10.

**Правило веса:** экспертный материал используется только как аналитический ориентир. Формулировки консультантов не воспроизводятся и не превращаются в `MUST` без подтверждения первичным источником.

## 12. Uncertainty / границы вывода

- Обезличивание требует фактической оценки возможности отнесения данных к лицу; простое удаление ФИО не гарантирует выход из режима ПД.
