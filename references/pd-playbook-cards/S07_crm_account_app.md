## 1. Business triggers

- CRM
- личный кабинет
- мобильное приложение
- единый customer profile
- история обращений/заказов
- push-уведомления

## 2. Processing activities

- создание аккаунта
- аутентификация
- исполнение заказов
- support
- аналитика
- маркетинг
- security logging

## 3. Subjects / data

**Субъекты**
- пользователь/клиент
- представитель корпоративного клиента

**Типичные данные**
- account identifiers
- контакты
- история действий/заказов
- device/app data
- support history
- security logs

## 4. Purpose model

- управление аккаунтом
- исполнение договора
- поддержка
- безопасность
- аналитика
- маркетинг

**Правило:** одна техническая система или один бизнес-процесс могут включать несколько самостоятельных целей. Каждая цель получает собственные `legal basis / dataset / recipients / retention`.

Общий слой G01–G15 из `_general-layer.md` применяется всегда, если карточка прямо не устанавливает более специальное правило.

## 6. Decision tree

1. Разложить систему по processing activities, а не по таблицам БД.
2. Определить legal basis и retention для каждой цели.
3. Выделить SDK/third-party integrations и вызвать S16/S17.
4. Проверить device IDs/analytics через S10.
5. Push/маркетинг проверить через S11.
6. Проверить локализацию и трансграничность архитектуры.

## 7. MUST controls

- data inventory полей/таблиц/интеграций
- RBAC и журналирование
- раздельные retention rules
- удаление/ограничение аккаунта не должно разрушать обязательные архивные записи, но лишние цели прекращаются

## 8. Recommended controls

- разделять operational и marketing profile логически/правами доступа

## 9. Evidence / документы

- system data map
- purpose matrix
- API/vendor register
- access matrix
- retention config

## 10. Red flags

- одна цель «работа CRM»
- неизвестные SDK
- вечные логи с идентификаторами
- использование support-текстов для обучения AI без S29

## 11. Regulator / expert layer

- Privacy Advocates и Б-152 поддерживают process-map подход; карточка использует собственную структуру.

**Правило веса:** экспертный материал используется только как аналитический ориентир. Формулировки консультантов не воспроизводятся и не превращаются в `MUST` без подтверждения первичным источником.

## 12. Uncertainty / границы вывода

- Технические идентификаторы оцениваются с учетом возможности определения пользователя в конкретной системе.
