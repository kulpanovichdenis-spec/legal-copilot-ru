**Назначение:** отдельно проверить архитектуру первичного сбора российских ПД и не смешивать локализацию с последующей трансграничной передачей.

## 1. Business triggers

- сайт/приложение собирает данные россиян
- глобальная CRM/HRIS
- иностранный SaaS
- webinar/marketing platform
- зарубежный CDN/API получает form payload
- глобальный customer/employee master

## 2. Processing activities

- первичный ввод/сбор
- запись
- систематизация
- накопление
- хранение
- уточнение
- извлечение
- последующая репликация

## 3. Subjects / data

**Субъекты**
- граждане РФ, чьи ПД собираются оператором

**Типичные данные**
- любые собираемые ПД, подпадающие под ч.5 ст.18

## 4. Purpose model

- любые бизнес-цели; локализация является архитектурным требованием поверх цели

**Правило:** одна техническая система или один бизнес-процесс могут включать несколько самостоятельных целей. Каждая цель получает собственные `legal basis / dataset / recipients / retention`.

## 6. Decision tree

1. Определить, происходит ли именно сбор ПД граждан РФ, в том числе через интернет.
2. Нарисовать first-write flow: browser/app → endpoint → queue/log → primary DB → backups → secondary systems.
3. Для перечисленных в ч.5 ст.18 операций определить местонахождение базы/сервиса.
4. Проверить установленные законом исключения; не расширять их по аналогии.
5. После выполнения localization test отдельно провести S23 для любой зарубежной передачи/доступа.
6. Проверить скрытые потоки: crash analytics, CDN/WAF forms, email routing, SaaS logs, support.

## 7. MUST controls

- российская архитектурная карта первичного сбора
- документированное основание любого исключения
- проверка не только основной БД, но и промежуточных систем, где фактически выполняются регулируемые операции
- online verification текущей редакции ст.18 перед запуском нового глобального сервиса

## 8. Recommended controls

- автоматический data-flow review при добавлении SaaS/SDK
- contractual requirement поставщику раскрывать locations/subprocessors

## 9. Evidence / документы

- data-flow diagram
- system/location inventory
- technical confirmation first-write
- exception memo if any
- change-control record

## 10. Red flags

- форма сайта сначала пишет в зарубежный SaaS, а потом копируется в РФ
- «сервер CRM в РФ» при зарубежных logs/backups/endpoints, которые участвуют в регулируемых операциях
- подмена localization аргументом о наличии согласия субъекта

## 11. Regulator / expert layer

- Privacy Advocates, Denuo и Б1 полезны как история интерпретации поправок 2025 года. Их мнения не заменяют буквальный текст текущей ст.18 и официальную практику.
- Любая вероятностная/риск-ориентированная модель консультанта маркируется `INTERPRETATION`, не `MUST`.

**Правило веса:** экспертный материал используется только как аналитический ориентир. Формулировки консультантов не воспроизводятся и не превращаются в `MUST` без подтверждения первичным источником.

## 12. Uncertainty / границы вывода

- Архитектурная квалификация отдельных технических узлов может быть спорной; в high-risk случаях запрашивать письменную позицию/документировать conservative design.
- Наличие российской первичной БД не отвечает само по себе на вопрос о допустимости последующей зарубежной передачи — это S23.
