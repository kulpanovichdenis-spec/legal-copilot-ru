# Сбор карточек знаний (knowledge-intake)

**Архитектурный паттерн:** sequential (проход ингестии → структурирование карточки → отчёт), low-medium freedom.

## Назначение

Довести исходники из `_inbox/` до структурированных карточек в `cards/`: механику
(извлечение текста, черновик, перенос оригинала) делает проход
`tools/knowledge_ingest/intake.py` без LLM; структурирование фактов — агент.
Соглашение о слое и схема карточки — `references/profile-knowledge-layer.md`.

## Принципы

1. **Ничего не финализировать.** Карточка — черновик (`candidate`); `verification: verified` ставит только юрист отдельным подтверждением.
2. **Только факты из источника + провенанс.** Каждый факт — со ссылкой на файл в `originals/` и место (пункт/страница). Чего в источнике нет — маркер по `references/citation-rules.md` (`[ПРОВЕРИТЬ ХАРАКТЕРИСТИКИ]` для физ./тех. параметров), а не догадка.
3. **Один домен на запуск.** `products`, `corporate` и `compliance` не смешивать — разные схемы и потребители.
4. **Статус — во frontmatter, карточку не двигать.** Черновик `status: needs_enrichment` → после структурирования `status: enriched`; между папками карточка не переезжает.
5. **Карточка — навигация, не правовое основание.** Это указатель на первоисточник; правовой вывод проверяется обычным циклом (CLAUDE.md).
6. **Конфиденциальность.** Материалы клиента — без cloud-OCR (`references/document-ingestion.md`); контент `profile/knowledge/` не коммитить.

## Алгоритм

### Шаг 1 — Проход ингестии

`python tools/knowledge_ingest/intake.py --domain <products|corporate|compliance> --once`.
Проход создаёт в `cards/` черновики со `status: needs_enrichment`, оригиналы
переносит в `originals/`. Пусто и нет черновиков — сказать юристу «новых материалов нет».

### Шаг 2 — Структурировать каждый черновик

Для каждой карточки `status: needs_enrichment`: прочитать раздел «Извлечённый текст»,
переписать в структурированные факты с провенансом; уточнить `name`, `aliases`
(синонимы/бренды/торговые наименования), `reg_number`; проставить маркеры на
неподтверждённых данных; удалить служебный комментарий; поставить `status: enriched`
(оставив `verification: candidate`). Сканы/картинки, где backend вернул stub, —
провести через docling MCP (`references/document-ingestion.md`), затем структурировать.

Для `compliance` сначала прочитать `skills/pharma-compliance/references/company-extraction-rules.md`
и `company-card-schema.md`. Сохранить карточку документа в `cards/documents/`, а каждое
самостоятельное правило — отдельной YAML-карточкой в `cards/rules/`. Не объединять
запрет, исключение, лимит и согласование в одну карточку. Обязательны source locator,
дословный evidence excerpt, применимость, версия/даты и review status. Обновить
`manifest.yaml`: перечислить документы, покрытие разделов и нерешённые конфликты.
Не выводить «правила нет» только из нулевой выдачи индекса.

Для презентации источник правила указывать как `слайд N`. Если draft содержит
`needs_layout_review: true`, проверить по оригиналу изображения, таблицы и порядок
чтения; нативный текст сам по себе не закрывает coverage. Для XLSX использовать
локаторы `лист!ячейка:ячейка`. При `needs_structured_review: true` отдельно проверить
формулы, data validation и объединённые ячейки; не превращать формулу или выпадающий
список в правило без проверки его смысла в книге.

После сохранения rule-карточек пересобрать производный индекс командой
`python skills/pharma-compliance/scripts/build_company_index.py`. Если индекс уже
существует, сначала показать юристу целевой путь и запросить подтверждение перезаписи;
только после подтверждения добавить `--confirm-overwrite`. Ошибка сборки не меняет
карточки и оригиналы — сообщить её как gap индекса.

### Шаг 3 — Отчёт юристу

Одной строкой на карточку: что готово (enriched), какие поля с маркерами, что
требует подтверждения. Напомнить, что `verified` ставит юрист. Ничего не отправлять.
