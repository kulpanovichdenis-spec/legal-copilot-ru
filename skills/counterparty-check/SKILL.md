# Counterparty Check

Архитектурный паттерн: sequential + multi-MCP, Medium freedom — фактические реквизиты извлекаются из подключённых источников, а модель сопоставляет их с документом и маркирует расхождения без догадок.

## Назначение

Skill проверяет контрагента по публичному идентификатору и готовит:
- карточку юрлица/ИП по данным ЕГРЮЛ/ЕГРИП;
- сверку реквизитов с тем, что заявлено в договоре/письме/претензии;
- оценку рисков работы с контрагентом (статус, недостоверные сведения, недоимки, учредители с пометками, возраст);
- готовый блок реквизитов для подстановки в документ;
- заметку для юриста с тем, что осталось проверить по другим реестрам (банкротство, РНП, ФССП, kad.arbitr.ru).

Источник данных — локальный Legal Overlay под namespace `legal-overlay`, инструмент `mcp__legal-overlay__dadata_party` (прямой read-only adapter к DaData `findById/party`). Codex и Claude не получают отдельную DaData-конфигурацию; ключи разрешаются общим локальным config loader. Подключение и ограничения — `references/dadata-mcp-setup.md`.

## Принципы

1. На вход — **только публичный идентификатор** (ИНН / ОГРН / ОГРНИП) или текст, из которого их можно извлечь. Никаких сумм, условий, текстов договора в DaData не отправлять.
2. Skill не подменяет проверку по специализированным реестрам — банкротство, РНП, ФССП, kad.arbitr.ru остаются за `web-research-tools.md` и работой юриста.
3. Любая оценка — информационная. Финальное решение о работе с контрагентом — за юристом и бизнесом.
4. Не выдумывать реквизиты. Если DaData недоступна или не нашла — маркеры `[DADATA НЕДОСТУПНА]` / `[DADATA НЕ НАЙДЕНО]` + `[ПРОВЕРИТЬ РЕКВИЗИТЫ]`.
5. Skill не подписывает, не отправляет, не подаёт документы.

## Когда использовать

- Юрист напрямую просит проверить контрагента: «проверь ИНН …», «что по компании ОГРН …», «дай карточку контрагента».
- Готовится договор / ДС / протокол разногласий — нужно подставить реквизиты сторон.
- Готовится претензия / иск / отзыв — нужен актуальный адрес для направления и подтверждённый статус ответчика.
- Готовится письмо контрагенту — проверить, что юрлицо не ликвидировано и адрес актуальный.
- Готовится ответ госоргану, где упоминается третье лицо — сверить наименование и адрес.
- В присланном контрагентом проекте договора реквизиты выглядят подозрительно (новая компания, незнакомый адрес) — сверить.

## Когда не использовать

- Контрагент — физическое лицо без статуса ИП (у DaData нет данных).
- Нужна глубокая проверка (банкротство / РНП / ФССП / арбитражные споры) — это отдельная работа через `references/web-research-tools.md` разделы 3.1 и 3.3 (Skill подскажет, что нужно дополнительно).
- Нужна проверка кредитной истории, реальной аффилированности, бенефициаров — DaData не отдаёт.

## Подготовка входа

1. Из запроса юриста / из присланного документа извлечь идентификатор:
   - **ИНН**: 10 цифр (юрлицо) или 12 цифр (физлицо/ИП);
   - **ОГРН**: 13 цифр (юрлицо);
   - **ОГРНИП**: 15 цифр (ИП).
2. Приоритет — ИНН (наиболее частый и уникальный).
3. Если в документе фигурирует только наименование без идентификатора — попросить юриста уточнить ИНН/ОГРН (или, как fallback, использовать [egrul.nalog.ru](https://egrul.nalog.ru/) через agent-browser; см. `references/web-research-tools.md` раздел 3.3).
4. Если идентификатор замаскирован (например, `ИНН 77*****893`) — НЕ восстанавливать «по похожести», попросить полный.

## Алгоритм работы

1. Извлечь идентификатор.
2. Вызвать `mcp__legal-overlay__dadata_party(query=<идентификатор>, count=1)`.
3. Получить структурированный ответ (сырой формат DaData Suggest Party — поле `suggestions`, список):
   - если `suggestions` пуст (`[]`) → маркер `[DADATA НЕ НАЙДЕНО]`, предложить юристу проверить идентификатор;
   - если инструмент недоступен / ошибка `TOOL_UNAVAILABLE`/`CONNECTOR_FAILED` → `[DADATA НЕДОСТУПНА]`, fallback на agent-browser по [egrul.nalog.ru](https://egrul.nalog.ru/);
   - нужные поля — в `suggestions[0].data`: `name.full_with_opf`, `inn`, `ogrn`, `kpp`, `state.status` (`ACTIVE`/`LIQUIDATING`/`LIQUIDATED`/`BANKRUPT`), `address.unrestricted_value`, `management.name`/`management.post`.
4. Сформировать карточку контрагента (см. структуру ниже).
5. Если skill вызван внутри другого skill-а (contract-review, procedural-document-drafter и т. п.) с переданным «эталонным» набором реквизитов из документа — сделать сверку: расхождения по наименованию / адресу / руководителю / КПП пометить отдельно.
6. Сформировать оценку рисков по правилам ниже.
7. Сформировать готовый блок реквизитов для подстановки в документ.
8. Дать заметку для юриста: что осталось проверить по другим реестрам.

## Обязательная структура ответа

```markdown
# Проверка контрагента: <короткое наименование>

## 1. Карточка (по данным ЕГРЮЛ/ЕГРИП на дату запроса)

| Поле | Значение |
|---|---|
| Полное наименование | … |
| Краткое наименование | … |
| ИНН / КПП / ОГРН | … / … / … |
| ОПФ | … |
| Дата регистрации | … (возраст: … лет) |
| Статус | ACTIVE / LIQUIDATING / LIQUIDATED / BANKRUPT / REORGANIZING |
| Юридический адрес | … |
| Признак недостоверности адреса (ФНС) | да / нет / — |
| Руководитель | ФИО, должность |
| Учредители | список с долями (отметки о недостоверности — обязательно) |
| Уставный капитал | … руб. |
| Основной ОКВЭД | код — расшифровка |
| Лицензии | список (при наличии) |
| Категория МСП | микро / малое / среднее / — |
| Финансы (год) | выручка, недоимки по налогам |

## 2. Сверка с реквизитами из документа (если применимо)

| Поле | В документе | В ЕГРЮЛ/ЕГРИП (DaData) | Совпадает |
|---|---|---|---|
| Наименование | … | … | да / нет |
| ИНН | … | … | да / нет |
| КПП | … | … | да / нет |
| ОГРН | … | … | да / нет |
| Адрес | … | … | да / нет |
| Руководитель | … | … | да / нет |

Расхождения — отдельным комментарием с уровнем риска по `references/risk-scale.md`.

## 3. Оценка рисков

- **Verdict:** ok / warning / danger
- **Уровень риска:** low / medium / high (по `references/risk-scale.md`)
- **Риски** (до 4 пунктов, кратко).
- **Рекомендации** (до 3 пунктов).

**Дисклеймер:** оценка носит информационный характер и основана на открытых данных реестра. Финальное решение о работе с контрагентом — за юристом и бизнесом.

## 4. Блок реквизитов для документа

Готовая шапка стороны для подстановки в договор / письмо / претензию — в формате `references/house-style.md`. Если каких-то полей в карточке нет — маркер `[ПРОВЕРИТЬ РЕКВИЗИТЫ]`, не выдумывать.

## 5. Заметка для юриста: что ещё нужно проверить

- банкротство — [bankrot.fedresurs.ru](https://bankrot.fedresurs.ru/) (через agent-browser / Tavily /extract);
- реестр недобросовестных поставщиков — [zakupki.gov.ru РНП](https://zakupki.gov.ru/epz/dishonestsupplier/search/results.html);
- исполнительные производства — [fssp.gov.ru](https://fssp.gov.ru/iss/ip);
- арбитражные споры — [kad.arbitr.ru](https://kad.arbitr.ru/);
- санкционные списки (при необходимости).

Подробнее — `references/web-research-tools.md` раздел 3.3.
```

## Правила оценки рисков

| Verdict | Признаки |
|---|---|
| **ok / low** | Статус `ACTIVE`; возраст > 1 года; адрес без пометки недостоверности; учредители без пометок; недоимки незначительные/отсутствуют. |
| **warning / medium** | Возраст < 1 года; адрес отмечен как недостоверный ФНС; учредители с пометкой о недостоверности; уставный капитал минимальный (10 000 руб. для ООО) при крупной сделке; нулевая отчётность при заявленной деятельности; категория МСП «микро» при контракте на крупную сумму. |
| **danger / high** | Статус `LIQUIDATED` / `LIQUIDATING` / `BANKRUPT` / `REORGANIZING`; крупные недоимки по налогам; директор массовый (есть признак — отдельный маркер DaData); комбинация warning-признаков. |

При **danger** — обязательно остановить подготовку документа без отдельной отмашки юриста и поставить блокирующий маркер.

## Что запрещено

- Отправлять в DaData что-либо кроме идентификатора (текст договора, суммы, контактные лица, ПДн).
- Подставлять в документ реквизиты «по памяти» без вызова DaData или явной отмашки юриста.
- Делать вывод о реальной благонадёжности «по похожему названию» / без идентификатора.
- Маркировать контрагента как «надёжного» или «годного к подписанию» — это решение юриста.
- Использовать DaData для проверки контрагента-физлица без ИП (нет данных).
- Игнорировать пометки о недостоверности сведений (адрес, учредители).

## Маркеры

- `[DADATA НЕДОСТУПНА]` — коннектор не отвечает / ключи не настроены; работа продолжается с маркерами `[ПРОВЕРИТЬ РЕКВИЗИТЫ]`.
- `[DADATA НЕ НАЙДЕНО]` — по идентификатору ничего не найдено в ЕГРЮЛ/ЕГРИП.
- `[ПРОВЕРИТЬ РЕКВИЗИТЫ]` — поле не подтверждено DaData (отсутствует в карточке или коннектор недоступен).
- `[РАСХОЖДЕНИЕ С РЕЕСТРОМ]` — данные в документе не совпадают с DaData (требует решения юриста).
- `[ПРОВЕРИТЬ БАНКРОТСТВО]`, `[ПРОВЕРИТЬ РНП]`, `[ПРОВЕРИТЬ ФССП]`, `[ПРОВЕРИТЬ АРБИТРАЖНЫЕ СПОРЫ]` — для проверок за пределами DaData.
- `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]` — при verdict `danger` / расхождениях.

## Использование из других skill-ов

Skill вызывается автоматически из других skill-ов, когда они готовят документ с реквизитами юрлица/ИП:

| Вызывающий skill | Когда подключать |
|---|---|
| `contract-intake` | На этапе сбора вводных, если бизнес уже назвал контрагента — проверить статус и получить шапку реквизитов. |
| `contract-review` | Перед формированием таблицы рисков — сверить реквизиты сторон с реестром; отметить расхождения в риск-таблице. |
| `amendment-drafter` | При подготовке ДС / протокола разногласий — подтвердить, что стороны действующие, реквизиты не изменились с момента подписания основного договора. |
| `procedural-document-drafter` | Для исков, претензий, отзывов — подтвердить адрес ответчика, статус, не исключено ли юрлицо из ЕГРЮЛ. |
| `gov-response` | Если в ответе фигурируют третьи лица (контрагенты компании) — сверить наименование и адрес. |

Skill-вызыватель передаёт идентификатор + (опционально) «эталонный» набор реквизитов из документа для сверки.
