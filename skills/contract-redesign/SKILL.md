# Contract Redesign

Паттерн: sequential + domain-intelligence. Разбор положений, структура и язык — High freedom (юридическое суждение); журнал изменений — Low freedom: схема `tools/contract_redesign/schema.md`, проверка и рендер `tools/contract_redesign/changelog.py`. Модель решает, существенно ли изменение; скрипт не пропускает журнал, где существенное изменение прошло без решения юриста.

## Назначение

Два режима:

- **legacy_redesign** — новая редакция на основе корпоративного шаблона, одного или нескольких прошлых договоров: юридические решения исходника сохраняются, структура и язык перестраиваются по логике сделки;
- **restatement** — консолидированная редакция действующего договора с учётом всех дополнительных соглашений.

Результат: новая редакция (.docx), журнал изменений (.docx для юриста + `changelog.yaml` рядом как рабочий файл), заметка юристу (.docx).

## Принципы

1. Источники до позиции — `references/skill-shared-steps.md`. Норму подтверждать через `route_norm_verification(..., probe=true)` только по маршруту `usable_now: true`.
2. **Наследуемое содержание ≠ наследуемая форма.** Исходник — источник согласованных положений, риск-позиции и формулировок, но не эталон структуры, языка и состава приложений. Методология — `references/contract-design.md` (раздел 12 — переработка и консолидация; разделы 2–11 — модель сделки, структура, язык, проверки).
3. **Ни одно изменение существа не проходит молча.** Каждое значимое положение исходника — строка журнала, включая удаляемые. Уровень C (существо), удаление содержательного пункта, непройденная проверка эквивалентности, противоречие источников — только с `lawyer_decision`. Журнал проходит `changelog.py validate` без ошибок до сохранения результата.
4. **Консолидация — только по решению юриста** и не меняет объём прав и обязанностей: при restatement допустимы уровни A и B; всё, что меняет существо, — новое ДС или решение юриста.
5. Не выдумывать положения, даты вступления ДС в силу, реквизиты, суммы. Любая неполнота — маркер (`references/citation-rules.md`).
6. Результат — черновик. Подписание, отправка, согласование — за юристом.
7. Пресейв перед `workflow/` — `references/skill-shared-steps.md`.

## Когда использовать

- «Переделай наш типовой договор поставки, он устарел и неудобный».
- «Сделай новый шаблон на основе этих трёх договоров с разными контрагентами».
- «Возьми наш прошлый договор с X и подготовь новую редакцию под логику сделки, но позиции не теряй».
- «К договору уже семь ДС, собери действующую редакцию» — после решения юриста о консолидации (предложить её может `amendment-drafter`).

## Когда не использовать

- Проект прислал контрагент и нужен анализ рисков и правки — `contract-review`.
- Нужно поменять одно-два условия действующего договора — `amendment-drafter` (минимальное изменение, без переработки договора).
- Исходника нет, договор с нуля — `contract-drafter`.
- Юрист прямо просит заполнить конкретный образец без переработки — `references/template-filling-rules.md`.

## Подготовка входа

1. Все исходники (договоры, приложения, ДС, протоколы разногласий) — через `tools/doc_ingest/router.py` по протоколу `references/document-ingestion.md`. Критично сохранить нумерацию пунктов и таблицы: журнал адресуется к пунктам.
2. Проверить `metadata.warnings`; маркеры OCR и упрощённых таблиц — сообщить юристу.
3. Реальные договоры — только локальные backend-ы (без cloud-OCR). Если юрист передал документ через конвейер обезличивания — работать с `workflow/_anonymizer/_ready/*.anon.md`, плейсхолдеры сохранять.
4. Если исходник относится к делу/контрагенту с папкой в `workflow/` — сначала `case-context.md` (правило CLAUDE.md «Контекст дела»).

## Алгоритм: legacy_redesign

1. **Рамка задачи.** Что за исходники (корпоративный шаблон / прошлые договоры / чей проект), под какой бизнес-сценарий нужна новая редакция, остаётся ли корпоративная риск-позиция исходника. Неясно — 1–2 вопроса юристу.
2. **Карта условий** по `references/contract-playbook.md` раздел 0 для типа договора: показывает пропущенные в исходнике существенные/рекомендуемые условия. Устаревшие нормы и показатели исходника (редакции, ставки) — проверка по «Рабочему циклу»; их актуализация — изменение существа (строка журнала уровня C).
3. **Разбор по положениям** (`contract-design.md` 12.2–12.4): для каждого значимого положения — строка журнала (`changelog.yaml` по `tools/contract_redesign/schema.md`): где было, юридическая функция, категория A/B/C/D для пунктов «Прав и обязанностей», уровень изменения, действие, где стало, существенно ли, причина. Несколько исходников с расхождением без установленной причины — `conflict: true`.
4. **Модель сделки, архитектура комплекта, структура** — `contract-design.md` разделы 2–6: структура по жизненному циклу; состав приложений заново; архитектура исходника не повторяется автоматически.
5. **Сборка новой редакции.** Формулировки исходника сохраняются, где они юридически верны (уровень A); упрощение языка — уровень B с проверкой смысловой эквивалентности (`contract-design.md` раздел 7); одобренные клаузы — `skills/clause-library/SKILL.md`. Строки журнала обновляются по факту (`target` — итоговые номера пунктов).
6. **Проверка журнала:** `python tools/contract_redesign/changelog.py validate --file "<путь>/changelog.yaml"` — ошибок 0; каждое предупреждение отработано или объяснено в заметке.
7. **Verification gate:** каждое значимое положение исходника есть в журнале (нет «потерянных» пунктов); проверки `contract-design.md` раздел 10, включая тест унаследованной структуры; ссылки на пункты сверены после финальной нумерации (`python tools/contract_redesign/xref.py dangling --file <новая редакция.md>` — висящих ссылок 0); existence-check норм; все несущие реквизиты, суммы, даты подтверждены или помечены.
8. **Выпуск** в `workflow/`: новая редакция — вариант по типу документа (`references/document-formatting.md` таблица 6.0, `tools/docx_style/profiles.py`); журнал — `changelog.py docx --file … --out …`; заметка юристу — профиль аналитической заметки.

## Алгоритм: restatement

1. **Решение юриста о консолидации** — зафиксировано (в сессии или в `case-context.md`); без него — предложить и остановиться.
2. **Сбор цепочки:** основной договор, все ДС и протоколы разногласий, их даты вступления в силу; нет даты — `[ПРОВЕРИТЬ СРОК]`; неполный комплект ДС — сообщить юристу до сборки.
3. **Пункт за пунктом:** действующая редакция с учётом ДС в хронологическом порядке → строка `clauses` (статус, история, конфликт). Исключённые пункты и отменённые приложения — отдельными строками со статусом `excluded`.
4. **Противоречия ДС** — не разрешать самостоятельно: `conflict: true`, вопрос юристу.
5. **Проверка журнала:** `changelog.py validate` — ошибок 0; предупреждение «ни один пункт не ссылается на ДС» отработано обязательно.
6. **Выпуск** в `workflow/`: консолидированная редакция без истории изменений в тексте (вариант основного договора, таблица 6.0); журнал — `changelog.py docx`; заметка юристу, где юридическая форма консолидации (ДС «изложить договор в новой редакции» или справочный свод) — `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]`.

## Обязательная структура ответа

```markdown
# Новая редакция на основе существующего договора

## 1. Режим и исходники
legacy_redesign / restatement; перечень исходников с ролями; для restatement — ДС с датами вступления в силу.

## 2. Итог журнала
Сколько положений сохранено / перенесено / объединено / в новой редакции / удалено; **сколько изменений существа** и сколько ждут решения юриста.

## 3. Изменения существа и противоречия — решения юриста
Каждое: где было → где стало, что меняется юридически, почему предлагается, варианты. Без решения юриста новая редакция не финализируется.

## 4. Новая структура
Разделы в порядке жизненного цикла и одной фразой логика; куда разнесены «Права и обязанности»; что изменилось в составе приложений.

## 5. Файлы
Новая редакция (.docx), журнал изменений (.docx), `changelog.yaml`, заметка юристу (.docx) — пути в `workflow/`.

## 6. Чек-лист перед проверкой юристом
- журнал: validate без ошибок, предупреждения отработаны;
- ни одно значимое положение исходника не потеряно;
- изменения существа выделены и не смешаны с редизайном;
- для restatement учтены все ДС, даты вступления подтверждены или помечены;
- ссылки на пункты сверены после финальной нумерации, existence-check норм пройден.
```

## Что запрещено

- «Найти похожий договор → скопировать → поменять переменные».
- Сохранять структуру исходника только потому, что она была в исходнике.
- Удалять или переформулировать положение без строки журнала.
- Проводить изменение существа как «редизайн» или «упрощение языка».
- Выбирать между противоречащими образцами или ДС самостоятельно, без установленной причины расхождения.
- Консолидировать договор без решения юриста; менять существо при консолидации.
- Сохранять результат при ошибках `changelog.py validate`.
- Маркировать новую редакцию как «готовую к подписанию».
