# Counterparty Letter

Паттерн: sequential + context-aware (High freedom — деловое суждение; ключевая логика — развилка трёх веток: простое письмо / письмо-обоснование позиции / досудебная претензия).

## Назначение

Skill готовит **деловое письмо контрагенту по договору**, которое не поднимается до уровня досудебной претензии:
- напоминание об оплате / о сроке / об исполнении;
- запрос закрывающих документов (акт, УПД, счёт-фактура), сверки, пояснений;
- уведомление (о смене реквизитов, контактного лица, о наступлении события по договору);
- простая (не досудебная) претензия / требование без цели соблюсти досудебный порядок;
- **письмо-обоснование правовой позиции** — документ, который не требует, а **убеждает** контрагента принять нашу редакцию/позицию в ответ на его замечания (к договору, NDA, рекламному материалу, толкованию нормы). Отдельная ветка со своим сценарием (см. ниже).

Результат — проект письма в .docx (в `workflow/`) + короткая заметка юристу. Для ветки «письмо-обоснование позиции» заметка юристу — **обязательный второй продукт** (полная аммуниция, см. правило двух продуктов).

## Развилка на входе (ключевой шаг) — три ветки

**Прежде чем писать — определить статус документа** (`references/procedural-playbook.md` 14.0) из контекста задачи и назвать его юристу одной строкой. **Уточнять у юриста — только если из контекста статус неясен** (решение юриста 2026-09-29).

1. **Досудебная претензия** (обязательный досудебный порядок ст. 4 ч. 5 АПК РФ; документ будет прикладываться к иску как доказательство соблюдения порядка) → **не этот skill**, а `procedural-document-drafter` §14 (полный сценарий). Сюда же — любой документ, который может позже использоваться как подтверждение соблюдения досудебного порядка (безопасный дефолт при сомнении — считать досудебной претензией).
2. **Простое письмо** — напоминание / запрос / уведомление / простое требование (не позиционируется как досудебная, не для соблюдения порядка) → ветка «простое письмо» ниже.
3. **Письмо-обоснование правовой позиции** — документ **не требует** исполнения, а **убеждает** контрагента принять нашу правовую позицию/редакцию в ответ на его замечания (к договору, NDA, рекламе, толкованию нормы) → ветка «письмо-обоснование позиции» ниже.

**Тест 2 vs 3:** цель простого письма — попросить/уведомить/напомнить (правовая квалификация минимальна или не нужна); цель письма-обоснования — **убедить правовой аргументацией** (норма + практика/подход регулятора — это и есть суть документа). Если контрагент прислал возражения к нашему документу и мы доказываем свою правоту — это ветка 3.

Развилка — зеркало правила §14.0.

## Принципы

1. Юрисдикция РФ; результат — черновик; ничего не отправлять без юриста.
2. Тон для контрагента — по `references/house-style.md` (деловой и твёрдый, без лишнего конфликта, **без угроз без правового основания**, без признаний собственного поведения без необходимости). Угрозы судебной защиты — обтекаемо, без указания конкретной инстанции (house-style + `procedural-playbook.md` 14.3). В записке юристу рекомендации адресны: кто, что и в какой срок делает.
3. **Риск самопризнания** — письмо не должно случайно признавать долг, просрочку, нарушение, вину, объём или обстоятельства во вред компании. Проверять каждую формулировку.
4. Не выдумывать факты, суммы, даты, реквизиты, номера договоров и актов — при пробеле маркер.
5. Если письмо ссылается на норму — существование ссылки проверяется по `references/source-hierarchy.md` (шаг 6) до сохранения; не найдено — `[ПРОВЕРИТЬ НОРМУ]`. Но письмо, как правило, обходится без правовой квалификации — норму включать только если она реально обосновывает требование.
6. Итоговый документ — сразу в .docx (`references/docx-generation.md`), не .md. Reader-facing текст проверяется по режиму `BUSINESS_EMAIL` из `references/business-legal-writing.md`: ответ/цель в начале, действие и срок адресны, пробел не маскируется, незаконный вариант не предлагается как выбор. Перед сохранением — чистка от AI-slop (`references/anti-slop.md`; машинная проверка — `tools/slop_check/`).
7. **Ветка «письмо-обоснование позиции»:** тон — вежливо-официальный дипломатический регистр (`references/house-style.md` «Для контрагента»); аргументация — по модели претензии/IRAC (`references/procedural-playbook.md` 14.1–14.3, `references/irac-rules.md`); всегда **два продукта** — письмо + записка юристу (`references/docx-generation.md` §3; отбор доводов — «не давать в руки лишнего»); глубина ресёрча — авто, гибрид (см. алгоритм ветки).

## Когда использовать

- «Напиши письмо контрагенту с просьбой прислать акты / УПД / счёт».
- «Напомни контрагенту об оплате / о сроке поставки».
- «Уведоми контрагента о смене реквизитов / контактного лица».
- «Сделай простую претензию / письмо-требование» — **без** цели соблюсти досудебный порядок.
- «Контрагент прислал замечания к нашему договору / NDA — обоснуй нашу позицию», «Ответь на возражения контрагента», «Убеди контрагента принять нашу редакцию», «Объясни правовой службе контрагента/канала, почему наш материал допустим» → **ветка «письмо-обоснование позиции»**.

## Когда не использовать

- Документ является досудебной претензией или может использоваться как подтверждение соблюдения досудебного порядка — `procedural-document-drafter` §14 (см. «Развилка на входе»).
- Иск, отзыв, ходатайство, жалоба, мировое — `procedural-document-drafter`.
- Ответ государственному органу — `gov-response`.
- Правка самого договора / ДС — `contract-review` / `amendment-drafter`.

## Алгоритм работы

1. **Развилка** — определить статус (три ветки выше). Досудебная → перенаправить в `procedural-document-drafter`, здесь не продолжать. Письмо-обоснование позиции → перейти в блок «Ветка «письмо-обоснование позиции»» ниже. Простое письмо → шаги 2–6.
1а. **Контекст дела** — если адресат/дело имеет папку в `workflow/` — прочитать `case-context.md` (правило CLAUDE.md «Контекст дела»), отчитаться одной строкой.
1б. **Проверенный опыт** — для простого требования с фактическим спором и для письма-обоснования найти релевантные `human_verified` объекты через `search_verified_knowledge` (либо `legal_search` с `source_types=["internal"]`). Использовать их только как evidence/drafting/risk context по `references/case-knowledge-layer.md`; candidates и case studies сами по себе в письмо не переносить, правовые тезисы проверять отдельно. Для административного напоминания или запроса документов этот шаг пропустить.
2. **Проверка контрагента** — обязательный шаг перед адресацией: `skills/counterparty-check/SKILL.md` (DaData MCP) по ИНН/ОГРН. Подтвердить, что юрлицо действующее; взять **актуальный адрес** (письмо не по адресу из ЕГРЮЛ может быть оспорено как ненадлежащее уведомление) и наименование/руководителя для адресации. Контрагент без идентификатора — запросить ИНН/ОГРН, не угадывать.
3. **Собрать фактуру** письма: договор (№, дата), суть обращения, что просим/уведомляем, срок ответа/исполнения, реквизиты для исполнения (при денежном требовании).
4. **Проверка риска самопризнания** — пройти по тексту: нет ли невыгодного признания долга/просрочки/нарушения/обстоятельств.
5. **Проект письма** — по структуре ниже, тон по house-style и `references/business-legal-writing.md`; служебные markers остаются в заметке юристу, а в письме преобразуются только в понятный вопрос/условие без сокрытия решающего пробела.
6. **Генерация .docx** в `workflow/` + короткая заметка юристу. Если подключён фирменный стиль (`profile/knowledge/brand/brand.yaml`), письмо собирается на бланке компании (`LetterheadDoc(purpose="counterparty_letter")`); незаполненные слоты из отчёта сборки назвать юристу. Правила — `references/brand-letterhead.md`.

## Ветка «письмо-обоснование позиции»

Отдельный жанр: не требуем — **убеждаем** контрагента принять нашу правовую позицию/редакцию в ответ на его замечания. Живые образцы жанра из практики — переписка по ТВ-рекламе (обоснование допустимости обозначения) и по NDA (ответ на замечания к соглашению).

Алгоритм ветки (шаги 1, 1а, 2, 4 из основного алгоритма выполняются так же — статус, case-context, counterparty-check, риск самопризнания):

1. **Собрать замечания контрагента по пунктам** и нашу целевую позицию/редакцию по каждому. Не выдумывать замечания — при пробеле `[ПРОВЕРИТЬ ФАКТ]`.
2. **Глубина ресёрча — авто (гибрид).** Выбрать по сути вопроса и **назвать уровень одной строкой** (лестница — `references/source-hierarchy.md`, «Настройка исследования»):
   - *quick* — норма очевидна, один ясный пункт;
   - *standard* — несколько замечаний, нужна норма + подход регулятора/практика;
   - *deep* — несколько спорных правовых пунктов, нужен разбор позиции против себя → вести исследование **движком `legal-opinion`** (`skills/legal-opinion/SKILL.md`: adverse-проход, `source-verifier`/`adversarial-researcher`), а письмо-обоснование = оформление результата. Нормы проверять по capability-маршруту из `references/source-hierarchy.md`.
3. **Правило двух продуктов** (`references/docx-generation.md` §3):
   - **(а) письмо контрагенту** — только доводы, прямо и однозначно работающие на позицию (`house-style.md` «не давать в руки лишнего»: убрать обоюдоострое, самоограничительные цитаты о своём продукте, слабые пункты);
   - **(б) записка юристу** — полная аммуниция: сверка норм (с редакциями), практика ВС/ФАС, рыночные ориентиры, business-развилки, всё обоюдоострое и стратегические `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]`.
4. **Аргументация — по модели претензии/IRAC** (`references/procedural-playbook.md` 14.1–14.3, `references/irac-rules.md`): по каждому пункту — существо замечания → краткая позиция → норма (что именно запрещено/разрешено) → практика / подход регулятора → «навстречу» (компромисс формы без уступки существа) → вывод.
5. **Тон — вежливо-официальный (дипломатический) регистр** (`references/house-style.md` «Для контрагента»): сдержанное несогласие, сохранение лица, **без угроз, срока-ультиматума и «оставляем за собой право обратиться в суд»** (это регистр претензии, не убеждения).
6. **Генерация двух .docx** в `workflow/`. Для письма-обоснования заполнить `business_writing.v1` в режиме `BUSINESS_EMAIL` и пройти `python tools/business_writing/final_check.py <manifest.json>`; manifest содержит фактический trace незакрытых gaps, а не только флаг. Для простого административного письма без материального правового/рискового вывода достаточно checklist `references/business-legal-writing.md`. Пресейв: existence-check каждой нормы (`references/source-hierarchy.md`, шаг 6) + чистка от AI-slop (`references/anti-slop.md` / `tools/slop_check/`).

Структура письма-обоснования: шапка (адресат + исх. №, дата) → обращение по наименованию → сухая благодарность за замечания → «по существу замечаний» (по пунктам, по модели IRAC) → «навстречу» (предлагаемые уточнения) → итог (надежда/расчёт на согласование) → подпись.

## Обязательная структура ответа

```markdown
# Письмо контрагенту

## 1. Статус документа
Подтверждение: это простое письмо (не досудебная претензия). Если статус снимался уточнением у юриста — отметить.

## 2. Что понятно
Адресат, договор (№, дата), цель письма, срок. Не названо — маркер.

## 3. Проверка контрагента
Итог counterparty-check: наименование, актуальный адрес для направления, статус юрлица. Расхождения с договором — отдельной строкой.

## 4. Проект письма (.docx)
Ссылка на сгенерированный .docx. Структура письма: шапка (адресат + наш исх. №, дата) → обращение по наименованию → суть (фабула кратко) → требование/просьба/уведомление → срок → последствия (обтекаемо, если применимо) → реквизиты для исполнения (при денежном) → подпись.

## 5. Заметка юристу
Короткая: какие места помечены маркерами, где проверен риск самопризнания, что осталось за юристом. Если статус документа спорный — явно указать, что при позиционировании как досудебной претензии документ нужно готовить по procedural-document-drafter §14.
```

Для ветки **«письмо-обоснование позиции»**: в §1 указать статус «письмо-обоснование» и выбранную глубину ресёрча (одной строкой); §4 — **два .docx** (письмо + записка юристу), структура письма по блоку «Ветка «письмо-обоснование позиции»»; §5 (записка юристу) — полноценный второй продукт с аммуницией, а не краткая приписка. Перед сохранением — отчёт по пресейв-гейту (норма-existence + slop-чек).

## Что запрещено

- Готовить досудебную претензию под видом простого письма (обход полного сценария §14) — при досудебном статусе перенаправлять в `procedural-document-drafter`.
- Включать признание долга/просрочки/нарушения/обстоятельств без указания юриста.
- Формулировать угрозу без правового основания или с указанием конкретной судебной инстанции без указания юриста.
- Выдумывать реквизиты, суммы, даты, номера договоров и актов. В письме-обосновании — также не выдумывать свойства/характеристики своего продукта или объекта: фактические утверждения сверяются с первоисточником, при пробеле — маркер.
- Отдавать результат в .md как итоговый (только .docx).
- В ветке «письмо-обоснование позиции» — сползать в претензию (угрозы, срок-ультиматум, «оставляем за собой право обратиться в суд»); выносить в письмо обоюдоострые доводы и полную аммуницию вместо записки юристу (нарушение правила двух продуктов).
