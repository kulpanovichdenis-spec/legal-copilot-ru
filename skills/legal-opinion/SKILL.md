# Legal Opinion

**Архитектура:** sequential + domain-intelligence, High freedom. Индекс-роутер к тонким карточкам-архетипам (`references/legal-opinion-cards/`); исследовательский движок переиспользуется из `references/source-hierarchy.md` («Workflow для правовых выводов»); детальная методология жанра — `references/legal-opinion-method.md` (глубина × формат, fact matrix, issue tree, синтез правила, adverse-pass, claim-ledger, шаблоны вывода, support-файл). Ничего из этого не дублируется в теле SKILL.

## Назначение

Skill готовит **черновик правового заключения (меморандума)** по поставленному правовому вопросу: переформулирует бизнес-вопрос в точные правовые вопросы, проводит исследование по нашим базам с настраиваемой глубиной, синтезирует правило, применяет его к фактам по IRAC (с обязательным разбором позиции против себя), калибрует уверенность и выдаёт мотивированный вывод с оценкой риска и рекомендацией.

Это заключение **по правовому вопросу** — отличается от заключений по проверяемому материалу (реклама — `fas-ad-practice-search`; договор построчно — `contract-review`).

**Оси исследования** (детали — `references/legal-opinion-method.md`, §1): глубина `research_depth` — **авто**, определяется по сигналам задачи; что конкретно меняется по уровням quick/standard/deep — операционная лестница в `references/source-hierarchy.md`, «Настройка исследования». Формат `output_format` (short_advice / legal_memo / full_legal_opinion) независим от глубины (короткий документ ≠ поверхностное исследование). Позиция `research_stance` — `neutral` (по умолчанию) или `position_led` (юрист заранее назвал искомую позицию/основание — обоснование строится под неё, но объективность и adverse-проход сохраняются). `synthesis_mode` — auto (по умолчанию) или lawyer_checkpoint (юрист сам формулирует правило после исследования).

## Что готовит skill

1. Переформулировка вопроса — 1..N точных правовых вопросов (issue tree);
2. Fact matrix (статусы фактов) и классификация вопросов по архетипу;
3. Исследование в заданной глубине (доктрина → практика → якорь-норма → аналогия);
4. Rule synthesis + извлечение позиций с перепроверкой по первоисточнику;
5. Анализ по IRAC с обязательным adverse-подшагом — блок на вопрос + сводный вывод;
6. Калибровка уверенности, риски, «что проверить», рекомендация; для LO-1/LO-4 — компонент «стоимость риска / принятие риска»;
7. **Два продукта**: правовое заключение (`.docx` в `workflow/`, формат по `output_format`) + support-файл `legal_opinion_research` (аудит-след; `.docx` юристу + техническая `.md` рядом).

## Принципы

1. Не из общего знания — сначала базы и «Workflow для правовых выводов» (`references/source-hierarchy.md`). Юрисдикция определяется до поиска; юрисдикции не смешиваются.
2. Заключение опирается на **проверенный первоисточник** (текст нормы + сверенный судебный акт). Консультационный слой (comments/доктрина/обзоры практики/telegram/opinions) часто **указывает основание** — его извлекают и **перепроверяют по первоисточнику**; на собственный авторитет комментария без проверки опираться нельзя. Не перепроверено — `[СВЕРИТЬ С ПЕРВОИСТОЧНИКОМ]`, в ratio не идёт.
3. Каждый правовой вопрос — отдельный IRAC-блок (`references/irac-rules.md`); калибровка формулировок, без абсолютов («всегда», «однозначно», «лишается всех прав» запрещены по умолчанию).
4. Гейт по **правовым версиям** (потолок, не минимум), не по числу запросов; вторичный tool-call cap на issue против ухода на круг; «не найдено» — только после expansions (`references/query-cookbook.md`), не с одной формулировки. Определение версии и пороги — `references/source-hierarchy.md`, «Ограничитель».
5. Verification gates перед сохранением (`references/source-hierarchy.md`): existence-check — discovery; каждую норму раскрыть через `route_norm_verification(..., probe=true)` и provider с `usable_now: true`. Маркеры неполноты — вплотную к реквизиту.
6. Аналогия — только с явным маркером `[ПРИМЕНЯЕТСЯ ПО АНАЛОГИИ: X→Y, отличие Z]`; региональная практика — с оговоркой.
7. Результат — черновик, `.docx` в `workflow/`, human review; честный отказ («применимого источника не найдено») вместо угадывания.

## Когда использовать

Триггеры:
- «юридическое заключение», «правовое заключение», «подготовь / нужно / надо / хочу заключение по вопросу», «заключение по вопросу о …», «меморандум», «правовая позиция по вопросу»;
- «можно ли по закону …», «вправе ли мы …», «допустимо ли …»;
- «как читать / толковать эту норму / это условие», «что означает …»;
- «какой это договор», «как квалифицировать эти отношения», «какой статус у …»;
- «какие риски, если мы …», «чем грозит …», «действительна ли сделка, если …»;
- общий правовой вопрос без привязки к конкретному документу на анализ или к спору.

## Когда не использовать

- **Построчный анализ конкретного договора** (протокол разногласий, правки клауз) → `contract-review`.
- **Составление документа** (иск, отзыв, претензия, ходатайство, ответ госоргану, письмо) → `procedural-document-drafter` / `gov-response` / `counterparty-letter`.
- **Проверка рекламного креатива** на риск ФАС → `fas-ad-practice-search`.
- **Проверка контрагента** по ИНН/ОГРН → `counterparty-check`.
- **Критика готовой позиции** → `position-critic`.
- **Анализ мультидок-дела целиком** (позиции всех сторон, вывод по спорным вопросам, стратегия, справка) → `case-analysis`; метод этого skill применяется там по каждому вопросу.
- **Материал для бизнеса по готовому выводу** (презентация для правления, записка на решение, обучение, памятка) → `business-communication`; заключение служит ему входом.
- **Дайджест или обзор изменений законодательства, проектов и практики** → `skills/legal-digest/SKILL.md`. Заключение подключается, если из обзора вырос отдельный правовой вопрос.

Если по ходу заключения нужен материал этих skills — они вызываются **как источники существа**, а `legal-opinion` собирает из этого меморандум (см. ниже).

## Взаимодействие с другими skill

`legal-opinion` — оркестратор-меморандум. Он **вызывает** профильные skills и сценарные карточки локального корпуса (`search_legal_kb`) для существа, но производит именно заключение:

| Нужно в заключении | Откуда берётся существо |
|---|---|
| Тип сделки / договорные риски | сценарные карточки локального корпуса (`search_legal_kb`: уступка, недействительность, аренда, ответственность — см. `references/query-cookbook.md`) |
| Регуляторный риск (реклама/КНМ/техрегулирование) | `skills/fas-ad-practice-search/SKILL.md`, `skills/fz248-knm-rospotrebnadzor/SKILL.md`, `skills/fz184-technical-regulation/SKILL.md` |
| Аргументационный блок IRAC под будущий документ | если итог — документ, а не заключение, ведущим становится `procedural-document-drafter` / `gov-response`, а `legal-opinion` не запускается |

## Классификация по архетипу (индекс-роутер)

Пройти таблицу, открыть **только** сработавшие карточки (обычно 1–2), не весь набор. При нескольких вопросах в одной задаче — по карточке на каждый.

| Сигнал в вопросе | Карточка | Что делает |
|---|---|---|
| «можно ли / вправе ли / допустимо ли сделать X» | LO-1 `references/legal-opinion-cards/01-dopustimost-deystviya-sdelki.md` | разрешено / запрещено / при условиях |
| «как толковать это условие / эту норму», «что означает» | LO-2 `references/legal-opinion-cards/02-tolkovanie-usloviya-normy.md` | доктрина + практика ВС → смысл нормы |
| «какой это договор», «как квалифицировать», «какой статус» | LO-3 `references/legal-opinion-cards/03-kvalifikaciya-pravootnosheniya.md` | правовая природа + последствия режима |
| «какие риски, если …», «действительна ли сделка», «чем грозит нарушение» | LO-4 `references/legal-opinion-cards/04-risk-nedeystvitelnost-otvetstvennost.md` | калиброванная оценка риска + цена вопроса |

Итеративность: если исследование по карточке даёт слабую релевантность или всплывает другой архетип (напр. вопрос «можно ли» упирается в риск недействительности) — добрать смежную карточку.

## Алгоритм работы

Полное наполнение каждого шага — `references/legal-opinion-method.md`. Ниже — костяк.

**Шаг 0 — Intake.** Если вопрос относится к делу с папкой `workflow/<дело>/` — прочитать `case-context.md` (и `deadlines.yaml`, если есть), а для мультидок-дела с собранным структурным слоем — ещё и `matter-timeline.yaml`/`matter-facts.yaml` (`references/matter-model-usage.md`); отчитаться одной строкой. Шаблон — `templates/agent-notes/case-context-template.md`. По типу вопроса найти `human_verified` через `search_verified_knowledge` и использовать только как evidence/drafting/risk context; кандидатов не использовать, правовые тезисы проверять отдельно. Правила — `references/case-knowledge-layer.md`. Определить `research_depth`, `output_format`, `research_stance`, `synthesis_mode` (метод-reference §1); если юрист не задал — оценить самому и **назвать выбранные значения одной строкой**. Если юрист заранее назвал искомую позицию/квалификацию/основание — `research_stance = position_led` (объективность обязательна: см. Шаг 4). Извлечь уже известные параметры из запроса/документов, не переспрашивать; недостающее критическое — **один** компактный набор уточнений.

**Шаг 1 — Fact matrix + issue tree.** Собрать fact matrix (статусы CONFIRMED/REPORTED/INFERRED/DISPUTED/UNKNOWN/ASSUMED — метод §2): отделить подтверждённое документом от сообщённого; не повышать статус тихо; decisive unknowns — под маркер и в текст заключения. **Для мультидок-дела с собранным factual layer** fact matrix строится **из `matter-facts.yaml`/`matter-timeline.yaml`**, а не пересобирается из исходников (`references/matter-model-usage.md`, «Проводка downstream»); слоя нет и дело fact-heavy — предложить завести его (не обязателен для разового вопроса). Развернуть бизнес-вопрос в issue tree (метод §3) — 1..N точных правовых вопросов, каждый трассируем к выводу. В `deep` определить **режим сведения** — раздельный (ответ по каждому вопросу) или комплексный (позиции объединяются в единый вывод; метод §3). Юрисдикция определяется **до поиска** (при неочевидности — `route_legal_query`), не смешивается.

**Шаг 2 — Классификация.** По каждому issue подобрать архетип по таблице выше, подгрузить только сработавшие карточки.

**Шаг 3 — Исследование** (в объёме `research_depth`). Запустить «Workflow для правовых выводов» (`references/source-hierarchy.md`): единая локальная доктрина (`search_doctrine`, затем `get_doctrine_unit`; `doctrine_only`) → для глубокого гражданско-правового вопроса авторизованная Glossa (`glossa_stats` → `glossa_support` → раскрытие контекста; обязательно supports/limits/contradicts) → практика (локальные `search_positions`, при пробеле КонсультантПлюс (`consultant_search` → раскрытие текста), затем релевантный Casus corpus; **как вести подбор, оценивать authority и статус практики — `references/case-law-search.md`**) → **якорь на текст нормы** через `route_norm_verification(..., probe=true)` и provider с `usable_now: true` → аналогия (с маркером). Внешние базы — только по `references/external-legal-databases.md`: доктрина/коммерческая карточка не заменяет раскрытый проверенный первоисточник. «Не найдено» — только после 2–4 expansions по словарю (`references/query-cookbook.md`), не с одной формулировки. Проверять релевантную дату/редакцию. Критерии достаточности — метод §4.

**Шаг 4 — Adverse pass + извлечение правил.** Отчёт изоляции — `ADVERSARIAL_POSITION` из `references/adverse-review.md`. Отдельно от обычного поиска — целенаправленно искать, что **против** предполагаемого вывода (метод §6; обязательно в standard/deep, по каждому ключевому issue в deep; глубокий разбор — `skills/position-critic/SKILL.md`). **В `research_stance = position_led` adverse-проход обязателен независимо от глубины**. Консультационный слой часто лишь **указывает основание**: норму раскрыть через capability-маршрут с `usable_now: true`; судебный акт — в первоисточнике; связь позиция→норма — через `list_position_norm_links`. В заключение идёт проверенный первоисточник (`references/citation-rules.md`), не комментарий; не перепроверено — `[СВЕРИТЬ С ПЕРВОИСТОЧНИКОМ]`. В standard/deep adverse-поиск ведёт `adversarial-researcher`; матрица — `references/legal-opinion-subagents.md`. Этот шаг строит позицию против; применение к нашему выводу — отдельный проход на Шаге 5. Найденные судебные акты разбирать по `references/court-decision-analysis.md`.

**Шаг 5 — Rule synthesis + анализ по IRAC.** Сначала **синтезировать рабочее правило** по каждому issue (метод §5) — не «ст. A говорит X; дело B говорит Y». Затем отдельный IRAC-блок Вопрос/Правило/Анализ/Вывод на каждый вопрос (`references/irac-rules.md`) с **обязательным adverse-подшагом** внутри Анализа (лучший контраргумент и почему он (не) срабатывает — метод §8). **Adverse-подшаг — отдельный проход по отчёту Шага 4, не пересказ его рядом с выводом**: каждый сильный довод против прикладывается к анализу (срабатывает / не срабатывает и почему; отличается ли по фактам), а довод, который не удалось ни опровергнуть, ни отличить, идёт в `dependencies`/`mitigation` и в риски Шага 6, а не исчезает молча (метод §6, «Два разных этапа»). При нескольких вопросах (`deep`) — перечень в начале; в конце по режиму сведения (§3): `separate` — самостоятельные ответы по каждому вопросу, `integrated` — единый комплексный вывод, синтезирующий позиции (метод §8). Калибровка уверенности — метод §9 (`position_strength` / `certainty` / `impact` / `dependencies` / `mitigation`), поверх `references/risk-scale.md`.

*Если `synthesis_mode = lawyer_checkpoint`* — после исследования не переходить к финальному применению: показать юристу Synthesis Pack (метод §7) и ждать.

**Шаг 6 — Риски и рекомендация.** Блок «риски + что проверить + рекомендация». Для архетипов **LO-1/LO-4** (взвешивается бизнес-действие) — **обязателен** компонент «стоимость риска / решение по lawful course и residual risk» (карточка LO-4; CLAUDE.md, «Блок "что поправить"», компонент 2): цена вопроса конкретно (штраф/взыскание/убытки/риск недействительности — из нормы либо под маркер), иные последствия, mitigation и остаточный риск законного варианта. Бизнес выбирает между законными вариантами и может принять их остаточный риск (`[ВОПРОС БИЗНЕСУ]` / `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]`). Нарушение не становится вариантом «принять риск»: его последствия объясняются отдельно, юридическая служба его не рекомендует. Для LO-2/LO-3 компонент не включается.

**Шаг 7 — Source verification (CLAIM_LEDGER) + gates.** Отдельным проходом после черновика прогнать claim-ledger (метод §10): каждое проверяемое утверждение → источник открыт непосредственно, реквизиты верны, вывод не шире источника, редакция на релевантную дату. Existence-check — только discovery; норму раскрыть через `route_norm_verification(..., probe=true)` и provider с `usable_now: true`. Не подтверждается — сузить/заменить/удалить/пометить (`[ПРОВЕРИТЬ НОРМУ]` / `[СВЕРИТЬ С ПЕРВОИСТОЧНИКОМ]`). В standard/deep проверку тезис→источник ведёт `source-verifier`, а для сложных deep-заключений — `consistency-checker`; матрица — `references/legal-opinion-subagents.md`. Отчёты проверок — JSON по схеме, статус «проверено» ставит `tools/agent_contracts/contracts.py validate`, перед записью `.docx` — `contracts.py check-run` (там же, «Отчёты по схеме и гейт сохранения»). Финальный YES/NO чек-лист — метод §12.

**Шаг 8 — Два продукта.** Собрать (1) **правовое заключение** `.docx` по `output_format` (метод §11) — `references/document-formatting.md` + `references/docx-generation.md`, заголовок «Правовое заключение»; и (2) **support-файл** `legal_opinion_research` (аудит-след; объём по `research_depth`) — `.docx` юристу + техническая `.md` рядом. Reader-facing слой проверить по режиму `LEGAL_MEMO` или `SHORT_ANSWER` из `references/business-legal-writing.md`: ответ или точная зависимость в начале, uncertainty классифицирована, action имеет owner/next step, risk — trigger/consequence. Внешняя бизнес-версия может преобразовать служебные markers в понятные оговорки, но исходные markers и trace остаются в заключении для юриста/support-файле. Для значимого reader-facing текста запустить `tools/business_writing/final_check.py`; его успех не заменяет claim-ledger, source-verifier и human review. Сохранить в `workflow/` (при явной категории дела — в подпапку, сообщив одной строкой). Ничего финального.

## Структура заключения (.docx) — по output_format

Полные шаблоны трёх форматов — `references/legal-opinion-method.md`, §11. Модель для всех: **вводная → выводы/рекомендации → мотивировка** (краткие выводы идут до подробного анализа). Дефолтный `legal_memo`:

```
Правовое заключение по вопросу «[короткая формулировка]»

1. Вводная часть (предмет и цель; фактическая ситуация; неустановленные обстоятельства и допущения; вопросы; изученные документы)
2. Выводы и рекомендации (по каждому вопросу: Вывод / Риск / Рекомендация)
3. Мотивировочная часть (по каждому вопросу: Вывод / Применимое правило / Обоснование-синтез / Применение к фактам / Контраргументы и риски / Итог)
   — для LO-1/LO-4 в блоке рисков: lawful course, стоимость и residual risk
4. Заметка юристу (маркеры, стратегические решения)
5. Источники (нормы / позиции / карточки; результаты existence-check)
```

`short_advice` — сжатая форма без полной мотивировки; `full_legal_opinion` — та же архитектура + scope, chronology, assumptions, risk matrix, варианты действий, приложения (метод §11).

## Что запрещено

- Выдумывать нормы, статьи, редакции, судебную практику, реквизиты, факты, суммы. Нет опоры — маркер.
- Подавать консультационный слой (comments/доктрина/обзоры практики/telegram/opinions) как самостоятельное основание без перепроверки первоисточника.
- Категоричные абсолюты в выводе; решать за бизнес выбор lawful course или принятие его residual risk; подавать нарушение как допустимый вариант.
- Смешивать два правовых вопроса в одном IRAC-блоке; смешивать юрисдикции.
- Отдавать заключение в `.md` как финал; маркировать результат «финальным / готовым».
