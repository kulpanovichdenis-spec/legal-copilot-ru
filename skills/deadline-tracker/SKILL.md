# Deadline Tracker

Пути в примерах приведены для новых дел. Для существующих файлов и специальных проектов применять `references/workflow-layout.md`.

Архитектурный паттерн: context-aware + Low freedom — детерминированное ядро `tools/deadline_tracker/tracker.py` (хранение, валидация, календарная арифметика, отчёт); модель — только извлечение сроков из документов и суждение о категории/приоритете.

## Назначение

Персистентный трекер сроков по конкретному делу/контрагенту: один YAML-файл в `workflow/<дело>/_llm/deadlines.yaml`, который живёт между сессиями. Skill закрывает три типа сроков:

- **procedural** — процессуальные (апелляция, кассация, отзыв, обжалование постановления КоАП);
- **prescription** — сроки из предписаний/запросов госорганов (исполнение, ответ, жалоба);
- **contract** — договорные (окончание действия, окно уведомления о непролонгации, гарантийные).

## Принципы

1. **Все операции с файлом — только через скрипт** `tools/deadline_tracker/tracker.py` (init/add/update/report). Модель не редактирует YAML руками и не считает «сколько осталось» в уме. Ручная правка файла юристом допустима.
2. **Скрипт не исчисляет юридические сроки.** Он хранит уже определённые даты и считает только календарное расстояние до них. Определение самой даты (рабочие/календарные дни, момент получения, перенос с нерабочего дня) — по gate из `skills/procedural-document-drafter/SKILL.md`, раздел «Что запрещено».
3. **`date_status: confirmed` — только при выполненном gate** (дата начала течения подтверждена первоисточником, порядок исчисления проверен по норме, перенос учтён) и обязательно с `--basis` (норма + как исчислено). Во всех остальных случаях — `needs_check`: скрипт сам пометит строку `[ПРОВЕРИТЬ СРОК]`.
4. **Не выдумывать даты и реквизиты.** Дата берётся из документа-первоисточника (определение, предписание, договор, уведомление о вручении). Нет документа — нет confirmed-даты.
5. **Трекер — рабочий файл агента и юриста** (.yaml допустим). Сводка `report` отдаётся юристу в чат; если юрист просит документ — .docx по `references/docx-generation.md`.
6. **Элементы не удаляются** — закрываются статусом (`done` / `cancelled`), чтобы история сроков сохранялась.

## Режимы

### Init — завести трекер

Когда юрист называет дело/контрагента, по которому нужен контроль сроков:

```
python tools/deadline_tracker/tracker.py init --file "workflow/<дело>/_llm/deadlines.yaml" --matter "<дело>"
```

Подпапка — по правилу CLAUDE.md о структуре `workflow/` (очевидная категория из реплики юриста; о выборе сообщить одной строкой).

### Add / Ingest — внести сроки

Источники: документы, переданные юристом (определение суда, предписание, договор), и результаты других skills — `procedural-document-drafter` (сроки обжалования), `gov-response` (срок ответа/исполнения предписания), `contract-review` / `amendment-drafter` (сроки действия, окна пролонгации и уведомлений). Для каждого срока:

```
python tools/deadline_tracker/tracker.py add --file "workflow/<дело>/_llm/deadlines.yaml" \
  --title "<что сделать>" --category procedural|prescription|contract|other \
  --due-date YYYY-MM-DD --date-status confirmed|needs_check \
  --basis "<норма + как исчислена>" [--blocking] [--lead-time N] \
  [--source-doc "<документ-первоисточник>"] [--responsible "<кто>"]
```

`--lead-time N` — оценка, сколько дней нужно на подготовку (по умолчанию 3); от неё считается зона риска: `(срок − сегодня) < lead_time`. `--blocking` — срок, пропуск которого блокирует дело (утрата права на обжалование и т. п.).

### Update — обновить статус

```
python tools/deadline_tracker/tracker.py update --file "..." --id D-001 --status done
```

Тем же режимом подтверждается дата после проверки юристом: `--date-status confirmed --basis "..."`.

### Report — сводка «что горит»

```
python tools/deadline_tracker/tracker.py report --file "workflow/<дело>/_llm/deadlines.yaml"
```

Порядок в отчёте: просрочено → зона риска → предстоит → без подтверждённой даты; внутри секций blocking первыми. Отчёт передавать юристу как есть, при необходимости — с кратким комментарием, что требует решения.

## Что запрещено

- **Не вносить дату как confirmed без выполнения gate и basis** (вносить как needs_check — это нормальный, а не ущербный статус).
- Не рассчитывать и не «уточнять» даты в обход скрипта и юриста.
- Не удалять элементы и не переписывать файл целиком.
- Не считать отчёт трекера юридическим заключением о сроках — это операционная сводка.

## Связанные файлы

- `tools/deadline_tracker/tracker.py` — ядро (есть `selftest`)
- `skills/procedural-document-drafter/SKILL.md` — gate на выдачу дат сроков («Что запрещено»)
- `references/procedural-playbook.md` — порядок исчисления конкретных процессуальных сроков
- `references/fz248-knm-rospotrebnadzor.md`, `references/fz184-technical-regulation.md` — специальные сроки по предписаниям
- `references/citation-rules.md` — маркеры, размещение маркера у несущего реквизита
- `templates/agent-notes/case-context-template.md` — контекст дела в той же папке `workflow/<дело>/` (фактура и решения; сроки — здесь, в трекере)
