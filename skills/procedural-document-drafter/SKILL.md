# Procedural Document Drafter

Пути в примерах приведены для новых дел. Для существующих файлов и специальных проектов применять `references/workflow-layout.md`.

Архитектурный паттерн: sequential + domain-intelligence, High freedom — модель строит процессуальную позицию и проект документа, используя playbook и проверенные источники как отдельные источники истины.

## Назначение

Skill готовит проект процессуального или претензионного документа, фактическую хронологию, карту доказывания, аргументацию по flexible IRAC внутри жанровой структуры, оценку процессуальных рисков и чек-лист перед подачей.

## Принципы

1. Источники до позиции — `references/skill-shared-steps.md`. Норму подтверждать через `route_norm_verification(..., probe=true)` только по маршруту `usable_now: true`.
2. Методология — по reference-файлам: структура и проверки документа — `references/procedural-playbook.md`; общий метод аргумента и его связи с анализом — `references/procedural-argument-method.md`; краткие правила IRAC — `references/irac-rules.md`; цитирование — `references/citation-rules.md`.
3. Никаких «суды считают» без конкретных актов. Никаких выдуманных номеров дел.
4. Никаких признаний долга, нарушения, вины, обстоятельств без явного указания юриста.
5. Результат — черновик. Подача документа — за юристом.
6. **Финальный deliverable — сразу в .docx** (см. «Формат итогового черновика» ниже). Сопроводительная записка юристу — тоже **.docx** (документ для человека → правило CLAUDE.md «Формат результата»); `.md`-файлы допустимы лишь как техническая копия для работы агента, не как итоговый файл записки и не для самого документа.
7. Пресейв перед `workflow/` — `references/skill-shared-steps.md`.

## Когда использовать

- Нужно подготовить иск, отзыв, возражения, ходатайство, заявление, жалобу.
- Нужно подготовить возражения на отзыв ответчика (письменные пояснения) или возражения на ходатайство другой стороны.
- Нужно подготовить претензию или ответ на претензию.
- Нужно подготовить уведомление об одностороннем отказе от исполнения договора (письмо о расторжении) — в том числе совмещённое с требованием о возврате аванса (раздел 29 playbook).
- Нужно подготовить мировое соглашение.
- Нужно подготовить заявление о взыскании судебных расходов.
- Нужно подготовить документ по делу об административном правонарушении (объяснения, возражения на протокол, жалоба на постановление и т. п.).

## Когда не использовать

- Это ответ госоргану вне рамок дела в суде — `gov-response`. Туда же: ответ на представление, возражение на предостережение, сопроводительное письмо госоргану (разделы 19–21 playbook).
- Это работа с договором без претензионного / судебного компонента — соответствующий contract-skill.
- Это простая (не досудебная) претензия / деловое письмо контрагенту — `counterparty-letter` (см. развилку `references/procedural-playbook.md` 14.0).

## Подготовка входа

На вход часто приходят файлы: судебные акты (PDF — нередко **сканы** с штампами), постановления, претензии, протоколы. Критично — реквизиты и сноски. Порядок файла — `references/skill-shared-steps.md`, «Подготовка файла». Для скана со штампом или многоколоночного акта docling обязателен.

При цитировании из извлечённого документа — указывать реквизиты (суд, дата, номер дела) **из самого документа**, не из OCR-предположений. Если реквизит не распознан — `[ПРОВЕРИТЬ РЕКВИЗИТЫ]`.

## Алгоритм работы

0. **Контекст дела.** Если дело или контрагент опознаётся и в `workflow/` есть его папка — прочитать `case-context.md` (и `deadlines.yaml`, если есть) до выбора типа документа. Одна строка юристу. Правило — CLAUDE.md «Контекст дела». **Досье договора (первым).** Если документ основан на договоре — сначала `references/contract-dossier-usage.md`, «Шаг 0 в договорных skills»: найти досье в реестре или собрать его и работать по нему, а не разбирать договор заново. **Слой знаний дела (вторым).** Если в папке дела документов не меньше порога, а `_knowledge/index.md` нет (`python tools/case_intake/knowledge_gate.py "workflow/<дело>"` вернул `required`) — `skills/matter-knowledge/SKILL.md`, затем документ: фактура берётся из слоя, а не из памяти сессии; договор в слое дела не разбирается заново, он в досье.
1. Определить тип документа. **Если это претензия — определить статус: простая (неформальная) или досудебная** (`references/procedural-playbook.md` 14.0). Статус определяется из контекста (задача юриста, case-context, планируемый иск, обязательность досудебного порядка) и называется юристу одной строкой; **спрашивать — только когда из контекста он неясен** (решение юриста 2026-09-29). Досудебная → готовить здесь по полному сценарию независимо от простоты требования (фундамент будущего иска). **Простая (не досудебная) претензия → это письмо контрагенту, перенаправить в `skills/counterparty-letter/SKILL.md`, здесь не готовить.** При неоднозначности — трактовать как досудебную (безопасный дефолт). **Если документ заявляет отказ от исполнения договора (в т. ч. вместе с требованием о возврате аванса) — это не претензия, а уведомление о расторжении: раздел 29 playbook, развилка 14.0 не применяется.**
1a. **Позиция и глубина исследования.** Определить `research_stance` (`references/source-hierarchy.md`, «Настройка исследования»): юрист **назвал** норму/основания → `position_led` (поиск и обоснование идут по этим основаниям, но **объективно** — adverse-проход обязателен); **не назвал** → `neutral`, агент сам устанавливает применимое право и квалификацию. Право исследуется по «Workflow для правовых выводов» (`references/source-hierarchy.md`) **до** формирования позиции; **глубина — авто** (по очевидности вопроса и наличию аналогичных кейсов). Перед составлением текста — предпросмотр-гейт (одноимённый раздел ниже).
1b. **Проверенный опыт прошлых дел.** По типу спора, проблеме и стадии вызвать `search_verified_knowledge` (либо `legal_search` с `source_types=["internal"]`) и использовать только объекты с `verification.status: human_verified`. `practice_pattern` может дать evidence checklist, drafting-приём или риск, но не подтверждает норму и не заменяет проверку права. Candidates не использовать в документе; при необходимости контекста открыть связанную case study по provenance. Правила — `references/case-knowledge-layer.md`.
2. Определить процессуальный режим (АПК / ГПК / КАС / КоАП / претензионный).
2a. **Суд, подсудность и госпошлина** — для иска и административного иска, до составления текста, пройти `skills/court-jurisdiction-resolver/SKILL.md`. Пошлину не считать вручную. Суд, адрес, реквизиты и сумму перенести в шапку и в пункт чек-листа «госпошлина рассчитана». Для претензии, отзыва, ходатайства и документов по КоАП этот шаг не запускать.
2b. **Приказ или иск.** Для денежного требования о взыскании, до текста иска, пройти `references/procedural-playbook.md` раздел 22.0 (`references/procedural-playbook/22.md`). Иск не составлять, пока юрист не выберет заявление о выдаче судебного приказа или иск.
2c. **Смена жанра.** Если документ делается из другого документа юриста («заявление о приказе из иска rev 2», «отзыв из моих возражений») — до составления карта полей: каждый факт, реквизит, довод и приложение исходной версии юриста → перенесён / осознанно исключён (причина — юристу). Правки юриста переносятся по умолчанию, документ не пересобирается «коротко». Состав нового жанра сверяется с нормой содержательно: каждое требование нормы → что реально есть в файле (например, к заявлению о судебном приказе прикладывается расчёт взыскиваемой суммы — `references/procedural-playbook/22.md` 22.11). Правовые развилки жанра (что можно просить) — через базу, не по памяти.
3. Определить процессуальную стадию.
3a. **Решающие факты и достаточность требования** (до составления). (1) Если неизвестен факт, без которого нельзя сформулировать требование или его основание (нет договора или иного основания, нет доказательства исполнения нашей стороной, неизвестен надлежащий ответчик), — результат шага: адресный запрос документов юристу/бизнесу, а не документ на допущениях; продолжать на допущениях — только по явному указанию юриста. (2) **Достаточность требования:** если факты нашей стороны верны, достаточны ли они для заявленного последствия? Статус — полное / не хватает фактов / структурный порок / правовая неопределённость / неопределённость квалификации. Отсутствие утверждения о факте ≠ отсутствие доказательства: сначала проверить, заявлен ли факт вообще. Статус — в записку юристу (п. 2 минимума).
4. Собрать фактическую хронологию. **Для мультидок-дела с собранным структурным слоем — читать готовые `matter-timeline.yaml`/`matter-facts.yaml`** (`references/matter-model-usage.md`, «Проводка downstream»), а не пересобирать хронологию из исходников; слоя нет и на входе массив документов — предложить завести (факт отделяется от квалификации до формирования правовой позиции).
5. Сформировать карту доказывания (см. `procedural-playbook.md`); при наличии factual layer опираться на его факты/стороны/пробелы и производную evidence-map, не собирая фактуру заново. Глубокий анализ доказательств — по фактам, которые одновременно **существенны и спорны** (или не установлены); бесспорные и несущественные — строкой. По каждому существенному элементу: доказательство с **дословной цитатой и точным местом** (документ, страница/пункт), опровергающее доказательство рядом, состояние — подтверждено / частично / спорно / пробел / нужно истребовать. Ключевые документы дела (прежде всего поданный иск) держать открытыми и сверять текст с ними, а не с пересказом.
5a. **Документ оппонента** (для отзыва, возражений, объяснений, жалобы). Каждый довод оппонента до опровержения проходит тест существенности (`references/procedural-playbook/26.md` 26.2): изменит ли он исход, если верен? Класс — отрицание существенного факта / альтернативная версия / правовое несогласие / самостоятельное возражение / несущественная риторика. Несущественное не опровергается «за компанию», существенное не пропускается. С оппонентом не соглашаться однозначно («договоры могут не образовывать…», а не «не образуют») — квалификацию даёт суд; позицию оппонента излагать кратко, не обосновывать за него.
6. Сформировать аргументацию по `references/procedural-argument-method.md`. Верхнюю структуру задаёт жанр; каждый существенный аргумент строится conclusion-first по flexible IRAC. Ясное правило не раздувать практикой; для оценочного критерия добавить Rule Support; для competing line — сильный counterargument и честный response/distinction. Апелляционную/кассационную жалобу строить по error-based карте раздела 30, а не как повтор иска.
7. Оценить процессуальные риски (пропуск срока, признание, раскрытие, переквалификация).
7a. **Предпросмотр-гейт** (перед составлением): норма не задана (Case B) **или** заявленные юристом основания объективно слабы/рискованны (Case A) → показать юристу краткую предварительную правовую квалификацию (нормы + квалификация спора/требования + основания, со ссылками) и **ждать утверждения или доработки**; текст документа готовится только после этого. Основания заданы и объективно держатся → к составлению. Детали — раздел «Предпросмотр правовой квалификации» ниже.
7b. **Adversarial workflow — обязателен** для иска, отзыва, апелляционной/кассационной жалобы, возражений и объяснений по существу, документов по КоАП (решение юриста 2026-09-29); для претензии, в т. ч. досудебной, — по усмотрению, когда от неблагоприятной практики существенно зависит решение; **не** для формальных ходатайств и сопроводительных. Отдельный этап поиска практики **против** позиции с обязательным подтверждением юристом — детали раздела «Adversarial workflow» ниже. В записке — строка «adverse проведён / не проведён и почему».
8. Подготовить проект документа. Каждый существенный факт текста — из утверждённого состояния дела (материалы, case-context, matter-facts), а не выведен при составлении. Существенный раздел получает thesis-heading: вывод + главная причина, без повышения статуса спорного факта. Факт прослеживается до fact/evidence/source, правовой тезис — до authority/passage; открытый пробел остаётся видимым. Стиль — `references/house-style.md`, «Для суда»; обстоятельства излагаются через их правовую квалификацию, а не пересказом. Терминология — по словарю материалов дела (26.4): точное наименование стороны и процессуальная роль, без рабочих слов из постановки задачи («фабрика», «дилер», «бренд» → «Ответчик 2», «товарный знак …»). Не формулировать за суд и не повторять то, что уже заявлено (просительную часть иска — в объяснениях). Для значимого документа до рендера заполнить `procedural_argument.v1`, запустить `python tools/procedural_drafting/draft_check.py <manifest>` и передать финальную смысловую сверку substantive critic; `READY_FOR_RENDER` не снимает source/human/adverse gates. Короткое формальное ходатайство полного manifest не требует.
9. Сформировать перечень приложений. **Каждое приложение есть у нашей стороны** (в папке дела или в приложениях к ранее поданным документам); документ, которого у нас нет или который принадлежит оппоненту, не прикладывается — он идёт в записку как «запросить / истребовать» (ходатайство об истребовании — 13.2). При сомнении — вопрос юристу до сборки.
10. Подготовить чек-лист перед подачей / направлением.

## Предпросмотр правовой квалификации (гейт перед составлением)

**Переиспользование анализа дела (шаги 3a/5/5a/8).** Применить `references/case-structure-method.md`. Если в `workflow/<дело>/_llm/_analysis/case-analysis.yaml` есть `case_structure`, читать его вместе с `matter-positions.yaml`, фактами и источниками, сверить с новой стадией/материалами и решениями юриста; не восстанавливать всё с нуля. Действия получить через `python -m tools.case_analysis.structure --case "workflow/<дело>"`. Для v1 явно назвать непроверенный объём и дополнить нужную часть; малые документы не требуют полной persistent-модели. Существенный пробел подтверждения, противоречие источников или вопрос допустимости требуют оценки и без прямого возражения оппонента. Молчание не повышает статус факта. Условная истинность sufficiency не становится фактом текста; существенное утверждение связано с источником. Существующие предпросмотр, adverse-гейт и проверка источников сохраняются; Stage C дополнительно не запускать.

Процессуальный документ не готовится «вслепую», пока не согласована правовая основа. Развилка по `research_stance` (`references/source-hierarchy.md`, «Настройка исследования»):

- **Case A — юрист назвал норму/основания** (`position_led`). Поиск и обоснование идут по этим основаниям, но **объективно**: обязательный adverse-проход, проверка первоисточника, калибровка.
  - Основания **объективно держатся** → к составлению документа; слабые места, контраргументы и риски всё равно отражаются в записке юристу (пп. 4–5 обязательного минимума).
  - Основания **объективно слабые/рискованные** → **сначала предпросмотр** (как Case B): документ не составлять, пока юрист не подтвердит выбор основания или не даст другое. Расхождение по существу — `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]`.
- **Case B — норма не задана** (`neutral`). Сначала исследование, затем **краткий предпросмотр**, и лишь после утверждения — составление.

**Что показывается в предпросмотре** (кратко, без полного текста документа): применимые нормы со ссылками; правовая квалификация спора/требования (для КоАП — состав); основания требования/возражения; ключевая практика (реквизиты); слабые места и главный контраргумент; предполагаемый тип документа и просительная часть одной фразой; открытые вопросы и недостающие вводные. Глубина исследования под предпросмотр — авто.

**Цикл.** Юрист **утверждает** → переход к составлению (шаг 8). Юрист **возвращает на доработку** → уточнить квалификацию/основания и показать предпросмотр повторно. Аналог в заключениях — Synthesis-checkpoint (`references/legal-opinion-method.md`, §7); здесь он адаптирован под процессуальный документ и по умолчанию **включён**, когда норму не задал юрист.

Предпросмотр — внутренний рабочий обмен с юристом (может быть кратким текстом в чате). Сам документ по-прежнему собирается **сразу в `.docx`** после утверждения.

## Adversarial workflow (шаг 7b)

Форматы двух этапов — `references/adverse-review.md`. Целенаправленный поиск практики **против** позиции — до финализации документа. Обычный поиск практики по теме этого не заменяет: запросы формулируются на поиск **сильнейшей практики против**, а не на подтверждение уже выбранной позиции.

**Диспетчеризация субагентов — `references/legal-opinion-subagents.md`, раздел «Использование в procedural-document-drafter».** Новых субагентов под процессуальные документы не заводится: переиспользуются те же `adversarial-researcher` / `source-verifier` / `consistency-checker` (решение 2026-09-08). В раннерах без этих субагентов (Codex, Cursor) те же этапы выполняются in-context — человеческий гейт при этом сохраняется.

**Последовательность (порядок этапов — часть архитектуры):**

1. **Adverse Case Search** — субагент `adversarial-researcher` (применяет методологию подбора практики `references/case-law-search.md`: гипотезы, authority-лестница, ВАС survival, статус практики). Вход: факты + правовой вопрос + разрешённые источники, **без** нашего предварительного вывода и **без** проекта документа. Ищет: конкурирующую квалификацию, отказ в аналогичных требованиях, процессуальные проблемы, отсутствие нужного доказательства, сильнейшие возражения оппонента.
2. **Adverse Case Pool** — найденные решения разбираются по `references/court-decision-analysis.md` (узкий тезис, отличия фактов от нашего дела, основания для distinguishing, locator на фрагмент). Начальный статус каждой карточки — `UNVERIFIED`.
3. **⛔ Гейт юриста — обязательный.** Пул предъявляется юристу до любого использования: по каждой карточке он подтверждает (`VERIFIED_RELEVANT`), отклоняет (`VERIFIED_NOT_RELEVANT`), отмечает отличия (`VERIFIED_DISTINGUISHABLE`) или бракует источник (`REJECTED_SOURCE`). **Агент не переводит карточку в `VERIFIED_*` сам.** Дальше идут только `VERIFIED_RELEVANT` и `VERIFIED_DISTINGUISHABLE`.
4. **Синтез позиции оппонента (steelman)** — на подтверждённом пуле: альтернативная квалификация, конкурирующее толкование нормы, фактические и процессуальные слабости, проблемы доказательств, аргументы против выбранного способа защиты. Требование: **лучшая разумная версия** позиции оппонента, а не удобная для опровержения слабая.
5. **Атака на нашу позицию — отдельный этап**, не тот же вызов. Вход: наш проект документа + подтверждённый пул + синтезированная позиция оппонента. Проверить по четырём осям: **факты** (что предполагаем, но не доказали; что толкуется иначе; какие документы противоречат нашей версии), **право** (альтернативные толкования, применимость неблагоприятной практики, правильность выбранного способа защиты, пропущенные специальные нормы), **доказательства** (чем подтверждён каждый тезис, пробелы, допустимость/относимость, что оппонент атакует), **процесс** (подсудность, сроки, бремя доказывания, необходимые ходатайства).
6. **Evidence/Proposition Matrix** — для значимых документов: `наш тезис → норма → судебная практика → доказательство → контраргумент → неблагоприятная практика → статус`. Цель — исключить ситуацию, когда в документе есть юридически значимое утверждение, но непонятно, на чём оно основано, чем доказано и чем может быть опровергнуто.
7. **Классификация замечаний**: **Critical** (способно изменить исход дела) / **Significant** (существенный недостаток позиции или доказательной базы) / **Minor** (улучшение аргументации). По каждому существенному — указать, что требуется: правка документа / доп. поиск / доп. доказательство / решение юриста.

**Почему этапы 1/4 и 5 разделены.** Первый строит качественный adversarial input в изоляции (агент не видит наш текст и не подгоняет критику под готовый ответ); второй применяет готовую позицию оппонента к нашим тезисам и доказательствам. Слияние в один проход «найди недостатки» — не полноценный критический анализ.

**Куда попадает результат:** пул, позиция оппонента, матрица и классификация замечаний — в записку юристу (`.docx`, пп. 4–5 обязательного минимума); правки текста — точечные, каждая существенная требует подтверждения юриста. Документ не сохраняется, пока не встроены отчёты всех запущенных субагентов (`references/legal-opinion-subagents.md`, «Диспетчеризация»).

**Решения юриста по пулу — в обучение.** После гейта зафиксировать в case-context (раздел решений): какие карточки юрист признал релевантными, какие отклонил и почему, какие distinguishing принял. Это материал для улучшения поиска практики, а не правка скилла в рамках дела.

## Обязательный минимум записки юристу

Вместо фиксированных 12 секций (решение юриста 2026-09-29): записка содержит то, что юрист использует; заголовки и порядок — по документу, пустые пункты не заполняются ради формы. Записка — `.docx`, отдельно от самого документа. Для иска, отзыва, жалобы, возражений, документов по КоАП и досудебной претензии в ней обязательно есть:

1. **Пробелы вводных** — каких документов, фактов, реквизитов не хватает; адресно: кто, что, у кого запрашивает.
2. **Достаточность требования** (шаг 3a) — статус и что его снижает.
3. **Карта доказывания** по существенным фактическим спорам и иным существенным доказательственным проблемам (шаг 5): элемент → факт → бремя → доказательство с цитатой и местом → опровергающее доказательство → состояние. Пробел подтверждения, противоречие источников или вопрос допустимости отражаются и при unknown/agreed позиции оппонента; точный fact_status и непроверенный источник не скрываются.
4. **Позиция оппонента и неблагоприятная практика** — существенные доводы и что с ними сделано; «adverse проведён / не проведён и почему»; при 7b — пул, позиция оппонента, матрица, Critical/Significant/Minor.
5. **Риски** — рискованные утверждения в тексте (что юристу пересмотреть) и применимые процессуальные риски: пропуск срока, признание долга / нарушения / вины / обстоятельств, переквалификация, отказ в обеспечении, встречный иск, раскрытие лишнего.
6. **Нормы и практика** — что проверено по маршруту `usable_now: true`, что под маркером; находки, не годные для текста (например, арбитражная практика по аналогии для суда общей юрисдикции), — здесь, а не в документе.
7. **Приложения** — каждое: есть у нашей стороны / запросить / истребовать (шаг 9).
8. **Чек-лист перед подачей / направлением** — применимые пункты: срок не пропущен; расчёт цены иска / суммы требований приложен; госпошлина рассчитана по шагу 2a (не вручную); доказательства приложены и упорядочены; полномочия проверены; порядок направления другой стороне соблюдён; досудебный порядок подтверждён; риск признания / раскрытия проверен; финальная проверка юриста.

Для досудебной претензии из п. 8 исключаются элементы подачи иска (госпошлина, цена иска, доверенность); дисциплина доказывания и рисков сохраняется. **Простая (не досудебная) претензия здесь не готовится** — `skills/counterparty-letter/SKILL.md` (шаг 1, `references/procedural-playbook.md` 14.0).

**Сам документ** (`.docx`) содержит то, что требует процессуальный режим: шапку и реквизиты суда / органа / адресата (кегль шапки = кегль основного текста), стороны и реквизиты, цену иска (если применимо), описание спора, существенные аргументы по flexible IRAC, просительную часть («Прошу суд»), перечень приложений, подпись. Собирается через `ProceduralDoc` (`tools/docx_style/profiles.py`, профиль — `references/document-formatting.md` §1–2), не самописной вёрсткой.

- замена штрафа предупреждением (ст. 4.1.1 КоАП РФ);

## Формат итогового черновика

**Правило**: финальный документ, который пойдёт юристу на проверку и потом адресату, готовится **сразу в .docx**. Промежуточная стадия «текст в .md → потом конвертация в .docx» — **исключена**: это лишний шаг, который вынуждает пользователя:
- копировать текст из .md в Word и форматировать вручную;
- терять структурные элементы (нумерация параграфов с висячим отступом, таблицы, полужирные подзаголовки, шапка с правым выравниванием);
- сверять две версии при правках.

**Структура работы**:

1. **Анализ + сопроводительная заметка для юриста** — `.docx` (применимые клаузы, маркеры, риски, стратегические комментарии). Это **внутренний документ**, для юриста, не для адресата, но всё равно документ для человека → по правилу CLAUDE.md «Формат результата» отдаётся в `.docx` (`.md`-копия — только техническая).
2. **Сам документ** — `.docx`, готовый к редактированию и отправке (как при работе с пользовательскими шаблонами).

**Технические правила генерации .docx** — см. `references/docx-generation.md`.

**Когда допустимо начинать с .md**:
- запрос пользователя на «черновой текст» / «набросок логики» / «план структуры» — без указания формата итогового deliverable;
- очень короткий документ, для которого .docx — избыточен (например, формула, цитата, перевод одного абзаца).

Во всех остальных случаях — **сразу .docx**.

## Документы по образцу (формальные ходатайства, заявления, уведомления, сопроводительные)

Если задача — подготовить документ по переданному образцу (типовое ходатайство об оплате штрафа, заявление о приобщении доказательств, сопроводительное письмо, уведомление о платеже и т. п.) — **обязательно** использовать `references/template-filling-rules.md` и `templates/sample-prep/field-mapping-template.md`.

Ключевые правила:

1. Различать **форму** (структура + стандартные формулировки — наследуется) и **объективные данные** (адресат, заявитель, реквизиты, номера, суммы, даты — всегда сверяются с первоисточником, даже если совпадают с образцом).
2. До любой подстановки — заполнить карту полей по `templates/sample-prep/field-mapping-template.md`: для каждого объективного поля указать первоисточник и извлечённое значение.
3. Не наследовать поля из образца автоматически. Случайное совпадение значений (один и тот же суд, одно и то же лицо в нескольких документах) не отменяет сверку.
4. При пересечении поля в нескольких источниках (например, УИН в постановлении и в квитанции) — сверять значения. Несовпадение — стоп-сигнал, маркер `[ПРОВЕРИТЬ СООТВЕТСТВИЕ ИСТОЧНИКОВ]`.
5. При генерации серии документов по одному образцу — каждый документ заполняется по **своему** первоисточнику. После генерации проверить, что поля не перетекли между документами серии.
6. Готовый результат сопровождается картой полей.

Маркеры:
- `[СВЕРИТЬ С ПЕРВОИСТОЧНИКОМ]` — поле требует проверки первоисточника, даже если подставлено;
- `[ПРОВЕРИТЬ СООТВЕТСТВИЕ ИСТОЧНИКОВ]` — поле есть в нескольких источниках, сверка не доведена до конца.

## Поиск информации

При подготовке процессуальных документов часто требуется веб-поиск: судебная практика по аналогичной категории (kad.arbitr.ru, ras.arbitr.ru, vsrf.ru), актуальная редакция нормы (pravo.gov.ru), проверка контрагента / истца / ответчика, разъяснения госорганов.

**Проверка реквизитов сторон — обязательный шаг перед формированием шапки иска / претензии / отзыва / ходатайства.** Подключать `skills/counterparty-check/SKILL.md` (DaData MCP) по ИНН/ОГРН каждой стороны: подтвердить, что юрлицо действующее (для ответчика — критично: если ликвидировано до подачи иска, иск возвращается); получить актуальный адрес для направления (особенно для претензии — отправка не по адресу из ЕГРЮЛ может быть оспорена); зафиксировать руководителя на дату подачи. Глубокие проверки — банкротство ([bankrot.fedresurs.ru](https://bankrot.fedresurs.ru/), особенно для оценки целесообразности иска), РНП, ФССП, kad.arbitr.ru — через `references/web-research-tools.md` раздел 3.3.

Использовать инструменты по `references/web-research-tools.md` (agent-browser для kad.arbitr.ru и форм; Tavily /search для актов и аналитики с фильтром по официальным доменам; WebFetch для прямых URL судебных актов).

Закрытие поиска — `references/skill-shared-steps.md`.

## Что запрещено

- **Не выдавать рассчитанную дату истечения процессуального срока как установленную.** Конкретную дату можно приводить только когда одновременно: дата начала течения подтверждена документом-первоисточником; порядок исчисления (рабочие/календарные дни, момент получения/вручения) проверен по норме; перенос окончания с нерабочего дня учтён. Во всех остальных случаях — привести норму и порядок исчисления, а вместо даты поставить `[ПРОВЕРИТЬ СРОК]`.
- Признавать долг / нарушение / вину / обстоятельства без явного указания юриста.
- Выдумывать номера дел, постановления Пленума, цитаты, реквизиты.
- Использовать аналитические статьи как замену судебных актов.
- Маркировать документ как «готовый к подаче».
- Включать суммы и расчёты без подтверждения.
- Раскрывать сведения, не относящиеся к спору.
