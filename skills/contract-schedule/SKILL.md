# Contract Schedule

Архитектурный паттерн: **domain-intelligence + low freedom** — модель извлекает обязательства из договора, детерминированное ядро `tools/contract_schedule/` считает даты и рисует файл. Модель не считает даты; скрипт не толкует договор.

## Назначение

По заполненному договору (файл или скан) построить .xlsx-график всех договорных сроков: что, кто, когда, от какого события, с дословной формулировкой срока и статусом каждой даты.

## Принципы

1. **Даты в графике — операционная проекция, а не исчисление срока.** Всё, кроме дат, взятых из договора дословно (`fixed`), выходит с `[ПРОВЕРИТЬ СРОК]`. Исчисление подтверждает юрист.
2. **`term_verbatim` заполняется всегда** — дословная формулировка из договора рядом с расчётной датой. Если расчёт неверен, юрист видит исходник, не открывая договор.
3. **Не выдумывать опорные события.** Непонятно, от чего течёт срок → `anchor: null`, строка выходит как `not_computed` с маркером. Правильный отказ — не ошибка.
4. **Опорные даты задаёт юрист** через `--anchor`. Модель не берёт дату подписания из текста скана самостоятельно.
5. **Календарь — данные, а не память модели.** Для года в диапазоне 2015–2100 движок считает рабочие дни сам по ст. 112 ТК РФ; если год подтверждён юристом в `holidays_ru.yaml` (сейчас 2026), используются именно эти данные с переносами. Год вне диапазона генератора без подтверждения в файле → расчёт отклоняется, восстанавливать праздники по памяти нельзя.
6. **Чувствительный договор — через обезличивание** (`tools/pre_anonymize/`, профиль `analytic`): маскирует стороны и реквизиты, оставляет суммы и даты, которые графику нужны.
7. **Результат — в `workflow/`** по общему правилу проекта.

## Порядок работы

1. **Ингестия** — через `tools/doc_ingest/router.py`. Скан — читать зрением в сессии. Протокол: `references/document-ingestion.md`. **Досье договора.** Если задача касается конкретного договора — сначала `references/contract-dossier-usage.md`, «Шаг 0 в договорных skills»: найти досье в реестре или собрать его и работать по нему, а не разбирать договор заново. Если досье договора есть, сроки и обязательства берутся из `current` и `_text/` досье, карточка — навигация; ингест не повторяется.
2. **Извлечение** — построить JSON по `tools/contract_schedule/schema.md`: по одному объекту на каждое обязательство со сроком. Обойти договор целиком, включая приложения и спецификации.
3. **Опорные даты** — спросить у юриста, если не заданы: дата подписания и фактические даты уже наступивших событий (аванс, поставка, приёмка).
4. **Сборка**:

   ```
   python -m tools.contract_schedule.schedule build --in obligations.json \
     --out "workflow/<договор>/график.xlsx" \
     --anchor contract_signing=YYYY-MM-DD [--anchor ...] \
     --title "<договор>" [--contract-end YYYY-MM-DD]
   ```

5. **Отчёт юристу** — практическим итогом: сколько обязательств, сколько дат требует проверки, какие нестыковки нашлись. Служебный вывод скрипта не пересказывать целиком.

## Что запрещено

- Выдумывать сроки, опорные события и суммы, которых нет в договоре.
- Заполнять `START`/`END` вручную в обход скрипта.
- Считать график юридическим заключением о сроках или основанием для действий по договору.
- Помечать результат готовым к использованию без проверки юристом.

## Связанные файлы

- `tools/contract_schedule/schema.md` — схема JSON обязательства
- `tools/contract_schedule/holidays_ru.yaml` — производственный календарь (подтверждённые юристом годы; движок сам генерирует остальные годы 2015–2100 по ст. 112 ТК)
- `skills/deadline-tracker/SKILL.md` — смежный skill: контроль сроков по делу между сессиями
- `references/document-ingestion.md` — протокол подготовки документов
- `references/citation-rules.md` — маркеры неполноты
