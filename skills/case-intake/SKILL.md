# Разбор входящих документов (case-intake)

Архитектурный паттерн: sequential + context-aware, mixed freedom — классификацию неоднозначных документов выполняет модель, а создание структуры дела и служебных файлов делегируется `tools/case_intake/`.

## Назначение

Довести до готовности то, что watcher уже подготовил: определить тип документа, разложить по делам, завести хронологию и сказать юристу, что пришло. Конвейер и границы классов — `references/execution-profiles.md`.

## Принципы

1. **Ничего не финализировать.** Раскладка — не подготовка документа. Юрист сам решает, что делать дальше; skill только предлагает следующий шаг.
2. **При сомнении — спросить юриста, а не молча в `unsorted/`.** Эскалация классификатора (`UNCERTAIN`/`INSUFFICIENT_CONTEXT`), низкая уверенность, низкое доверие OCR, ворох неясных фото, неопределимое имя дела/третьего лица — становятся **пунктами уточнения** (одним блоком). В `unsorted/` уходит только явно отложенное юристом. Уточнение — про раскладку, не про квалификацию (спрашиваем «что это за пачка / приложение к иску или отзыву», не «какова перспектива»).
3. **Правовых выводов на этом этапе нет.** Тип документа — это классификация, а не квалификация правоотношения. Никаких оценок перспектив, никаких маркеров неполноты от классификатора.
4. **Карточку дела юриста не переписывать.** Существующий `case-context.md` не изменяется автоматически; создаётся только если его нет.
5. **Реквизиты — как в тексте.** Классификатор не нормализует наименования и номера; сверка с реестрами — отдельная задача (`counterparty-check`).
6. **Расхождение — сигнал, а не помеха.** Если номер дела от классификатора не совпал с найденным regex-ом, документ идёт в `unsorted/` с указанием обоих значений.

## Алгоритм

### Шаг 1 — Собрать очередь

Прочитать `workflow/_claims/queue/*.json`. Пусто — сказать «новых документов нет» и остановиться. Если очередь пуста, но в канале лежат файлы — сначала прогнать watcher: `python tools/case_intake/watcher.py --once`.

### Шаг 1а — Дочитать то, что не смог OCR

Карточка с `needs_vision_read: true` означает: Tesseract выдал мусор (рукопись, плохой скан), `text_head` классификатору бесполезен. До шага 2:

1. `python tools/case_intake/vision_read.py render <карточка>` — страницы в PNG во временную папку (путь в выводе).
2. Прочитать страницы своей моделью и записать расшифровку в `.txt` в той же временной папке. Расшифровка близко к тексту, без пересказа и без додумывания: неразборчивое — `[неразборчиво]`, сомнительное слово, цифра или реквизит — с `?`. Штампы и пометки (вх. №, дата регистрации) — отдельной строкой.
3. `python tools/case_intake/vision_read.py apply <карточка> <расшифровка.txt> --cleanup <папка render>` — расшифровка становится `text_head` (исходный OCR остаётся в `ocr_text_head`), временные PNG удаляются.

Читать картинку моделью разрешено только для карточек с флагом и только моделью рабочей сессии; для `workflow/_anonymizer/` — никогда (исключение и его границы — `references/ocr-setup.md`). Если страница не читается и глазами — не гадать: пункт уточнения юристу (принцип 2). В отчёте шага 4 отметить, что текст дочитан по изображению и реквизиты нужно сверить со сканом.

### Шаг 2 — Классифицировать (класс B, субагент)

По каждой карточке вызвать субагента `intake-classifier`, передав **только**: имя файла, `text_head` из карточки и задачу `document_intake`. Не передавать контекст дела, соседние документы и свои предположения — дисциплина входа класса B (`references/execution-profiles.md` §5).

При нескольких документах вызывать субагентов **параллельно** — задачи независимы.

Полученный JSON вписать в поле `classification` карточки (перезаписать файл карточки).

### Шаг 2а — Диагностика «что за дело» (до раскладки)

По всей пачке (из карточек: `text_head` + `case_numbers` + результаты классификатора) синтезировать и показать юристу **до** раскладки:
- номер(а) дела и форум/инстанция — насколько определимо;
- стороны и **кто есть кто** (истец/ответчик/третьи лица; спорное — с пометкой `[ПРОВЕРИТЬ ФАКТ]`);
- **инвентарь** пачки: сколько файлов и чего («1 иск, 2 судебных акта, 3 ходатайства, 40 фото неясного назначения, 5 нераспознанных сканов»);
- открытые вопросы (что уточнить перед раскладкой).

Это класс C (синтез), правовых выводов не делает. Дальше — раскладка по подтверждённому.

### Шаг 3 — Разложить (класс A, код)

По каждой карточке:

```bash
python tools/case_intake/bootstrap.py workflow/_claims/queue/<файл>.json
```

Скрипт (класс A) создаёт папку дела по конвенции `ГГГГ.ММ.ДД CLAIM/GOV <имя>` (для новых дел; существующие подбирает по frontmatter), раскладывает документ в **ролевую подпапку** (`core.role_folder`: иск→`Иск_приложения/`, отзыв/возражения/объяснение→`*_приложения/`, ходатайство→`Ходатайства/`, судебные акты→`Судебные акты/`, экспертиза→`Экспертиза_<имя>/`, третье лицо→`Третье_лицо_<имя>/`, прочее и `иное`→корень), **переименовывает копию** в `ГГГГ-ММ-ДД <Тип> <сторона>.ext`, заводит `case-context.md` при отсутствии и вносит событие в `matter-timeline.yaml`. В отчёте — `case_subfolder`. Карточка очереди (извлечённый текст `text_head`, классификация, OCR-метаданные) не удаляется: она переезжает в `workflow/<дело>/_knowledge/intake/<имя документа>.intake.json` с полем `placed_as`, а для `unsorted/` — рядом с файлом. `Доказательства/` и `Проекты/` приём не наполняет (доказательства переносит юрист/уточнение; `Проекты/` — drafting-skills).

### Шаг 4 — Отчитаться юристу

По одной строке на документ, без служебного JSON:

```
Иск ООО «Альфа» → дело А40-12345-2025 (папка заведена). Предлагаю: procedural-document-drafter
Ответ Роспотребнадзора → дело ООО-Бета. Предлагаю: gov-response
Скан без реквизитов → unsorted (нечитаемый текст, эскалация классификатора)
```

В конце — сводка: сколько разложено, сколько в `unsorted/` и что с ними делать. Если заведены новые папки дел — сказать явно, чтобы юрист проверил названия.

### Шаг 5 — Слой знаний (обязателен по порогу)

Если в отчёте раскладки `knowledge_layer: required` (в деле не меньше порога документов, `_knowledge/index.md` нет; порог — `tools/case_intake/knowledge_gate.py`), в той же сессии выполнить `skills/matter-knowledge/SKILL.md`: только фактура, правовых выводов нет, разрешения юриста не требуется. Задачу приёма `queue_cli complete` по такому делу не закроет (код возврата 2), пока слоя нет. Пропуск — только по указанию юриста: `--skip-knowledge-gate "причина"`, причина пишется в задачу.

Если дело из 1–2 документов (одна входящая претензия, один иск) — кроме drafting-skill предложить и **оценку**: `case-analysis` по упрощённому пути (перспективы, позиция). Цель канала `_claims` включает предварительную оценку, а не только раскладку; выбор — за юристом.

## Что запрещено

- Готовить, дополнять или отправлять документы на этом шаге.
- Переводить документ в дело при эскалации или низкой уверенности «чтобы не висел».
- Редактировать существующий `case-context.md` или чужие события хронологии.
- Читать оригиналы из `processed/` целиком ради «лучшей» классификации — если `text_head` не хватило, это `INSUFFICIENT_CONTEXT` и решение юриста. Исключение — карточки с `needs_vision_read` (шаг 1а): там оригинал читается по изображению, потому что текста нет вовсе.
- Делать выводы о перспективах дела, сроках и рисках — для этого есть профильные skills.

## Связанные файлы

- `references/execution-profiles.md` — классы исполнения, дисциплина входа, протокол эскалации.
- `.claude/agents/intake-classifier.md` — субагент класса B.
- `tools/case_intake/` — `watcher.py` (подготовка очереди), `bootstrap.py` (раскладка), `core.py` (разбор номеров, маршрутизация, safety), `vision_read.py` (дочитывание сканов, с которыми не справился OCR).
- `references/ocr-setup.md` — локальный OCR и исключение для дочитывания моделью.
- `workflow/README.md` — описание канала приёма для юриста.
- `references/matter-model-usage.md` — правила хронологии дела.
- `templates/agent-notes/case-context-template.md` — полный шаблон карточки дела (конвейер создаёт сокращённую).
