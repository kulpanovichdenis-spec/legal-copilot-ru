# Trademark Search (Pre-Filing Screening)

Архитектурный паттерн: sequential + multi-MCP + domain-intelligence, High freedom — инструменты собирают результаты поиска, а модель анализирует сходство и риск по методике без подстановки отсутствующих данных.

## Назначение

Skill готовит **методический отчёт о проверке** обозначения на риск отказа в регистрации в качестве товарного знака по п. 6 ст. 1483 ГК РФ (тождество / сходство до степени смешения с ранее зарегистрированными ТЗ для однородных товаров).

Применяется на стадии **выбора названия / pre-filing screening** — до подачи заявки в Роспатент.

**Поиск выполняется самим skill-ом** через:
- `agent-browser` (Vercel Labs) — для form-driven сайтов (linkmark.ru, WIPO GBD);
- `Tavily API` — для extract карточек Madrid Monitor по IR-номерам и для фонового `/search` по общеизвестным ТЗ.

Ручной режим — fallback при недоступности инструментов.

Все детали технологии — в `references/trademark-search-automation.md`. Методология (критерии сходства, классы МКТУ, шаблон отчёта) — в `references/trademark-similarity-search.md`.

## Что готовит skill

1. План поисковых запросов (варианты обозначения, классы МКТУ, юрисдикции);
2. **Автоматическое выполнение** поиска по базам (Роспатент — первичная РФ, linkmark.ru, WIPO GBD, WIPO Madrid Monitor);
3. Список потенциальных противопоставлений по результатам поиска;
4. Анализ каждого противопоставления по **4 критериям сходства**;
5. Оценку однородности товаров и услуг;
6. Совокупный уровень риска для каждого противопоставления;
7. Итоговую рекомендацию (подавать / подавать с уточнениями / не подавать / доработать);
8. **Журнал автоматизации** (что вызывалось, какие persistent URL-ы, сколько credits израсходовано);
9. Заметку для юриста и патентного поверенного.

## Принципы

1. **Методология** — по `references/trademark-similarity-search.md`; **техника автоматизации** — по `references/trademark-search-automation.md`.
2. **Verification-first (обязательный первый шаг).** До вывода и сохранения отчёта выполнить existence-check ссылок, затем отдельно раскрыть нормы через `route_norm_verification(jurisdiction="RU", probe=true)` только у provider с `usable_now: true`; сверить действующую редакцию МКТУ. Не подтверждено — маркер, а не догадка. Детали — CLAUDE.md «Финальная валидация перед сохранением».
3. **Никакой категоричности.** Финал — за патентным поверенным и Роспатентом. Skill готовит **рекомендацию**, не **заключение**; при неопределённости ставит маркеры. Совокупный риск — по `references/risk-scale.md` с ТЗ-поправками.
4. **Никаких выдуманных** номеров регистраций, дат, классов, правообладателей. ТЗ не найден — так и пишется; инструмент не отработал — фиксируется, никаких подставленных данных.
5. **Базы поиска.** Первичная РФ — официальная поисковая платформа Роспатента `searchplatform.rospatent.gov.ru/trademarks` (ТЗ РФ + общеизвестные ТЗ РФ + международные ТЗ; встроенные фонетика/семантика/нечёткий поиск); `linkmark.ru` — кросс-проверка и удобный агрегатор; WIPO Global Brand Database — международный фронт; WIPO Madrid Monitor — карточки IR. Иные базы — по запросу юриста.
6. **Результат — `.docx` в `workflow/`** (human review, черновик), оформление и сборка — `references/document-formatting.md` + `references/docx-generation.md`. Технический журнал автоматизации, сырые ответы и скриншоты — в `logs/trademark-search/{дата}-{обозначение}/` (материал для агента и проверяемости, не deliverable).
7. **Конфиденциальность**: предполагаемые наименования товарных знаков **не считаются существенными данными** (юридическое решение проекта) — публичный поиск допустим без дополнительных мер.

## Когда использовать

Триггеры:
- «проверь товарный знак», «свободно ли название», «не зарегистрирован ли уже», «pre-filing», «trademark check», «trademark clearance»;
- регистрация нового БАД / ЛП / косметики / медицинского изделия — для проверки названия;
- выбор названия для новой линейки продуктов;
- получение уведомления Роспатента о схожих знаках — для предварительного анализа;
- проверка названия конкурента / нового бренда на возможность возражения.

## Когда не использовать

- Защита в споре по уже поданной заявке (там — `procedural-document-drafter` + правовая база `trademark-similarity-search.md`);
- Полное FTO-исследование с официальным заключением (за пределами skill — у патентного поверенного);
- Регистрация НМПТ, географических указаний, фирменных наименований, коммерческих обозначений (требуют отдельной методики);
- Анализ договоров на использование / отчуждение ТЗ (там — `contract-review`);
- Защита против нарушения прав на уже зарегистрированный ТЗ (там — `procedural-document-drafter` для иска / претензии).

## Инструменты автоматизации

| Инструмент | Когда |

| `agent-browser --headed --session linkmark` | linkmark.ru — кросс-проверка и агрегатор ТЗ РФ (локально; сервер пока не хостит agent-browser — см. BL-015) |

| `mcp__legal-overlay__tavily_search` | Общеизвестные ТЗ, отраслевой фон (включая `include_domains`) — локальный Overlay вызывает Tavily напрямую |
| `mcp__legal-overlay__tavily_research` → `tavily_get_research` | Асинхронный качественный синтез по бренду (по запросу юриста); создать задачу и опрашивать результат по `request_id` |

**Перед началом поиска** skill обязан:
1. Проверить доступность `agent-browser --version` (нужен для linkmark.ru/WIPO GBD — локально);
2. Проверить `overlay_status`: provider `tavily` должен быть `configured_not_probed` или `connected`; холостой API-вызов не делать, поскольку он расходует credits;
3. Согласовать с юристом план поиска;
4. Если инструменты недоступны — предупредить и предложить fallback.

## Алгоритм работы

### Шаг 1 — Сбор вводных

**Прогрессивный поиск прошлого опыта (в начале).** Если обозначение / продукт / линейка / заявитель уже проходили работу — послойно и дёшево проверить `workflow/`: имена папок → frontmatter их `case-context.md` → при совпадении прочитать `case-context.md` найденного дела (прошлые проверки того же бренда, выбранная стратегия, отклонённые варианты, ранее найденные противопоставления). О связи с прошлым делом — одна строка юристу. Опыт ≠ правовое основание: право проверяется обычным циклом. Правило — CLAUDE.md «Контекст дела (case-context)».

Получить или запросить у юриста:
- **обозначение** (одно или несколько вариантов);
- **тип знака**: словесный / изобразительный / комбинированный / объёмный / иной;
- **классы МКТУ** для регистрации (или попросить юриста определить — типично для БАД-компании 5, 3, 30, 35, 44);
- **юрисдикции**: РФ обязательно; Мадрид / ЕС / США / Китай — по запросу;
- **заявитель**: своя компания или клиент;
- **контекст**: для какого продукта / линейки;
- **цель проверки**: screening / спор / коммерческий выбор.

При недостатке вводных — задать **точные вопросы** юристу. Не делать предположений.

### Шаг 2 — Подготовка вариантов обозначения

Сформировать **5–10 формулировок** для поиска:

- точное написание;
- варианты с кириллицей и латиницей (Аквамарин / Aquamarine);
- морфологические варианты ([БРЕНД] / Ломарелл / Ломарела);
- фонетические варианты (б-п, з-с, у-ю, и-ы);
- разбивка / слитное написание (Лома Рель / ЛомаРель / [БРЕНД]);
- сокращения и расширения.

### Шаг 3 — Проверка доступности инструментов

```powershell
agent-browser --version          # → версия или ошибка (нужен для linkmark.ru/WIPO GBD)
# Tavily /search, /extract и async /research — через локальный Overlay (`legal-overlay`).
# overlay_status не тратит API credits и показывает configured_not_probed до первого рабочего вызова.
```

Если что-то недоступно — пометить fallback-вариант и предупредить юриста.

### Шаг 4 — Автоматическое выполнение поиска

**Skill сам выполняет поиск** по протоколам из `references/trademark-search-automation.md`:

#### 4.1 Официальная платформа Роспатента (agent-browser) — первичная база РФ

`searchplatform.rospatent.gov.ru/trademarks` — официальный первоисточник Роспатента (Приоритет 1): **ТЗ РФ**, **общеизвестные ТЗ РФ** (ст. 1508 ГК РФ — частично закрывает `[ПРОВЕРИТЬ ОБЩЕИЗВЕСТНОСТЬ]`) и **международные ТЗ**, со встроенными **фонетическим / семантическим / нечётким** поиском (то, чего нет в linkmark). Логин для базового поиска не требуется (подтверждено 2026-09-02). SPA — только `agent-browser`, Tavily не подходит.

Для основного варианта обозначения:
1. Вкладка **ТЗ РФ**, тип **Словесный**; режим **Фонетический**/**Семантический** + **Частичное сходство (нечёткий поиск)** — один запрос заменяет ручные фонетические вариации;
2. Прогнать основной вариант; при узкой выдаче — точные варианты;
3. Отдельно проверить вкладку **Общеизвестные ТЗ РФ**;
4. Сохранить persistent URL выдачи; распарсить результаты (номер, класс МКТУ, правообладатель, дата приоритета/регистрации, статус);
5. Пошаговый селекторный протокол (`@ref`, вкладки, URL-схема выдачи) — `references/trademark-search-automation.md` §4a. Селекторы **требуют live-recon** перед первым боевым прогоном (SPA, вёрстка не зафиксирована) — до этого шаг помечается `[ТРЕБУЕТСЯ LIVE-RECON СЕЛЕКТОРОВ]`, результаты не выдумываются.

#### 4.2 linkmark.ru (agent-browser) — кросс-проверка и агрегатор

Для каждого варианта обозначения:
1. `agent-browser --headed --session linkmark open https://linkmark.ru/`;
2. `snapshot` → найти @ref поля поиска по подписи `"Поиск товарных знаков, НМПТ и заявок"`;
3. `fill @ref "{вариант}"`;
4. `snapshot` → найти @ref кнопки `"Найти"`;
5. `click @ref`;
6. `wait 3000`;
7. `eval "window.location.href"` → сохранить persistent URL результата;
8. `snapshot` → распарсить результаты (top-30) по разделителю `rowheader "Свидетельство:"`;
9. Для топ-3 близких — открыть карточку (клик на номер ТЗ), `snapshot` оверлея, закрыть оверлей.

#### 4.3 WIPO GBD Similar Name Search (agent-browser)

1. `agent-browser --headed --session wipo-gbd open https://branddb.wipo.int/branddb/en/similarname`;
2. `snapshot` → проверить наличие CAPTCHA:
   - **Если есть** `checkbox "I'm not a robot"` — пауза, сообщение юристу: «Решите CAPTCHA в открытом окне Chrome», ждём подтверждения;
   - Если нет — продолжаем;
3. Найти @ref поля `LabelText "Brand name"` → соответствующий `textbox`;
4. `fill @ref "{основной вариант}"`;
5. Найти @ref combobox для strategy → `select Fuzzy`;
6. `snapshot` → найти @ref активной кнопки `Search` → `click`;
7. `wait 8000` + сохранить persistent URL;
8. `snapshot` → top-30 результатов;
9. Для топ близких — клик → карточка `/en/similarname/brand/{ID}` → snapshot → **сохранить ID и IR-номера** (если найдена Madrid-запись).

#### 4.4 Madrid Monitor (Tavily /extract)

Для каждого IR-номера, найденного в 4.3 — через локальный Overlay (прямой Tavily adapter):
```
mcp__legal-overlay__tavily_extract(
  urls=["https://www3.wipo.int/madrid/monitor/en/showData.jsp?ID=ROM.{N}"],
  extract_depth="advanced",
  format="markdown"
)
```

Парсить markdown (`results[0].raw_content`) → record (Holder, Reg.Date, Expiration, Nice classes, Designation list).

Полный протокол и fallback (прямой вызов, если сервер недоступен) — `references/trademark-search-automation.md` §6.3.

**Fallback** при ошибке Tavily — `agent-browser --headed --session madrid open …showData.jsp?ID=ROM.{N}`.

#### 4.5 Контекст (Tavily /search)

```powershell
$body = @{
  query = "{обозначение} товарный знак общеизвестный"
  search_depth = "basic"
  max_results = 5
  include_domains = @("vsrf.ru","pravo.gov.ru","rospatent.gov.ru","consultant.ru")
} | ConvertTo-Json
```

#### 4.6 Журнал

Каждый запрос фиксируется в `logs/trademark-search/{date}-{name}/automation-journal.json`:
- инструмент, база, запрос, время, persistent URL, число найденных, ошибки, израсходованные credits.

#### 4.7 Если автоматизация не сработала

- Конкретный шаг помечается `[АВТОМАТИЗАЦИЯ НЕ СРАБОТАЛА: {причина}]`;
- Никаких выдуманных результатов;
- Если упало > 1 базы — skill спрашивает юриста: продолжать с тем что есть или ждать восстановления / fallback.

### Шаг 5 — Анализ противопоставлений

Для каждого найденного потенциально релевантного ТЗ — оценка по 4 критериям:

1. **Фонетическое сходство**: [высокое / среднее / низкое] + обоснование (количество слогов, начальные/конечные звуки, длина);
2. **Графическое (визуальное) сходство**: [высокое / среднее / низкое] + обоснование;
3. **Семантическое сходство**: [высокое / среднее / низкое] + обоснование;
4. **Общий зрительный образ**: интегральная оценка.

Затем — **однородность товаров и услуг**:
- Сопоставление классов МКТУ;
- Природа товара, круг потребителей, условия реализации, взаимозаменяемость.

Затем — **совокупный риск** по таблице из `trademark-similarity-search.md`.

- Собственные знаки компании: если найденный знак есть во внутреннем реестре (`profile/knowledge/ip/index/by-product.md` или `python -m tools.ip_registry query --number <N>`), пометить его как собственный, а не противопоставление; статус по реестру — на дату выгрузки (`skills/ip-registry`).

### Шаг 6 — Подготовка отчёта (.docx в workflow/)

Каноническая структура — раздел «Обязательная структура ответа» ниже (**единственный источник**, чтобы не было дрейфа; методология содержания разделов «Анализ» и «Риск» — `references/trademark-similarity-search.md`, «Критерии сходства» и «Уровни риска»). Журнал автоматизации — по `references/trademark-search-automation.md` §11.

Отчёт — **deliverable для юриста / бизнеса → `.docx` в `workflow/`** (в worktree-сессии — в основную `workflow/` по абсолютному пути), сборка по `references/docx-generation.md`, оформление по `references/document-formatting.md`. Если есть релевантная папка дела `workflow/<дело>/` — сохранять туда. Технический журнал (`automation-journal.json`), сырые ответы и скриншоты — в `logs/trademark-search/{дата}-{обозначение}/` (проверяемость, не deliverable; .md-копия отчёта может лежать рядом как техническая).

**Перед сохранением .docx — обязательный existence-check** ссылок на ФЗ/кодекс (принцип 2): ст. 1483, 1508 ГК РФ, Приказ Минэкономразвития № 482, Пленум ВС РФ № 10 и действующая редакция МКТУ. Результат existence-check коротко — в разделе «Заметка юристу».

### Шаг 7 — Заметка юристу

Обязательно указать:
- что проверено (какие базы, какие варианты, какие классы);
- что **не проверено** (общеизвестные ТЗ за пределами фона, фирменные наименования, доменные имена и т. п.);
- где автоматизация **не сработала** и потребовался fallback;
- что требует подтверждения у патентного поверенного;
- что является `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]`;
- результат existence-check норм (принцип 2): проверено / не найдено / выставленные маркеры.

**Close-out.** Сохранив .docx в `workflow/<дело>/`, создать или обновить там `case-context.md` (шаблон `templates/agent-notes/case-context-template.md`): статус, что проверено (базы, варианты, классы), найденные противопоставления и совокупный риск, выбор стратегии юриста (если был), следующий шаг. Правило — CLAUDE.md «Контекст дела (case-context)»; это общий workflow-инвариант проекта, не специфика ТЗ. Если работа по бренду разовая и папки дела нет — case-context не обязателен.

## Поиск информации

Специализированные протоколы поиска по базам (платформа Роспатента, linkmark.ru, WIPO GBD, WIPO Madrid Monitor) — в `references/trademark-search-automation.md`. Это **надстройка** над общим слоем веб-инструментов `references/web-research-tools.md` (agent-browser + Tavily + WebSearch).

Помимо специализированных баз могут потребоваться: проверка правообладателя в ЕГРЮЛ (если РФ-компания), банкротство правообладателя (влияет на актуальность регистрации), судебная практика по аналогичным противопоставлениям (kad.arbitr.ru). Использовать общий слой через `web-research-tools.md`.

## Что запрещено

- Давать категоричное юридическое заключение о возможности регистрации.
- **Выдумывать** номера регистраций, даты приоритета, классы МКТУ, правообладателей. Если поиск не дал результата — так и пишется.
- **Замазывать ошибки автоматизации** — если CAPTCHA не прошла, agent-browser упал, Tavily вернул error — это фиксируется явно, без маскировки.
- Оценивать однородность товаров без указания конкретных позиций (запрещены общие фразы «однородные товары»).
- Делать вывод по знаку, не проверив **минимум 2 базы** (официальная платформа Роспатента + WIPO GBD; linkmark.ru — кросс-проверка).
- Маркировать рекомендацию как «решение» — это **рекомендация**, не более.
- Делать массовые автоматические запросы к WIPO Madrid Monitor (запрещено документацией). Только точечные ссылки на конкретные IR-номера.
- **Хардкодить ref-ы** в agent-browser. Каждый раз — `snapshot` → поиск по подписи → актуальный @ref.

## Маркеры

- `[ПРОВЕРИТЬ ИСТОЧНИК]` — требуется проверка дополнительной базы или автоматизация не отработала;
- `[ПРОВЕРИТЬ ОБЩЕИЗВЕСТНОСТЬ]` — проверить, не входит ли ТЗ в перечень общеизвестных (ст. 1508 ГК РФ);
- `[ПРОВЕРИТЬ ПРИОРИТЕТ]` — уточнить дату приоритета;
- `[ПРОВЕРИТЬ ОДНОРОДНОСТЬ]` — спорные классы МКТУ;
- `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]` — выбор стратегии (подавать / переговоры / альтернативный знак);
- `[ТРЕБУЕТСЯ ПАТЕНТНЫЙ ПОВЕРЕННЫЙ]` — за пределами screening;
- `[АВТОМАТИЗАЦИЯ НЕ СРАБОТАЛА: {причина}]` — конкретный этап поиска перешёл в ручной fallback.
