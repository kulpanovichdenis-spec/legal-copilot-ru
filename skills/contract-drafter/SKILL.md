# Contract Drafter

Паттерн: sequential + domain-intelligence (High freedom — юридическое суждение; детерминированного ядра нет).

## Назначение

Skill готовит **проект нового договора** после того, как существенные условия собраны (бизнесом напрямую или через `contract-intake`):
- карту существенных / рекомендуемых условий по типу договора;
- проект договора — сразу в .docx;
- сопроводительную заметку для юриста (принятые допущения, маркеры, открытые вопросы, обоснование выбора формулировок);
- чек-лист перед финальной проверкой юристом.

## Принципы

1. Источники до позиции — `references/skill-shared-steps.md`. Норму подтверждать через `route_norm_verification(..., probe=true)` только по маршруту `usable_now: true`.
2. **Порядок сборки — закон и комментарии раньше формы, процесс сделки раньше структуры.** Сначала карта условий по `references/contract-playbook.md` раздел 0 (ГК РФ + доктринальные комментарии), потом коммерческие блоки раздела 2, затем структура договора по жизненному циклу сделки, и только потом текст из `skills/clause-library/SKILL.md` и образцов `legal-document-samples`. Образцы — источник формулировок, не структуры (решение юриста 2026-09-14). Не начинать с шаблона/образца. Модель сделки, архитектура комплекта, структура, язык, иерархия источников при выборе условий и проверки удобства — по `references/contract-design.md` (единый источник; форма никогда не меняет юридический смысл).
3. Skill не принимает бизнес-решения (цена, объём, скидка, готовность к компромиссу) и не квалифицирует сделку как крупную / с заинтересованностью — только отмечает маркером.
4. Цитирование — по `references/citation-rules.md`. Уровни риска — по `references/risk-scale.md`.
5. Не выдумывать стороны, реквизиты, суммы, даты, характеристики предмета. Любая неполнота — маркер.
6. Результат — черновик. Подписание, отправка, согласование — за юристом.
7. Пресейв перед `workflow/` — `references/skill-shared-steps.md`.

## Когда использовать

- Бизнес прислал полный бриф «нужен договор с X на Y», существенные условия названы.
- `contract-intake` отработал, вводные собраны, юрист просит проект.
- Есть все данные для проекта и нужен готовый текст договора.
- Нужен новый документ комплекта к действующему рамочному договору — спецификация, заказ, приложение (техническое задание, цены, SLA, формы): сначала функция документа и граница с основным договором (`references/contract-design.md` раздел 4). Изменение уже подписанных условий — не сюда, а в `amendment-drafter`.

## Когда не использовать

- Вводные ещё не собраны, нужны вопросы бизнесу — `contract-intake`.
- Есть готовый проект договора и нужен его анализ — `contract-review`.
- Нужно изменить действующий договор (ДС) или сделать протокол разногласий — `amendment-drafter`.
- Новая редакция на основе существующего шаблона / прошлых договоров или консолидация договора с ДС — `contract-redesign`.
- Нужна претензия / письмо по спору — `procedural-document-drafter`.

## Алгоритм работы

0. **Контекст дела.** Если контрагент или сделка опознаётся и в `workflow/` есть его папка — прочитать `case-context.md` до сборки проекта. Одна строка юристу. Правило — CLAUDE.md «Контекст дела».
1. **Проверка полноты вводных.** Убедиться, что собраны: тип договора, стороны и их роли, предмет, цена и порядок оплаты, сроки. Если чего-то из этого нет — не «додумывать», а вернуть юристу короткий список недостающего (или перенаправить в `contract-intake`). Не начинать проект на догадках о существенных условиях.
2. **Карта условий по типу договора** — по `references/contract-playbook.md` раздел 0: тип → discovery регулирующей главы/статей ГК РФ → verification нормы по capability-маршруту → существенные условия (ст. 432 ГК РФ + вид договора) → рекомендуемые условия и спорные места из комментариев/практики. Результат — двухуровневый список (существенные / рекомендуемые).
3. **Коммерческие блоки** — пройти чек-лист `references/contract-playbook.md` раздел 2 (предмет, цена, оплата, сроки, приёмка, ответственность, расторжение, форс-мажор, подсудность и т. д.) и применимые специальные блоки раздела 5 (ПДн, реклама, ЛП/БАД, ЭДО, ИС, санкции).
4. **Модель сделки и архитектура комплекта** — по `references/contract-design.md` разделы 2–4: сущности сделки и карточки существенных обязательств (кто / что / когда / триггер / вход / выход / кому / как / доказательство / последствие), пользователи договора, состав документов (единый договор / рамочный + спецификации или заказы / договор + приложения) с разделением стабильных и переменных условий. Существенное условие не выносится в будущий документ без механизма его согласования. Модель — внутренняя; юристу — только выбранная архитектура, её логика и развилки.
5. **Проверка контрагента** — обязательный шаг перед вписыванием реквизитов сторон (см. «Поиск информации»).
6. **Структура по жизненному циклу сделки** — по `references/contract-design.md` раздел 5: порядок разделов повторяет, как стороны исполняют сделку (например, для поставки: предмет и модель работы → заказы → поставка → документы → приёмка → качество → цена и расчёты → претензии → ответственность → расторжение → заключительные положения); сначала условия успешного исполнения, затем — что происходит при нарушении. Раздел «Права и обязанности сторон» не заводится по умолчанию: каждое право/обязанность ставится в раздел процесса, к которому относится. Структура образца `legal-document-samples` не копируется — даже если образец ближе всего по типу сделки. Паттерны (таблицы, график этапов, «если — то», карта документов, функциональные заголовки) — только под конкретную проблему (раздел 6).
7. **Сборка текста.** Формулировки типовых условий — из `skills/clause-library/SKILL.md` (приоритетнее образцов: одобрены юристом), затем из образцов `legal-document-samples` (категория contracts, под тип сделки) — с обязательной адаптацией под стороны/нумерацию/предмет и под структуру шага 6; существенные и рекомендуемые условия из карты (шаг 2) и специфика предмета/цены — пишутся индивидуально. Язык, модальность, определения, ссылки на пункты — `references/contract-design.md` разделы 7–9.
8. **Verification gate** — перед сохранением: карта существенных условий закрыта (нет пропущенных → иначе риск незаключённости, ст. 432 ГК РФ); existence-check всех ссылок на ФЗ/кодексы; все несущие реквизиты, суммы, даты, характеристики предмета либо подтверждены источником, либо помечены маркером; проверки `references/contract-design.md` раздел 10 — сквозная цепочка исполнения (триггер / срок / сторона / доказательство / последствие на каждом переходе), «найти — понять — действовать — подтвердить — нарушение», тест унаследованной структуры (если использовались образцы), тест избыточной визуализации; ссылки на пункты сверены после финальной структуры.
9. **Генерация .docx** в `workflow/` (по `references/docx-generation.md`) + сопроводительная заметка юристу отдельным .docx.

## Обязательная структура ответа

```markdown
# Проект договора

## 1. Что уже понятно
Тип договора, стороны и роли, предмет, ключевые экономические параметры, сроки, кто инициатор, желаемая дата. Не названо — маркер.

## 2. Карта условий по типу договора
По `contract-playbook.md` раздел 0, двухуровневый список:
- **Существенные (по закону)** — регулирующая глава ГК РФ, каждое существенное условие с нормой-основанием; помечено, как оно закрыто в проекте;
- **Рекомендуемые (из комментариев/практики)** — условие + короткое обоснование (доктринальный комментарий / спорная практика), почему стоит отразить.

## 3. Архитектура комплекта и структура
- **Состав документов** — какие документы нужны сделке и почему (что в основном договоре, что в спецификации / заказе / приложении); при трёх и более документах — карта документов и порядок разрешения противоречий между ними.
- **Структура** — перечень разделов в порядке жизненного цикла и одной фразой логика; куда поставлены условия, которые в образцах обычно живут в «Правах и обязанностях».
- **Паттерны** — какие таблицы / навигаторы применены и какую проблему каждый решает (или «не применялись»).

## 4. Открытые вопросы / чего не хватает для финала
Что должен решить бизнес или юрист (не выдумывается): недостающие реквизиты, спорные бизнес-развилки, отраслевые подтверждения, развилки архитектуры (раздел 11 `contract-design.md`).

## 5. Принятые допущения
Явный список: где при отсутствии данных принято разумное типовое условие (диспозитивная норма ГК РФ, стандартная клауза) — чтобы юрист видел, что подставлено «по умолчанию», а не согласовано.

## 6. Проект договора
Ссылка на сгенерированный .docx в `workflow/`. Обязательные рамочные элементы: преамбула (стороны, подписанты, основания полномочий), реквизиты и подписи, приложения. Между ними — разделы в порядке жизненного цикла сделки (шаг 6). Независимо от порядка должны быть закрыты: предмет, цена и порядок оплаты, сроки, приёмка и закрывающие документы, ответственность, заверения и гарантии, конфиденциальность, форс-мажор, расторжение, применимое право и подсудность.

## 7. Заметка для юриста
По шаблону `templates/agent-notes/review-note-template.md`: что закрыто по карте условий, архитектура и логика структуры (раздел 3), что подставлено как допущение, какие маркеры остались, какие нормы/источники требуют проверки, какие решения за юристом, что нельзя отправлять без проверки.

## 8. Чек-лист перед финальной проверкой юристом
- все существенные условия по карте закрыты (ст. 432 ГК РФ);
- реквизиты сторон проверены (counterparty-check);
- цена, суммы, ставка НДС, даты — подтверждены или помечены;
- ссылки на нормы прошли existence-check;
- специальные блоки (ПДн / реклама / ЛП-БАД / ИС / санкции) закрыты, если применимы;
- подписанты и основания полномочий — подставлены или помечены;
- цепочка исполнения без пробелов (триггер / срок / сторона / доказательство / последствие);
- один объект — один термин во всём комплекте; неиспользуемых определений нет;
- ссылки на пункты и приложения сверены после финальной структуры.
```

## Ключевые правила содержания

1. **Закон и комментарии — раньше формы** (принцип 2). Карта условий раздела 0 строится до сборки из образцов и реестра клауз; структура — по жизненному циклу сделки, образцы дают формулировки.
2. **Существенные условия — обязательны.** Пропуск существенного условия по типу договора — риск незаключённости (ст. 432 ГК РФ), не косметика. В заметке юристу — отдельно.
3. **Клаузы из реестра приоритетнее образцов.** `skills/clause-library/SKILL.md` — одобренные юристом формулировки; образцы `legal-document-samples` — источник формулировок и тактики, не структуры и не выверенная позиция (см. `references/contract-playbook.md` раздел 0.5 и правило «образцы ≠ право» в CLAUDE.md). При конфликте формулировок — реестр.
4. **Подписанты не выбираются самостоятельно.** Если инициатор указал подписанта и основание полномочий — подставить; если нет — оставить поля пустыми + `[ПРОВЕРИТЬ РЕКВИЗИТЫ]`.
5. **Ставка НДС — актуальная 22 %** (20 % устарела; см. `references/contract-playbook.md` 7.8). Суммы — цифрами + прописью.
6. **Характеристики предмета** (материалы, габариты, техпараметры) — только из источника (спецификация, ТЗ, обмеры); нет источника — `[ПРОВЕРИТЬ ХАРАКТЕРИСТИКИ]`, не сочинять правдоподобную конкретику.

## Формат итогового черновика

Проект договора — **сразу в .docx** в `workflow/`, по правилам `references/docx-generation.md`; оформление — вариант по типу документа (`references/document-formatting.md` таблица 6.0: «Стандарт» / «Для физлиц» / «Рубрикатор»; сборка через `tools/docx_style/profiles.py`), заметка юристу — профиль аналитической заметки (раздел 7). Промежуточная стадия «текст в .md → потом в Word» исключена. Сопроводительная заметка юристу (допущения, риски, маркеры, обоснование формулировок) — тоже **отдельным .docx** рядом (документ для человека → правило CLAUDE.md «Формат результата»; `.md`-копия допустима только как техническая), по образцу `templates/agent-notes/review-note-template.md`.

Если юрист явно просит только «черновой текст / набросок структуры» без готового договора — допустимо начать с .md; во всех остальных случаях — сразу .docx.

## Поиск информации

**Проверка контрагента — обязательный шаг перед формированием преамбулы и реквизитов.** Подключать `skills/counterparty-check/SKILL.md` (DaData MCP) по ИНН/ОГРН каждой стороны: подтвердить, что юрлицо действующее; получить актуальную шапку реквизитов (наименование, адрес, руководитель, КПП) для преамбулы; отметить ранние риски (недостоверный адрес, статус, минимальный капитал при крупной сделке). Контрагент назван без идентификатора — запросить ИНН/ОГРН, не угадывать.

Публичные идентификаторы (ИНН, ОГРН, наименование) — разрешены к передаче в DaData. Данные сделки (цена, особые условия) — не передавать в публичные API.

Для актуальных норм и ставок (ключевая ставка ЦБ для ст. 395 ГК РФ, ставка НДС, регуляторные требования) — `references/web-research-tools.md` (Tavily /search; WebFetch на прямой URL акта). Не выдумывать нормы, ставки, практику. При недоступности инструментов — `[ИНСТРУМЕНТ НЕДОСТУПЕН]` / `[DADATA НЕДОСТУПНА]` и чек-лист для ручной проверки юристом.

## Что запрещено

- Начинать проект без собранных существенных условий — додумывать предмет/цену/стороны.
- Собирать договор из образца/шаблона раньше карты условий раздела 0.
- Копировать структуру и порядок разделов образца вместо структуры по жизненному циклу сделки; заводить «Права и обязанности сторон» только потому, что раздел есть в образце.
- Принимать бизнес-решения (цена, объём, скидка) за бизнес.
- Квалифицировать сделку как крупную / с заинтересованностью — только маркер.
- Выдумывать реквизиты, суммы, даты, характеристики предмета.
- Самостоятельно выбирать подписанта.
- Использовать устаревшую ставку НДС 20 % в новых договорах.
- Маркировать проект как «готовый к подписанию».
