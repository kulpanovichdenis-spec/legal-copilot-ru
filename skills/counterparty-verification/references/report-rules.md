# Правила сборки «Лист проверки контрагента»

Назначение: как результат due diligence (методология — `skills/counterparty-verification/references/methodology.md`, вердикт — `skills/counterparty-verification/references/risk-rules.md`) сворачивается в итоговый DOCX «Лист проверки контрагента» (2–4 стр.). Документ **собирается программно** — `tools/counterparty_verification/report_docx.py`, `build_report(case_data, out_path)` — по общему правилу проекта «любой .docx собирается из структуры и правил, а не переносится из готовой болванки» (`references/docx-generation.md`, раздел «Главный принцип»). Этот файл не переопределяет `references/docx-generation.md` (шрифт, поля, кириллица `eastAsia`, проверка результата) — он фиксирует специфику именно этого документа: состав разделов и evidence-first mapping.

## 1. Структура документа

Ровно та последовательность разделов, которую строит `build_report` в `tools/counterparty_verification/report_docx.py` — состав разделов не меняется без синхронной правки скрипта:

1. **Заголовок** — «ЛИСТ ПРОВЕРКИ КОНТРАГЕНТА».
2. **Контрагент** — наименование, ИНН/ОГРН (РФ) или иностранный ID, страна, дата проверки.
3. **Параметры сделки** — предмет, сумма, аванс, отсрочка, длительность, обеспечение и т. п. (то, что собрано на INTAKE — `skills/counterparty-verification/references/methodology.md`, раздел 1); если параметры не переданы — раздел явно отмечает это ограничение.
4. **Итоговая оценка** — вердикт `🟢 ДОПУСТИМО` / `🟡 ДОПУСТИМО С УСЛОВИЯМИ` / `🔴 ВЫСОКИЙ РИСК` (`verdict` строго `green`/`yellow`/`red` — иное значение роняет `ReportError`, см. `tools/counterparty_verification/schema.md`).
5. **Таблица проверки** — построчно: Правоспособность, ЕГРЮЛ, Адрес, ЕИО, Полномочия, Финансы, Суды, Банкротство, ФССП, Федресурс, Санкции, Лицензии (состав строк — по факту проведённых проверок конкретного контрагента; строки, неприменимые к стране/сделке — `N/A`). Каждая строка — статус проверки в свободном тексте + метка риска `🟢`/`🟡`/`🔴`/`⚪`(manual)/`N/A` (`RISK_EMOJI` в `report_docx.py`).
6. **Выявленные риски** — только значимые находки (не пересказ всей таблицы), каждая — с кратким основанием; полный FACT/ANALYSIS/RISK/RECOMMENDATION остаётся в рабочем анализе, в отчёт сворачивается компактно. **Только факты о самом контрагенте** (статус, финансы, суды, банкротство, санкции, полномочия). Собственные недоработки, недоступность источников, отсутствие свежей выписки — **не сюда**, а в «Ограничения проверки» (п. 9). Терминология точная: «лист записи ЕГРЮЛ» (о событии) ≠ «выписка из ЕГРЮЛ» (актуальный свод).
7. **Необходимо запросить** — точечный список дозапроса (`skills/counterparty-verification/references/methodology.md`, раздел 6), не «максимальный пакет». Только документы/сведения due diligence контрагента; **не включать** операционные реквизиты сделки (банковский счёт для оплаты, реквизиты для перечисления и т. п.) — это не проверка контрагента.
8. **Рекомендации** — конкретные действия (снизить аванс, получить обеспечение, дозапросить документ, отказаться от сделки), не общие фразы.
9. **Ограничения проверки** — раздел про **процесс проверки**, а не про контрагента (не путать с «Выявленные риски»). Сюда: недоступные источники с **фактической** причиной (не предполагаемой — «инструмент недоступен в сессии» / «сработала CAPTCHA» / «сайт не отвечает» / «платный доступ»), собственные недоработки сбора, отсутствие свежей официальной выписки, источники, не существующие/неприменимые в юрисдикции, пункты на ручную проверку (`MANUAL CHECK REQUIRED`).
10. **Источники** — по каждому существенному выводу: название источника, URL (где применимо), дата обращения, сохранённый файл в досье (если скачивался).

## 2. Evidence-first mapping

Каждый пункт разделов «Выявленные риски» и строк таблицы, отмеченных не как `N/A`, должен быть прослеживаем до конкретной записи в разделе «Источники» — название, URL/реестр, дата, путь к сохранённому файлу в подпапке досье (`01_Реестр/` … `09_Прочее/`, см. `tools/counterparty_verification/case_folder.py`, `SUBFOLDERS`). Формулировка риска без соответствующего источника в этом разделе — дефект отчёта, а не допустимое упрощение: он не проходит методологию evidence-first (`skills/counterparty-verification/references/methodology.md`, раздел 3).

Практическое правило сборки `case_data["sources"]` (см. форму в `tools/counterparty_verification/schema.md`, раздел «case_data для DOCX»): при добавлении в `case_data["risks"]` любой строки — сразу добавить (или сверить, что уже есть) соответствующую строку в `case_data["sources"]`. Обратное не требуется — не каждый источник в «Источниках» обязан порождать риск (например, «ЕГРЮЛ (DaData) — статус ACTIVE, риска не создаёт» тоже фиксируется как использованный источник).

## 3. Запрещённая формулировка

Итоговая оценка и любой текст отчёта **не используют слово «надёжен»** (и синонимичные формулировки «годен к подписанию», «безопасный контрагент» и т. п.). Допустимая формулировка — только уровень допустимости по шкале раздела 1, п. 4 (`ДОПУСТИМО` / `ДОПУСТИМО С УСЛОВИЯМИ` / `ВЫСОКИЙ РИСК`). Это тот же принцип, что действует в лёгком `skills/counterparty-check/SKILL.md` («Что запрещено»), распространённый на полный DD-отчёт: решение о работе с контрагентом остаётся за юристом и бизнесом, документ этого skill'а — вход для решения, не само решение.

## 4. Генерация и верификация

- Генерация — исключительно через `tools/counterparty_verification/report_docx.py`, функция `build_report(case_data, out_path)`. Форма `case_data` зафиксирована в `tools/counterparty_verification/schema.md`, раздел «case_data для DOCX».
- Технические правила документа (шрифт Times New Roman + `w:eastAsia`, поля, размер страницы, вёрстка таблиц) — по `references/docx-generation.md`; `report_docx.py` уже их реализует, дополнительно настраивать не нужно.
- Путь сохранения — `case["report_docx"]` из `tools/counterparty_verification/case_folder.py` (`workflow/_counterparty/<досье>/<досье>_Лист_проверки.docx`; в worktree-сессии — по абсолютному пути основного чекаута).
- **Верификация — обратным извлечением текста**: после сборки — `extract_docx_text(path)` (тот же модуль) и сверка, что ключевые элементы (заголовок, вердикт, обязательные разделы) присутствуют в извлечённом тексте, до того как результат передаётся юристу. Это тот же приём, что использует `selftest()` модуля (`tools/counterparty_verification/report_docx.py`), — не отдельная новая процедура.
- **DOCX — не единственный выход.** Наряду с листом проверки собирается **машиночитаемая карточка** `card.json` (`tools/counterparty_verification/card.py`, `build_card`) и ведётся `case-context.md` — единый информационный слой дела. Доказательства (выписки/скриншоты/выгрузки/PDF) сохраняются в подпапки досье `01_Реестр`…`09_Прочее` (evidence-first, `skills/counterparty-verification/references/methodology.md`, раздел 3), а не только упоминаются в «Источниках».

## 5. Открытая версия у юриста (точечная правка)

Если юрист уже открыл/поправил ранее сгенерированный DOCX (в т. ч. добавил комментарии) — не перезаписывать открытый файл: сохранить исправленную версию под новым именем (`…_v2`), а версию юриста оставить как есть (например, в `09_Прочее`). Общий принцип точечной правки/непересборки поверх правок юриста — `references/docx-generation.md`, раздел «Точечная правка существующего .docx».

## Связанные файлы

- `tools/counterparty_verification/report_docx.py` — сборка и обратное извлечение текста (`build_report`, `extract_docx_text`).
- `tools/counterparty_verification/schema.md` — точная форма `case_data`.
- `tools/counterparty_verification/case_folder.py` — путь досье, подпапки, именование файлов.
- `references/docx-generation.md` — общие технические правила генерации .docx (шрифт, поля, кириллица, проверка результата).
- `skills/counterparty-verification/references/methodology.md` — evidence-first, откуда берутся данные для отчёта.
- `skills/counterparty-verification/references/risk-rules.md` — откуда берётся вердикт `green`/`yellow`/`red`.
- `skills/counterparty-check/SKILL.md` — тот же запрет на «надёжен» в лёгкой версии проверки.
