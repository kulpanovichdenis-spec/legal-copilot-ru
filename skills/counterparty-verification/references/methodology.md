# Методология due-diligence проверки контрагента

Назначение: базовая методология skill `counterparty-verification` — что и зачем собирается на входе, как контрагент однозначно идентифицируется, что значит evidence-first в этом skill, какой иерархии источников подчиняется фактура проверки и как вести себя, когда источник недоступен. Это не оркестрация (она в `skills/counterparty-verification/SKILL.md`) и не risk-engine (он в `skills/counterparty-verification/references/risk-rules.md`) — здесь только то, как собираются и обосновываются факты, на которых строится дальнейшая оценка.

## 1. INTAKE — что нужно получить перед стартом проверки

### Обязательный минимум

Без этого проверку не начинать (не хватает данных даже для однозначной идентификации):

- наименование контрагента (полное или в том виде, в котором его назвал юрист/бизнес);
- страна регистрации (или основание считать, что это РФ);
- хотя бы один официальный идентификатор — ИНН, ОГРН (для РФ) либо регистрационный номер в реестре страны регистрации (для иностранного контрагента).

Если из обязательного минимума не хватает идентификатора — это не блокирует старт (см. `skills/counterparty-verification/countries/RU.md` — поиск по наименованию как альтернативный вход), но однозначная идентификация (раздел 2) всё равно обязательна до перехода к проверке по существу.

### Желательные параметры сделки

Собираются по возможности — от них зависит вес риска (раздел «Transaction-weighted» в `skills/counterparty-verification/references/risk-rules.md`), а не полнота идентификации:

- предмет сделки (что покупается/продаётся/оказывается);
- роль контрагента (поставщик, покупатель, исполнитель, заказчик, посредник, лицензиар/лицензиат и т. п.);
- сумма сделки и валюта;
- размер и условия аванса;
- отсрочка платежа;
- длительность отношений (разовая сделка / длящийся договор);
- наличие обеспечения (банковская гарантия, залог, поручительство, страхование);
- критичность для бизнеса (замещаемый поставщик / единственный источник; типовая закупка / стратегическая зависимость).

Если параметры сделки не переданы юристом — проверка проводится по общим критериям без transaction-weighting, и это ограничение прямо отражается в разделе «Ограничения проверки» итогового DOCX (`skills/counterparty-verification/references/report-rules.md`).

**Спрашивать, а не гадать.** Если недостающая вводная **материально меняет оценку или полномочия** (например: наша роль — лицензиат или лицензиар; исключительная или простая лицензия; кто кому и сколько платит; наличие аванса), её нужно **уточнить у юриста одним вопросом**, а не выносить в отчёт как флажок-догадку («характер лицензии не подтверждён») и не достраивать по предположению. Флажок уместен только для того, что объективно нельзя добрать в моменте (пробел в источнике), а не для того, что можно просто спросить.

## 2. IDENTIFICATION — однозначная идентификация контрагента

### Набор для РФ

- полное наименование (с ОПФ);
- сокращённое наименование;
- ИНН;
- ОГРН;
- КПП (если применимо — для обособленных подразделений);
- дата регистрации.

### Набор для иностранного контрагента

- юридическое наименование (в оригинальном написании и — если применимо — в русской транслитерации);
- регистрационный номер в реестре страны регистрации;
- страна;
- юрисдикция / штат / провинция регистрации (для стран с субнациональными реестрами, например США);
- иной применимый идентификатор (например, Unified Social Credit Code для КНР — см. `skills/counterparty-verification/countries/CN.md`).

### Gate: неоднозначная идентификация

Если поиск по наименованию/идентификатору возвращает **несколько похожих компаний** (совпадающее или почти совпадающее наименование, разные ИНН/ОГРН, разные регионы регистрации) — проверка **не продолжается** до тех пор, пока контрагент не идентифицирован однозначно. Действие: вернуться к юристу с перечнем найденных совпадений (наименование + ИНН/ОГРН + адрес по каждому) и попросить подтвердить, о какой компании речь, либо предоставить точный идентификатор.

Это жёсткий gate skill'а (см. `skills/counterparty-verification/SKILL.md`, раздел Hard gates) — не рекомендация, а условие, без выполнения которого дальнейшие шаги (полномочия, суды, санкции) не имеют смысла: они будут собраны не по тому лицу.

## 3. Evidence-first: FACT / ANALYSIS / RISK / RECOMMENDATION

Каждый существенный вывод в проверке контрагента должен быть прослеживаем до конкретного источника. Формулировка вывода без источника («контрагент выглядит рискованным») недопустима — вместо неё используется структура из четырёх слоёв:

- **FACT** — что установлено и откуда (источник + дата получения);
- **ANALYSIS** — что это означает в контексте параметров конкретной сделки;
- **RISK** — какой уровень риска это создаёт (по `skills/counterparty-verification/references/risk-rules.md`) и почему именно этот уровень, а не другой;
- **RECOMMENDATION** — что сделать: запросить документ, снизить сумму/аванс, получить обеспечение, отказаться от сделки, либо принять риск с одобрения бизнеса.

Пример:

```
FACT: по данным ЕГРЮЛ (DaData, выписка от 28.08.2026, 01_Реестр/...ЕГРЮЛ.pdf)
контрагент зарегистрирован 01.06.2026 (возраст на дату проверки — 88 дней),
уставный капитал — 10 000 руб. (минимальный для ООО).

ANALYSIS: контрагент выступает поставщиком по сделке на 15 000 000 руб.
с авансом 50% (7,5 млн руб.). Молодая компания с минимальным капиталом
и без публичной истории исполнения обязательств несёт повышенный риск
неисполнения при значительном авансе.

RISK: 🟡 YELLOW — совокупность (малый возраст + минимальный капитал +
крупный необеспеченный аванс относительно параметров сделки); не RED,
поскольку иных red flags (недостоверность, суды, банкротство, санкции)
не выявлено.

RECOMMENDATION: снизить аванс до уровня, не создающего существенных
потерь при неисполнении, либо получить банковскую гарантию на сумму
аванса; при принятии риска без изменения условий — [ВОПРОС БИЗНЕСУ].
```

Это иллюстративный пример методологии, а не воспроизведение конкретного кейса из первоначального технического задания — verbatim-текст ТЗ в репозитории не сохранён; структура и формулировки собраны по правилам evidence-first и `references/risk-scale.md`.

Каждый вывод такого рода в итоговом DOCX сворачивается в компактную запись (строка таблицы + пункт «Выявленные риски» + пункт «Источники»), но при подготовке проверки агент обязан пройти все четыре слоя внутренне — это дисциплина сбора, а не только формат отчёта.

**Доказательство сохраняется, а не только цитируется.** Evidence-first означает не только ссылку на источник в тексте, но и **сохранённый файл-доказательство** в соответствующей подпапке досье (`01_Реестр`…`09_Прочее`): выписка/лист записи (PDF), скриншот или выгрузка страницы официального источника/агрегатора, экспорт результата поиска. Извлечённые из документов и источников сведения сводятся в **машиночитаемую карточку** `card.json` (`tools/counterparty_verification/card.py`) — единый информационный слой дела, пригодный для повторного использования и сверки; человекочитаемый контекст — в `case-context.md`. Вывод, под который не сохранено доказательство и который не отражён в карточке, — недоработка сбора, а не допустимое упрощение.

## 4. Иерархия источников для доказательной базы due diligence

Эта иерархия — про фактуру о контрагенте (статус, полномочия, суды, банкротство, санкции), а не про толкование норм права. Для правового обоснования (например, требований к корпоративному одобрению сделки в `skills/counterparty-verification/references/authority-check.md`) применяется обычный цикл — `references/source-hierarchy.md` и `references/citation-rules.md`, эта иерархия его не заменяет.

Порядок убывания веса источника:

1. **Официальный государственный источник** — реестр (ЕГРЮЛ/ЕГРИП, аналог за рубежом), картотека суда (kad.arbitr.ru, ГАС «Правосудие»), реестр банкротств (Федресурс/ЕФРСБ), банк данных ФССП, реестр лицензий регулятора, официальный санкционный список.
2. **Официальный документ**, полученный от контрагента или из первоисточника (устав, решение/протокол об избрании ЕИО, доверенность, лицензия) — при условии, что подлинность не вызывает сомнений (реквизиты сверяются с реестром).
3. **Судебный источник** — текст судебного акта (не пересказ в СМИ/агрегаторе).
4. **Официальный корпоративный disclosure** — раскрытие информации эмитентом (для публичных компаний), обязательные публикации (Федресурс, реестр аффилированных лиц и т. п.).
5. **Надёжный коммерческий агрегатор** (например, Rusprofile) — используется только когда официальный источник недоступен технически (не как замена ему по умолчанию) или для быстрой предварительной ориентации, которая затем сверяется с официальным источником.
6. **СМИ и аналитика** — используется только для контекста (репутационный фон, публичные споры), никогда как доказательство юридического статуса, регистрационных данных или полномочий.

Правила применения:
- **агрегатор не заменяет доступный официальный источник** — если официальный реестр отвечает, вывод строится на нём, агрегатор — только вспомогательная сверка;
- **СМИ ≠ доказательство юридического статуса** — упоминание в прессе о банкротстве не заменяет проверку по Федресурс/kad.arbitr.ru; в отчёте статус контрагента обосновывается только источниками уровней 1–4;
- **называть документы точно.** «Лист записи ЕГРЮЛ» фиксирует **конкретное регистрационное событие** (создание ЮЛ, изменение сведений) на свою дату и быстро устаревает; «выписка из ЕГРЮЛ» — **актуальный свод** сведений на дату её получения. Предоставленный контрагентом лист записи (тем более о создании) — не подтверждение текущего состояния: для актуального статуса/адреса/участников/ЕИО берётся свежая выписка. Подменять эти понятия в отчёте нельзя.

## 5. Fault tolerance — недоступность источника

Комплексная проверка использует много источников (реестр, суды, банкротство, ФССП, санкции, лицензии) — часть из них технически может быть недоступна (защита от автоматизации, CAPTCHA на ФССП, временная недоступность сайта, платный доступ). Правила:

- **сначала реально попытаться открыть источник** — причина незавершённости фиксируется по факту попытки, а не презюмируется. Нельзя написать «ФССП — CAPTCHA» или «КАД недоступен», не попытавшись открыть источник: указывается **фактическая** причина (инструмент/браузер недоступен в сессии, сработала CAPTCHA, сайт не отвечает, платный доступ);
- **недоступный источник отмечается, но не останавливает проверку в целом** — переход к следующему шагу workflow, а не блокировка всей due diligence из-за одного источника;
- недоступность фиксируется в разделе «Ограничения проверки» итогового DOCX с указанием, какой источник недоступен и по какой фактической причине (`skills/counterparty-verification/references/report-rules.md`);
- источники, требующие обхода технической защиты (CAPTCHA и аналоги) — не обходятся; результат — `MANUAL CHECK REQUIRED`, шаг остаётся за юристом (пример — ФССП, `skills/counterparty-verification/countries/RU.md`);
- **собственная недоработка или недоступность источника — это НЕ риск контрагента.** Отсутствие свежей выписки, непроведённая из-за недоступности инструмента проверка, неполнота сбора идут в раздел **«Ограничения проверки»**, а не в **«Выявленные риски»**. В «Выявленные риски» попадают только факты о самом контрагенте (его статус, финансы, суды, банкротство, санкции, полномочия);
- **«не найдено» ≠ «риска нет».** Если источник отвечает, но по контрагенту ничего не найдено (например, нет судебных дел на kad.arbitr.ru) — это фиксируется как факт («по данным kad.arbitr.ru на дату проверки судебных дел не найдено»), а не молчаливо опускается и не превращается в утверждение об отсутствии риска. Если источник **не проверялся** технически — это отдельная, более слабая формулировка («проверка не проведена: источник недоступен») и она не может быть представлена как «риска нет».

## 6. Дозапрос документов — только с объяснимой целью

Список недостающих документов для запроса у контрагента формируется не «на всякий случай по максимуму», а точечно — под конкретный пробел, выявленный по ходу проверки (см. также анти-паттерн в `skills/counterparty-verification/references/risk-rules.md`, раздел «Анти-паттерны»). Каждый пункт списка сопровождается причиной запроса.

Типовые позиции (запрашиваются, если по ним есть конкретный пробел):

| Документ | Когда запрашивается |
|---|---|
| Устав (действующая редакция) | Не подтверждены ограничения полномочий ЕИО / порядок одобрения крупных сделок / сделок с заинтересованностью |
| Решение / протокол об избрании (назначении) ЕИО | Не подтверждён срок полномочий действующего ЕИО или основание его избрания |
| Доверенность | Договор подписывает не ЕИО, а представитель по доверенности |
| Решение об одобрении крупной сделки / сделки с заинтересованностью | Параметры сделки требуют корпоративного одобрения по уставу или закону, а факт одобрения не подтверждён |
| Лицензия / допуск СРО / иное разрешение | Предмет сделки лицензируется, а действующая лицензия не подтверждена по реестру регулятора |
| Бухгалтерская (финансовая) отчётность | Крупный аванс / отсрочка / длительные отношения при отсутствии публичной финансовой картины |
| Документы о праве собственности (на предмет сделки, обеспечение) | Сделка предполагает переход/обременение конкретного актива, право на который контрагента не подтверждено реестром |
| Банковская гарантия / иное обеспечение | Выявлен риск, снижаемый обеспечением (см. пример в разделе 3), а обеспечения в условиях сделки нет |
| Сведения о бенефициарных владельцах (UBO) | Не идентифицированы конечные бенефициары при значимости сделки или при санкционных рисках (`skills/counterparty-verification/references/sanctions-check.md`) |

Запрашивать «максимальный пакет документов» без привязки к конкретному выявленному пробелу — не соответствует методологии (см. анти-паттерны в risk-rules.md).
