# Clause Review

Архитектурный паттерн: context-aware + domain-intelligence, Medium freedom — юридическую оценку выполняет модель, а выход ограничен фиксированной JSON-схемой одного договорного пункта.

## Назначение

Skill даёт компактный анализ **одного пункта договора** для встроенного в редактор (Word Add-in TaskPane) ассистента. Объём входа — от одного предложения до нескольких абзацев одного пункта. Объём выхода — короткий **структурированный JSON** по фиксированной схеме (см. `references/clause-review-response-schema.md`).

## Отличие от `contract-review`

| Параметр | `contract-review` | `clause-review` |
|---|---|---|
| Вход | целый договор + приложения | один пункт / фрагмент |
| Выход | редлайн и итог в чате; разбор рисков, письмо и заметка — по запросу | **один JSON** с компактной рекомендацией |
| Назначение | системный анализ перед подписанием | точечный анализ во время редактирования |
| Сценарий | юрист готовится к согласованию | юрист читает договор и тыкает на спорный пункт |
| Длительность | минуты на анализ всего документа | секунды на пункт |
| Канал | чат / диалог | автоматический вызов из боковой панели |

Если пришёл целый договор по ошибке — **переключиться на `contract-review`** или вернуть `needMoreContext: true` с просьбой выделить конкретный пункт.

## Принципы

1. Источники до позиции — `references/skill-shared-steps.md`. Норму подтверждать через `route_norm_verification(..., probe=true)` только по маршруту `usable_now: true`.
2. Анализ строится по `references/contract-playbook.md` и реестру `skills/clause-library/SKILL.md`.
3. Уровни риска — строго по `references/risk-scale.md` (раздел про clause-level, машиночитаемые значения).
4. Формат ответа — один JSON по `references/clause-review-response-schema.md`, без текста вне JSON и без вывода о договоре в целом.
5. Цитировать только проверенные нормы и практику по `references/citation-rules.md`; при сомнении или зависимости от соседних пунктов вернуть `needMoreContext: true`, заполнить `contextNeeded` и поставить маркер в `lawyerNote`.
6. Результат — рекомендация юристу, не финальное заключение.

## Когда использовать

- Юрист выделил пункт в Word и нажал «Анализировать выделенный пункт».
- Юрист в чате просит: «оцени этот пункт» / «что не так в этой клаузе» / «предложи редакцию по такому-то условию».
- При работе с правками контрагента (red-line) — оценка одной правки.

## Когда не использовать

- Целый договор — `contract-review`.
- Подготовка нового документа — `contract-intake`.
- ДС или протокол разногласий — `amendment-drafter`.
- Процессуальный документ — `procedural-document-drafter`.
- Объяснение / ответ госоргану — `gov-response`.

## Входные данные

Минимум:
- **`text`** — текст пункта.

Желательно (повышает точность):
- **`contractType`** — тип договора (поставка, подряд, лицензия, контрактное производство, иное).
- **`ourRole`** — наша сторона (покупатель, поставщик, заказчик, исполнитель, лицензиар, лицензиат).
- **`counterpartyName`** — наименование контрагента.
- **`counterpartyInn`** — ИНН (для возможной отдельной проверки через counterparty endpoint).
- **`reviewGoal`** — цель анализа (`analyze-risk`, `propose-wording`, `prepare-comment`).

## Что определить

1. **`clauseType`** — тип пункта по словарю (см. ниже).
2. **`riskLevel`** — уровень риска по `risk-scale.md` (машиночитаемые значения).
3. **`issue`** — в чём проблема (одно-два предложения, по существу).
4. **`recommendation`** — что предложить (одно-два предложения).
5. **`proposedWording`** — конкретная предложенная редакция пункта.
6. **`counterpartyComment`** — формулировка для отправки контрагенту (деловой и конструктивный тон).
7. **`needMoreContext`** + **`contextNeeded`** — нужны ли соседние пункты для надёжной оценки.
8. **`lawyerNote`** — что юристу проверить / какое стратегическое решение принять.

## Словарь типов пунктов (`clauseType`)

Используются как enum в JSON. Если ни один не подходит — `"иное"` + пояснение в `issue`.

- `"предмет"` — предмет договора, объём, спецификация;
- `"цена"` — цена, порядок оплаты, валюта, изменение цены;
- `"сроки"` — сроки исполнения, поставки, оказания услуг;
- `"приёмка"` — порядок приёмки, акты, претензии по приёмке;
- `"качество"` — требования к качеству, гарантия;
- `"ответственность"` — неустойки, убытки, ограничение ответственности;
- `"расторжение"` — основания и порядок расторжения, односторонний отказ;
- `"форс-мажор"`;
- `"конфиденциальность"`;
- `"интеллектуальная собственность"`;
- `"персональные данные"` (152-ФЗ);
- `"реклама и маркировка"` (38-ФЗ, ОРД);
- `"подсудность и применимое право"`;
- `"уступка прав"`;
- `"привлечение третьих лиц"` (субподряд / субпоставка);
- `"уведомления"`;
- `"электронный документооборот"`;
- `"антикоррупционные заверения"`;
- `"санкции и экспортный контроль"`;
- `"заверения и гарантии"`;
- `"срок действия и автопролонгация"`;
- `"иное"`.

## Уровни риска

Машиночитаемые значения для JSON-поля `riskLevel` (см. также `references/risk-scale.md`):

- `"блокирующий"` — без устранения двигаться нельзя;
- `"высокий"` — обязательная правка или мотивированное решение юриста;
- `"средний"` — желательно править, допустимо принять с компенсацией;
- `"низкий"` — техническая шероховатость, принять;
- `"вопрос-бизнесу"` — не юридическое решение, передать бизнесу.

## Формат ответа

**Только JSON. Никакого текста вне JSON. Никаких markdown-обёрток вроде `<code>```json ... ```</code>`.**

**Исключение — режим развёрнутого обоснования в чате.** Если юрист в чате явно просит аргументацию, а не карточку («найди обоснование», «почему это противоречит ГК/доктрине», «объясни», «докажи») — вернуть развёрнутый разбор по `references/house-style.md` (нормы → практика → блок «Было/Стало» → заметка юристу), с той же дисциплиной источников (принцип 1). JSON в этом режиме — дополнительно по запросу юриста или Word Add-in. Автоматический вызов из TaskPane — всегда только JSON.

Полная схема — `references/clause-review-response-schema.md`. Краткая форма:

```json
{
  "clauseType": "<enum из словаря>",
  "riskLevel": "<enum из шкалы>",
  "issue": "<одно-два предложения>",
  "recommendation": "<одно-два предложения>",
  "proposedWording": "<готовая редакция пункта или пустая строка>",
  "counterpartyComment": "<формулировка для контрагента или пустая строка>",
  "needMoreContext": <true | false>,
  "contextNeeded": ["<имя нужного пункта>", "..."],
  "lawyerNote": "<что проверить юристу>"
}
```

Если `needMoreContext: true` — `riskLevel` ставится по доступной информации, в `issue` указывается, что без контекста оценка предварительная.

## Подготовка входа

Обычно clause-review получает уже выделенный пункт (поле `text`) от пользователя или Word Add-in. Файл целиком приходит реже — но если пришёл:

1. Прогнать через `tools/doc_ingest/router.py` или `markitdown_runner.py`.
2. Получить `markdown` + `structured_json` по протоколу `references/document-ingestion.md`.
3. Найти запрошенный пункт через `structured_json.sections[id]` (например, «5.2.3») — сохранить его `id` и контекст соседних пунктов в поле `contextNeeded`.
4. Маркеры `[ОЦР НЕ УВЕРЕН]` для текста пункта — обязательно отразить в `lawyerNote`.
5. **Конфиденциальность**: реальные договоры — без cloud-OCR.
6. Если ингестия в текущей сессии недоступна — `[ИНСТРУМЕНТ НЕДОСТУПЕН]` и попросить юриста дать текст пункта.

Если приходит уже текст пункта (а не файл) — этот шаг пропускается, работать сразу с `text`.

## Алгоритм работы

1. Прочитать `text`.
2. Определить `clauseType` по словарю.
3. Сверить с реестром клауз (личный слой профиля `profile/knowledge/clauses/`, см. раздел «Использование реестра клауз»): есть ли одобренная формулировка этого типа клаузы — если да, использовать как базу для `proposedWording`.
4. Применить чек-листы из `references/contract-playbook.md` (для соответствующего раздела — общие проверки, red flags, fallback-позиции).
5. Определить `riskLevel` по `references/risk-scale.md`.
6. Сформулировать `issue`, `recommendation`, `proposedWording`, `counterpartyComment`.
7. Оценить, достаточно ли данных. При сомнении — `needMoreContext: true` + конкретный перечень в `contextNeeded`.
8. Положить в `lawyerNote` всё, что требует проверки / стратегического решения.
9. Вернуть **только JSON**.

## Использование реестра клауз (личный слой профиля)

При выявлении проблемной клаузы — **первым делом** проверять, есть ли в реестре одобренная формулировка по этому типу. Реестр — **личный слой профиля** `profile/knowledge/clauses/cards/<slug>.md` (файлы, не MCP):

1. **Glob** по `profile/knowledge/clauses/cards/*.md` + **Read** — по типу клаузы (`clauseType` / ключевые слова пункта; frontmatter `applies_to`/`name`/`aliases` и тело; ⚠️ карточки в `.gitignore` — обычный Grep-инструмент их не видит, для контент-поиска `rg --no-ignore`);
2. прочитать `profile/knowledge/clauses/cards/<slug>.md` — полный текст выбранной клаузы для `proposedWording`. Профиля/карточки нет → `proposedWording` оставить пустым, зафиксировать в `lawyerNote`, не выдумывать.

Ориентир «тип клаузы → `<slug>`» (полный указатель с применимостью — в `skills/clause-library/SKILL.md`):

- ЭДО — `01-edo`;
- НПД — `02-npd-samozanyatost`;
- автопролонгация — `03-avtoprolongatsiya`;
- возврат денежных средств (ВЭД) — `04-vozvrat-valyutny-kontrol`;
- персональные данные — `05-pdn-meropriyatiya`;
- ОРД / интернет-реклама — `06-markirovka-reklamy-ord`;
- недостатки работ — `07-nedostatki-rabot`;
- инструктажи и допуск к работам — `08-instruktazhi-hse`;
- сдача-приёмка — `09-sdacha-priemka`;
- исключительные права — `10-isklyuchitelnye-prava`;
- претензии — `11-pretenzii-spory`;
- форс-мажор — `12-fors-mazhor`;
- уведомления — `13-uvedomleniya`;
- акт сверки — `14-akt-sverki`;
- нерегистрированные ЛС — `15-postavka-nereg-ls`;
- индексация на ИПЦ — `16-indeksatsiya-tseny`;
- срок действия — `17-srok-deystviya`;
- смена адреса мероприятия — `18-smena-adresa-sroka`;
- обязанности Учреждения (КИ) — `19-obyazannosti-uchrezhdeniya-ki`;
- NDA (преамбула/термины, обязательства, ответственность, исключения/срок, прочие положения, споры/язык/уведомления, контакты/подписи) — `20-nda-preambula-terminologiya` … `26-nda-kontakty-podpisi`.

Если совпадение есть — использовать формулировку из реестра как `proposedWording` (с адаптацией под текущий договор: наименования сторон, нумерация, предмет — см. правило в начале `skills/clause-library/SKILL.md`). Реестр — **drafting material, не правовой источник**: правовую опору проверять отдельно.

## Поиск информации

При анализе пункта может потребоваться веб-проверка: актуальная редакция нормы из ГК/НК/иного кодекса (pravo.gov.ru), актуальная ключевая ставка ЦБ для пунктов с процентами, рыночные практики формулировок, разъяснения по спорной норме.

Использовать инструменты по `references/web-research-tools.md`: Tavily /search для актуальных норм и ставок; WebFetch для прямого URL акта.

Поскольку clause-review возвращает строгий JSON по схеме (`references/clause-review-response-schema.md`), при недоступности инструментов — фиксировать неопределённость в полях `markers` (например, `[ПРОВЕРИТЬ СТАВКУ]`, `[ПРОВЕРИТЬ РЕДАКЦИЮ]`) и в `lawyerNote`. Не выдумывать ставки и редакции.

## Что запрещено

- Маркировать клаузу как «годная без правок» вместо юриста.
- Возвращать что-либо кроме JSON по схеме (исключение — режим развёрнутого обоснования по явной просьбе юриста в чате, см. «Формат ответа»).
- Выдумывать условия, которых нет в тексте.
- Делать вывод о договоре в целом по одному пункту.
- Цитировать конкретные нормы / практику без проверки.
- Указывать в `proposedWording` свободный текст, если в реестре `skills/clause-library/SKILL.md` есть готовая формулировка по типу клаузы (использовать реестр).
- Использовать эмоциональный тон в `counterpartyComment`. Стандарт — деловой и конструктивный.

## Маркеры

В полях `issue`, `recommendation`, `lawyerNote` допустимо использовать маркеры:
- `[ПРОВЕРИТЬ ФАКТ]`, `[ПРОВЕРИТЬ НОРМУ]`, `[ПРОВЕРИТЬ ИСТОЧНИК]`, `[ПРОВЕРИТЬ СРОК]`, `[ПРОВЕРИТЬ РЕКВИЗИТЫ]`, `[ПРОВЕРИТЬ КОРПОРАТИВНЫЕ ОДОБРЕНИЯ]`, `[ПРОВЕРИТЬ НАЛОГОВЫЕ ПОСЛЕДСТВИЯ]`, `[СТРАТЕГИЧЕСКОЕ РЕШЕНИЕ ЮРИСТА]`.

В `proposedWording` и `counterpartyComment` маркеры **не используются** — это готовый текст для копирования.
